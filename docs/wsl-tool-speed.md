# Windows와 WSL의 도구 호출 속도 비교

CUELO를 Windows 네이티브에서 WSL2(Ubuntu) 단일 실행으로 옮긴 뒤, 같은 PC에서 에이전트 도구 호출의 속도와 실패율이 어떻게 달라졌는지 세션 기록으로 비교한 결과입니다. 2026-10-09에 한 번 측정했으며, 이후 버전에서 다시 재지 않았습니다.

## 측정 방법

- **대상:** 같은 PC에서 Windows 호스트로 실행한 세션과 WSL에서 실행한 세션의 도구 결과 기록입니다. 이관 때 복사만 된 옛 세션은 WSL 쪽에서 뺐습니다.
- **기간과 표본:** Windows 2026-09-29 ~ 10-09, 약 28,000건. WSL 2026-10-06 ~ 10-09, 약 3,500건.
- **시간:** 도구 호출 하나가 시작해서 결과를 돌려줄 때까지의 시간입니다. 모델이 생각하는 시간은 들어가지 않습니다.
- **p50·p90:** 호출을 빠른 순으로 세웠을 때 50%·90% 지점의 시간입니다. p50은 보통 걸리는 시간이고, p90은 열 번 중 느린 한 번을 뺀 상한입니다.
- **실패율:** 도구가 오류로 끝난 비율입니다. 사용자가 중간에 끼어들어 실행되지 않은 호출과, 배포 재시작으로 끊긴 대기는 실패에서 뺐습니다.

## 읽는 법

- **짧은 도구는 몇 ms~수십 ms 느려졌습니다.** read·grep·write·todo·glob의 p50이 2~10배가 됐지만, 절대값으로는 수십 ms 안쪽입니다. 사람이 체감할 차이는 아닙니다.
- **긴 도구는 빨라졌습니다.** bash·eval은 p50이 절반 이하로 줄었고, p90(느린 쪽)도 크게 줄었습니다. Windows에서 셸과 런타임을 띄우는 비용이 빠진 효과로 보입니다.
- **느린 꼬리는 대부분 줄었습니다.** read·write·eval의 p90이 Windows보다 낮습니다. 평소 속도보다 가끔 굼뜬 정도가 줄었다는 뜻입니다.
- **git_finalize 실패율 14.8%는 표본이 27건이라** 4건만으로도 이 값이 됩니다. 같은 기간 WSL 쪽 작업은 대부분 이관·배포·진단이어서 실패가 몰리는 작업 구성이었습니다.

## 한계

- **OS만 바뀐 비교가 아닙니다.** 두 기간 사이에 내장 omp 코어 버전과 하는 일의 종류가 바뀌었습니다. 차이 전부를 WSL 효과로 보면 안 됩니다.
- **WSL 표본이 작습니다.** 약 3.6일, 세션 23개입니다. 건수가 적은 도구(glob·git_finalize·skim)의 비율은 흔들리기 쉽습니다.
- **Windows 드라이브 위 프로젝트(`/mnt/c` 등)는 거의 들어 있지 않습니다.** WSL에서 Windows 드라이브의 파일을 Linux 도구로 대량으로 다루면 WSL 디스크(ext4)보다 훨씬 느립니다. 같은 날 따로 잰 값으로는 파일 약 3,900개 저장소의 `git status`가 ext4에서 6ms, Windows 드라이브에서 약 4초였습니다. 그래서 파일이 많은 작업은 WSL 디스크 안의 사본에서 하는 편이 낫습니다. CUELO는 Windows 드라이브 위 저장소의 Git 명령을 Windows Git으로 실행해 이 차이를 줄입니다([하네스 안내](./harness.md#git-마감-도구)).

## 같은 비교에서 찾아 고친 것

이 비교는 속도 외에 실패 종류도 함께 봤습니다. 총 실패율은 줄었지만, 오류로 표시되지 않는 조용한 실패가 몇 가지 있었고 `0.10.4`에서 고쳤습니다.

- WSL에서 코드 정의·참조 찾기(LSP)가 언어 서버를 찾지 못하던 문제
- 에이전트 셸이 실행한 `wsl.exe`의 메시지가 깨져 보이던 문제
- 의미 검색의 판정 질문이 32개를 넘으면 판정 서비스가 요청을 거절하던 문제
- WSL에서 SHION 상담 기록이 비어 보이던 문제
- WSL 갱신의 미리 빌드가 CPU·메모리를 모두 써서 중간에 끝나던 문제

자세한 변경은 [변경 기록](../CHANGELOG.md)의 `0.10.4`를 참고하세요.
