# CUELO가 사용하는 공개 OMP 하네스

OMP 하네스는 코딩 에이전트가 요구를 작업으로 나누고, 변경을 검증하고, 증거로 검수하는 작업 규칙·SOP·확장·core 패치의 묶음입니다. 공개 트리는 [`Tools/OMP_Global_Config/agent/`](../Tools/OMP_Global_Config/agent/)와 [`Tools/OMP_Global_Config/patches/`](../Tools/OMP_Global_Config/patches/)에 있습니다. CUELO 앱과 구분되는 omp 작업 환경용 자료입니다.

## 설치와 공개 범위

공개된 `agent/`는 [설치 안내](installation.md)의 `setup`이 사용자의 `~/.omp/agent`에 복사합니다. 이미 있는 파일은 바꾸거나 지우지 않고, 없는 파일만 추가합니다. `config.yml`이 없는 프로필에는 기본 운영 설정(학습·메모리·요청 예산)으로 새 파일을 만들고, 제공자 요청을 스스로 쓰는 자동 기능은 꺼 둡니다. 이 저장소에는 사용자별 모델 설정이 없으므로 `modelRoles`는 사용자가 정합니다. 설치 때 `--model`(core `default`)과 `--role <이름>=<provider/model>`을 직접 넘기면 그 새 파일에 그 값만 적고, 나중에는 CUELO 설정의 Model roles 화면에서 바꿉니다. 기존 `config.yml`은 보존되어 플래그를 다시 줘도 역할·Jev 설정이 채워지지 않습니다. [기존 프로필 보완 절차](installation.md#기존-프로필의-역할과-jev-보완)를 따르세요. 지정하지 않은 하네스 역할은 `maker_route`에서 해당 후보만 사용 불가로 표시됩니다. CUELO 앱 자체는 이 하네스를 설치하지 않아도 기본 대화가 가능합니다.

공개 저장소에는 역할·검수 절차와 런타임 확장, 정책 규칙, core 패치가 포함됩니다. 반면 계정이나 모델 선택 정보를 담는 `config.yml`·`models.yml`, 개인 skills, 작업 기록은 공개하지 않습니다. npm 패키지도 해당 개인 파일과 제공자 API 키, 독립 `omp` CLI를 동봉하지 않습니다. 설치에 필요한 Node/Bun/Git과 기능별 CLI·메모리 모델의 경계는 [설치 안내](installation.md#새-windows-pc에서-먼저-준비할-것)를 따릅니다.

공개 설치기의 `--role` 옵션과 CUELO 모델 역할 화면에서 Maker 후보뿐 아니라 검토·도구·판정 역할도 지정합니다. 역할별 제공자 조건과 설정 방법은 [설치 안내](installation.md#하네스-도구검토판정-역할)를 따르세요. CUELO 패키지의 SDK 패치는 CUELO 런타임에만 적용되며 사용자가 별도로 설치한 `omp` CLI에는 적용되지 않습니다.

WSL 프로젝트에 기존 Windows 소스 사본이 명시적으로 연결되어 있으면, 작업을 마무리할 때 검증·게시한 커밋을 Windows 사본에도 반영합니다. 이는 한 대화의 임시 선택이 아니라 [전역 규칙](../Tools/OMP_Global_Config/agent/RULES.md)의 공통 세션 정책입니다. Main은 `git_finalize` 뒤 설치된 `tools/git-finalizer/sync-checkout.ts`를 `--source`, `--target`, `--revision`으로 호출합니다. 같은 origin·branch의 깨끗한 사본만 정확한 커밋으로 fast-forward하며, 미커밋 수정·미추적 파일·갈라진 이력은 보존하고 알립니다. UNC로 WSL 폴더를 여는 것만으로 Windows 사본을 갱신했다고 보고하지 않습니다. 실시간·양방향 감시나 새 사본 생성은 하지 않고, 설치된 프로필·인증 DB·세션·실행 산출물·독립 CLI도 복사하지 않습니다. WSL 단일 CUELO의 실행본·활성 프로필 배포는 별도 지원 절차를 따릅니다.

내장 코어는 OMP **18.12.6**을 사용합니다. 18.12.1에서는 upstream이 모델 목록 조회가 끝나기 전의 캐시 상태도 아직 조회 중으로 보고, 조회가 끝난 뒤에도 없는 모델만 한 번 경고합니다. 그래서 시작 직후 잘못된 모델 없음 경고를 막던 CUELO 패치는 18.12.1 이상에서 적용하지 않습니다. 18.11.3에서 upstream은 저장된 세션을 읽기 전용으로 상담하는 `seance` agent를 추가하면서 다른 agent의 발주별 `model`을 거절하게 했습니다. 패치된 SDK는 `maker` agent의 모델 selector 하나만 계속 받아 Main이 고른 `<후보>:auto`를 그대로 넘기며, 그 밖의 agent에는 upstream 거절을 유지합니다. 학습 근거 경로 오류는 프로젝트 루트의 절대 경로를 보이지 않고 「the project root」라고만 알립니다. 긴 응답 뒤 문맥 한도를 넘었을 때 최근 대화를 남겨 두고 앞부분을 압축하는 upstream 수정과, 종료한 SDK 세션의 MCP 관리자가 메모리에 남던 문제의 수정을 반영합니다. 18.10.4에서 upstream이 Codex Code Mode를 없애면서 computer 선언 파일도 사라졌으므로, CUELO가 그 파일에 넣던 보조 선언은 18.10.4 이상에서 적용하지 않습니다. 모델에 보이는 computer 도구 안내는 그대로입니다. 18.10.2부터 upstream은 task 서브에이전트의 구조화 결과(`yield`·`outputSchema`)를 `task.structured` 설정으로 켜고 끄며 기본값은 꺼짐입니다. CUELO의 Maker 완료 보고는 구조화 결과를 쓰므로 하네스 프로필의 `config.yml`이 이 설정을 켭니다. 18.9.1부터 upstream이 동시에 열린 세션마다 백그라운드 작업 관리자를 따로 두고 자식 작업에는 부모의 관리자를 그대로 넘기므로, CUELO는 이 부분의 SDK를 고치지 않고 그 구조가 있는지만 확인합니다. 긴 eval·터미널 출력 처리, 병렬 셸 초기화, 계정 갱신과 유효한 기억 연결에 관한 upstream 수정을 반영합니다. 계정 상속에는 upstream의 제공자별 필터를 사용하면서 CUELO의 지정 계정 고정과 Maker 계정 선택 규칙을 유지합니다. 기존 core 패치의 이전 18.9.1 적용 경로도 보존합니다. 18.7.0부터 추론 강도를 직접 고르면 대기 중인 prewalk 모델 인계가 풀립니다. 웹의 「Auto, 최대 X」 상한을 바꾸거나 재시작 때 상한을 복원하는 것은 강도 선택이 아니어서 그 자체로는 인계를 풀지 않습니다. 부모 메시지로 깨어난 SubAgent turn의 답은 부모가 기다리거나 취소할 수 있는 async 작업으로 전달됩니다. 패치된 내장 코어는 이미 실행 중이던 turn에 부모 지시가 끼어든 경우 그 turn이 지시를 실제로 처리했는지 끝난 뒤에 판단하고, 한 turn의 답은 한 번만 정산합니다. 그래서 처리하지 못한 지시를 이어받은 다음 turn과 함께 부모가 답을 두 번 받거나, 그 사이에 다른 메시지가 끼어들어 답이 빠지지 않습니다. CUELO 웹 서버에서 띄운 셸과 이름 있는 service에는 Linux·macOS의 PTY 실행을 포함해 서버의 `NODE_ENV`·`PORT`·Next 내부 변수가 넘어가지 않습니다. 발주별 모델 전달과 advisor 기록 제외 내보내기는 upstream 구현을 사용하고, Maker의 단일 모델·승인 후보·소유권 검증은 그대로 적용합니다. 공식 standalone CLI와 패치된 내장 코어의 동작 범위는 구분합니다. 완료율 추정 설정은 `task.completionProbe`이며, 웹의 SDK 실행 경로에서는 주기적인 추가 추정 요청을 하지 않습니다. 기존에 이 기능을 꺼둔 환경에는 이 항목의 추가 호출 절감이 없습니다. 18.12.3에서는 upstream이 부모 지시가 실제로 처리된 뒤에야 그 turn의 답을 부모에게 보내는 판정을 직접 갖췄습니다(#16305). 패치된 내장 코어는 같은 정산을 그 판정 위에 얹고, 모든 에이전트에게 보내는 일괄 메시지(broadcast)는 부모의 지시로 세지 않습니다. 그 버전부터 `computer.control.acquire`의 반환 안내 문구는 upstream 것을 그대로 씁니다.

18.12.6의 MCP 재인증 명령은 서버의 로컬 `omp` 터미널에서 사용합니다. CUELO 웹은 브라우저·인증 callback을 연결하지 않은 이 명령을 계속 거절하며, 인증 URL을 기다리는 상태로 들어가지 않습니다. 다른 MCP 명령은 기존 처리 경로를 유지합니다.

캐릭터 확장(`character-voice.ts`)의 RIN·MIO는 Anthropic OAuth 계정의 0번·1번 자리를 기본으로 씁니다. 이 번호는 로그인한 순서로 정해지는 자리일 뿐 계정 ID·이메일 같은 개인 정보가 아니며, 공개본에서도 코드 그대로 동작합니다. 해당 자리에 쓸 자기 계정은 `omp`로 직접 로그인해 준비합니다. 계정이 하나뿐인 상태에서 MIO로 전환하면 1번 자리 계정을 찾지 못했다고 알리고 현재 세션 모델을 유지합니다.

패치된 내장 코어에서는 한 계정의 로그인이 만료되거나 인증이 취소돼도 그 계정의 자리가 비어 있을 뿐, 뒤 계정이 앞 자리로 당겨지지 않습니다. 그래서 0번 계정이 만료돼도 1번 계정은 계속 MIO이고, 빈 0번 자리(RIN)를 고르면 다른 계정으로 대신하지 않고 계정을 찾지 못했다고 알립니다. 같은 계정으로 다시 로그인하면 원래 자리로 돌아오며, 그 계정에 걸어 둔 수동 끄기와 사용량 대기는 그대로 남습니다. 같은 조직의 다른 계정으로 로그인하면 빈 자리를 차지하지 않고 새 자리를 받습니다. 로그아웃한 계정은 자리를 반납합니다. 사용량 패널은 인증이 실패한 계정을 수동 끄기·사용량 대기와 구분해 재로그인 안내로 보여 주며, `omp usage`도 같은 조직의 다른 계정 인증 실패를 숨기지 않습니다. `omp token --account N`과 `/session pin N`의 번호도 이 자리 번호입니다.

## 문서 편집 기본 도구

기존 Word·Excel·PowerPoint 문서의 열기·편집·변환은 LibreOffice의 Writer·Calc·Impress를 우선 사용합니다. 새 문서 초안은 기존 `draft` 절차를 따릅니다. 사용자가 MS Office를 지정하거나 매크로·외부 연결·전용 기능·서식 호환성 때문에 필요한 경우에는 MS Office를 사용합니다.

원본은 보존하고 복사본이나 새 출력 파일에서 작업합니다. 저장·변환 뒤에는 변경 영향 범위의 한글 글꼴·배치·표·수식과 계산 결과를 확인합니다. Craft나 프로그래밍 라이브러리로 기존 문서를 다시 저장하려면 해당 형식·버전의 보존 검증이 필요합니다. LibreOffice가 없거나 필요한 기능을 처리하지 못하면 그 사실을 알리고 검증된 대안을 선택하며, 이 기본값만으로 프로그램 설치·삭제나 MCP 등록을 수행하지 않습니다.

## UI·문서 산출 전 점검

화면 코드나 강의·보고용 HTML·문서를 사용자에게 넘기기 전에 `kill-ai-slop` 스킬의 스캐너(`scripts/scan.mjs`)로 제네릭한 AI 스타일 징후를 확인합니다. 적중은 판정이 아니라 단서이므로 해당 코드를 읽어 확정하고, 확정한 징후는 고치거나 의도적으로 남긴 이유를 보고에 적습니다. 스캐너는 한국어 문구를 보지 않으므로, 한국어 사용자용 문구(데이터 파일 속 문항·보기·표 문자열 포함)는 번역투·쉼표 과다·과장 어휘 같은 패턴 목록으로 넘기기 전에 감지만 합니다. 사용자나 과제가 문구 수정을 요청하면 같은 스킬의 교정 절차를 범위 안 모든 문자열에 끝까지 적용합니다. 한 번만 나와도 결정적인 패턴 7개는 스킬 본문에 표로 두어, 상세 참조 파일을 다 읽지 않아도 등급이 틀리지 않게 합니다. 굵은 글씨 강조는 문단당 1개까지로 둡니다. 이 점검은 권고 절차이며 빌드나 커밋을 막는 검사가 아닙니다.


## 이전 세션 원문 회수

CUELO Main에는 `session_recall` 읽기 전용 도구가 있습니다. 기본 구성에서는 `read xd://session_recall`로 사용법을 확인한 뒤 `write xd://session_recall`에 JSON 인자를 전달합니다. 도구를 모두 끈 세션과 Maker·복구된 Maker에는 노출하지 않습니다. Ctrl+K의 사람이 쓰는 대화 검색은 그대로입니다.

- 검색: `{"query":"배포 승인"}`. 공백으로 나눈 단어가 모두 들어 있는 사용자·assistant 텍스트를 찾습니다(대소문자 무시, 구문 검색 아님). 현재 프로젝트가 기본이며 워크트리는 같은 프로젝트로 취급합니다.
- 주변 읽기: `{"session_id":"<검색 결과 sessionId>","entry_id":"<entryId>","radius":3}`. 선택된 현재 분기에서 앵커 앞뒤의 대화를 읽습니다. 파일 경로를 직접 입력하지 않습니다.
- 현재 세션은 최신 압축으로 가려진 구간만, 다른 세션은 선택된 분기의 대화를 대상으로 합니다. 현재 문맥에 남은 메시지·분기에서 버린 메시지·도구 결과·thinking·압축 요약은 돌려주지 않습니다. fork로 복사된 대화도 중복 반환하지 않습니다.
- 보관된 세션은 `include_archived: true`, 다른 프로젝트는 `scope: "all_projects"`를 명시한 경우에만 포함하며 출처를 표시합니다. 자격증명 패턴은 반환 전에 가립니다.
- 검색은 최대 8건·세션당 2건, 읽기 반경은 기본 3·최대 8입니다. 시간·읽기량·결과 수·출력 한도, 읽는 도중 바뀐 파일이나 읽기 불가 파일로 일부만 처리하면 `status: "partial"`과 `incomplete` 사유 배열을 반환합니다. 빈 부분 결과는 기록이 없다는 뜻이 아닙니다. 시간 예산은 처리 경계에서 확인하며 진행 중인 파일 목록·stat 호출을 강제로 중단하는 실시간 제한은 아닙니다.

도구는 저장된 대화를 수정하거나 새 색인 DB를 만들지 않습니다. 원문은 당시 발언의 증거이지 현재 지시·실행 승인이 아니며, 현재 요청과 적용 조건을 다시 대조해야 합니다. 미결 작업을 자동으로 상시 수정하는 기능도 아닙니다.

## 컨텍스트와 압축 운용

`contextWindow`는 하네스가 인식하는 모델의 문맥 용량이고, `compaction.thresholdPercent`·`thresholdTokens`·`modelThresholds`는 압축 시작점을 정하는 core 설정입니다. 모델별 항목은 `provider/model-id`의 정확한 ID부터 해석하므로 새 ID가 이전 모델의 override를 자동 상속하지 않습니다. Main과 Maker 모두 해당 core 해석을 사용하며 압축 때마다 JEV가 결정하거나 별도 hook을 호출하지 않습니다. 창 값을 바꿔도 제공자 자체의 실제 지원 범위가 늘어나는 것은 아닙니다.

OMP 18.8.9부터 `modelThresholds`의 숫자는 고정 압축 시점이 아니라 백분율을 적용할 기준 창입니다. 예를 들어 기준 `500000`과 `thresholdPercent: 70`은 350,000 토큰에서 압축합니다. 이전 버전의 고정 시점 `350000`을 그대로 넣으면 백분율이 다시 적용되므로 업그레이드 시 실효값을 확인해야 합니다. 이 기준 창은 모델의 `contextWindow` 자체를 바꾸지 않습니다.

변경은 실제 요청 구간·압축 빈도·압축 뒤 재탐색·보고 비용과 품질 근거로 판단합니다. 역할·모델별 조건을 나누고, 보고되지 않은 비용·캐시 쓰기를 0으로 추정하지 않습니다. cache read/write 및 압축 뒤 재작성 비용을 함께 보고, API 가격 환산과 구독 사용 한도를 혼동하지 않습니다. [Claude Code 비용 안내](https://code.claude.com/docs/en/costs)와 [Codex 설정 참고](https://developers.openai.com/codex/config-reference)도 비용과 문맥·압축 설정의 차이를 설명합니다. 개인 사용 이력에서 나온 “400K·29% 절감”은 이 하네스의 재현 결과나 품질 보장이 아닙니다. 이는 운영·측정 원칙이며 내부 분석 도구나 개인 측정 자료를 공개 설치에 동봉한다는 뜻은 아닙니다.

압축·재개 뒤에는 기존 결정·보존 계약·미결 작업·검증 명령과 종료 코드·artifact locator부터 이어받습니다. 과거 지시가 결론에 영향을 주는데 불명확하면 위 원문 회수 도구로 좁게 확인합니다. 토큰 수만으로 작업을 끊거나 재시작 직전 강제 압축을 추가하지 않으며, 고정 사용량 절감이나 더 나은 완료 품질을 자동 보장하지 않습니다.

모델 통계의 캐시율은 `cacheRead / (input + cacheRead + cacheWrite)`입니다. 캐시 수치를 보고하지 않는 판정 API는 「미보고」로, 메타데이터가 없어 보고 여부를 가릴 수 없는 경우는 「알 수 없음」으로 표시합니다. 이 표시만으로 캐시 기능의 미지원 여부를 판정하지는 않습니다. 전체 비율에서도 이 모델들을 제외하고 「일부」라고 알립니다. 가격표가 없는 사용량은 「가격 미상」으로 표시하며, 일부만 계산한 추정 비용은 `≥`로 구분합니다. 이는 토큰 단가 환산값의 하한이며 실제 청구액·구독료의 하한이 아닙니다.


## 역할과 작업 모드

[전역 안내](../Tools/OMP_Global_Config/agent/AGENTS.md)와 [Maker SOP](../Tools/OMP_Global_Config/agent/sop/maker.md)는 두 역할을 정의합니다.

- **Main**은 사용자 요구와 수용 조건, 승인, 작업 분할·라우팅, 중간 검수와 최종 판정을 소유합니다. 위임하지 않은 작업은 직접 수행합니다.
- **Maker**는 명시된 범위에서 조사·구현·재작업·자기 변경의 집중 검증을 끝까지 맡습니다. 별도 validator나 다단계 에이전트 역할을 기본 구조로 두지 않습니다.

`routine`은 Main이 한 흐름으로 끝내는 작업, `large`는 독립적으로 완료 가능한 조각을 분리하는 작업, `high-risk`는 결과나 코드 성질상 편집 전 Main 개입과 이후 drift 검수가 필요한 작업입니다. 규모와 위험은 서로 다른 축입니다. 상세 기준은 [subagent 규칙](../Tools/OMP_Global_Config/agent/rules/subagent.md) 및 기계 판독 가능한 [harness-policy.json](../Tools/OMP_Global_Config/agent/rules/harness-policy.json)에 있습니다.

### 대화의 작업 흐름

결과 카드와 실행 중 상태줄은 실제 도구 호출·결과를 바탕으로 작업 흐름을 보여 줍니다. 그래프에서는 Main과 Maker의 작업, 검사·교차리뷰·게시 단계와 재수정 경로를 구분하며, 관련 노드에서 기록·변경 파일·문서를 확인할 수 있습니다. 넓은 카드는 단계 상자를 한 줄로, 740px 이하 카드는 일어난 순서대로 적는 세로 레일로 그립니다. Maker 카드도 조사·구현·검증·보고·Main 판정을 같은 방식으로 보여 주며, 다시 깨운 Maker가 이번 실행 전에 받은 판정은 「이전 판정」으로 구분합니다. Maker의 업무 종류는 발주 기록에 있는 경우에만 표시합니다. 기록이 없다는 이유로 구현·진단 중 하나를 추정하지 않습니다. `.omp` 작업 폴더(omp가 읽는 설정 경로는 제외)나 시스템 임시 폴더에만 쓴 파일은 수정·변경 결과로 세지 않습니다.

끝난 턴이 화면(HTML)·문서(PDF·Word)·이미지를 결과물로 만들었으면 카드는 결과부터 보여 줍니다. 미리보기와 「결과 보기」가 맨 앞에 오고, 위 그래프와 남은 일은 접힌 채 아래에서 펼칩니다. 코드·설정·시험 파일과 Markdown 기록은 결과물로 꼽지 않습니다.

실제 진행 중에는 지금 단계의 진행 표시만 움직입니다. 완료되면 연결선과 판정 결과가 정지한 상태로 남습니다. 끝난 그래프의 「재생」을 누르면 실제로 지난 단계를 기록된 차례대로 다시 밝힙니다. 서브에이전트 갈래는 처음 수정 다음에, 되돌아온 재수정은 마지막 귀환 하나만, 변경 결과는 맨 끝에 밝힙니다. 재생이 끝나면 정지한 그래프로 돌아갑니다. 재생 간격은 일정해서 실제 걸린 시간을 뜻하지 않습니다. 움직임도 완료율이나 확인되지 않은 동시 실행을 뜻하지 않습니다. 동작 줄이기 설정에서는 재생이 움직임 없이 차례만 밝히며, 현재 상태와 기록 확인은 유지됩니다.

검증 결과는 검사한 뒤의 수정 여부와 함께 읽습니다. 앞서 통과한 검사가 있어도 이후 수정된 상태를 검증한 것으로 표시하지 않습니다. 종료 코드만으로 검사 실행 여부나 결과를 확정할 수 없는 복합 명령은 미확인으로 남고, 응답을 사용할 수 없는 교차리뷰가 앞선 실패를 지우지 않습니다.

실행 중 전달된 지시로 같은 작업의 대화가 나뉘면 이전 흐름을 이어 보되, 별도의 새 요청까지 합치지 않습니다. 비공개 파일 게시가 끝나고 공개 변경이 없어 CI가 생기지 않은 것으로 확인된 경우에는 CI를 「필요 없음」으로 표시합니다. 공개 코드 변경이나 결과를 모르는 게시까지 같은 상태로 처리하지 않습니다.

압축이나 서버 업데이트 재개로 요청의 시작 부분이 화면에서 가려져도, 같은 요청의 기록을 이어서 집계합니다. 완료 카드의 남은 일은 해당 시점에 저장된 할 일 상태를 따릅니다. 도구를 다른 도구 안에서 실행했더라도 저장된 상태를 사용하며, 답변의 완료 선언이나 임의로 출력한 문구를 성공 근거로 삼지 않습니다. 새 요청·다른 분기의 할 일이나 검사 결과가 과거 카드에 섞이지 않도록 구분합니다. 입력창 위 할 일 줄은 실시간 보고를 우선하며, 실행 중이 아닐 때도 저장된 최신 할 일 기록으로 복원합니다.

## 발주와 검수 계약

Main은 작업을 발주할 때 목표·사용자 수용 조건·보존 동작·허용 경로·검증 범위를 정합니다. [`maker_route`](../Tools/OMP_Global_Config/agent/rules/subagent.md)는 작업 분류와 남은 판단, 후보 적합성, 기존 owner와 중복되는지를 돕는 발주 전 판단입니다. 결과는 Main의 조언이지 자동 승인이나 자동 배정이 아닙니다.
`WORK_CLASS`를 명시하면 준비 단계에서도 `feature`·`maintenance`·`diagnostic` 중 하나인지 확인합니다. 잘못된 값은 모델 판정이나 준비 참조 발급 전에 오류로 알리고, 다른 값으로 추정해 바꾸지 않습니다. 후속 발주의 생략·상속 규칙은 그대로 유지합니다.
준비 참조로 발주할 때 `name`을 생략하면 그 참조에 저장된 이름을 복원합니다. 이름을 명시했다면 준비한 이름과 정확히 같아야 합니다. `model`은 추천에서 자동으로 채우지 않으며, Main이 선택한 후보를 `:auto`를 붙여 반드시 전달합니다. 준비 참조의 세션·배치·유효성 검사도 유지합니다.
Main이 추천을 본 뒤 다른 후보를 고르거나 새 발주를 선택하면, 준비 참조 바로 다음 줄에 `ROUTING_REASON: <근거>` 한 줄을 붙여 발주합니다. 복원한 원문 끝에 그 줄이 붙고, 추천 변경 검사는 그 근거를 그대로 확인합니다. 근거를 `context`에 넣었더라도 참조가 하나뿐이고 그 참조에 근거 줄이 없으면 그 task의 근거로 옮겨 발주합니다. 참조가 여럿이거나 그 밖의 줄을 덧붙이면 지금처럼 거절합니다.
같은 배치로 여러 작업을 발주하면 공통 후보·판단 기준은 한 번 해석하고, 마지막 비동기 조회 뒤 전체 항목의 준비 정보와 소유권을 확인해 예약합니다. 다른 발주에서는 현재 후보를 새로 확인하므로, 배치 사이에 바뀐 조건을 오래된 캐시로 통과시키지 않습니다.
Main은 자신이 읽고 활용한 Skill 가운데 맡길 조각과 관련된 것만 브리프에 넘깁니다. Skill 이름과 필요한 절, Main이 적용한 판단, 아직 불명확한 점을 짧게 적고 원문 전체는 복사하지 않습니다. 필수 Skill은 Maker가 착수 전에 직접 읽으며, Main의 요약이 그 직접 확인을 대신하지 않습니다. 적용이 헷갈리거나 요약과 현재 코드가 어긋나면 Maker가 해당 절을 다시 확인하고, 실제로 적용한 판단과 근거를 완료 보고에 연결합니다. 이 인계는 자동 차단 검사가 아닙니다.

Skill을 쓰기로 했으면 그 Skill의 절차와 기준대로 결과를 냅니다. 직접 만든 정규식·스크립트·발췌로 절차 일부를 대신했거나 범위를 줄였다면 그 결과를 Skill의 결과로 부르지 않고, 대신한 부분과 빠진 범위를 보고에 밝힙니다. 컨텍스트가 모자라면 기준이나 범위를 줄이는 대신 파일 단위로 나누거나 Maker에게 맡깁니다.

보고에 실행 기록에서 온 수치의 비교·추이·분해가 있고 값이 셋 이상이면, Main은 표나 문장 옆에 Mermaid 차트(막대, 시간선 등)를 하나 넣습니다. 전후 측정, 실행 시간, 단계별 소요, 통과·실패 수가 그런 값입니다. 최종 보고만이 아니라 진행 중 중간 보고, 한 문장 안에 나열한 수치, 결정을 묻는 질문 앞 근거 문장에도 적용하며, 수치를 근거로 결정을 물을 때는 차트를 먼저 보이고 묻습니다. 값은 도구 출력·실행 기록·측정 산출물에서 온 것만 쓰고 출처를 적습니다. 산문에서 추정한 수치로는 그리지 않습니다. 측정 횟수와 편차를 적는 규칙은 그대로입니다.

Main이 완료된 Maker에게 `write agent://<id>`로 후속 지시를 보내면 런타임 advisory는 같은 session의
실제 attempt에 `routing_verdict`가 아직 기록되지 않았는지 알려줍니다. Main은 증거를 보고
`accepted`·`rework`·`held`를 직접 기록합니다. 증거 보충 요청은 자동 재작업 판정이 아닙니다.
Main은 최종 판정과 `routing_verdict` 저장 성공 확인을 같은 단계에서 끝냅니다. 산출물을 사용하거나 다음 실험·배포로 넘어간 것으로 기록을 대신하지 않습니다. 최종 답변 전에는 이번 요청의 실제 실행 식별자별 완료 attempt와 판정 기록을 대조합니다. 이미 확인한 증거는 재사용하며, 근거가 부족하면 이유를 붙인 `held`로 남깁니다. 누락 표시를 없애기 위해 자동으로 수용하지 않습니다. 이는 Main의 마감 절차이며 별도 자동 합격이나 발주 차단 장치가 아닙니다.
`held`는 기록된 판정이지만 닫힌 판정은 아닙니다. 같은 일을 재개나 새 발주로 다시 맡겨 끝냈다면 Main은 옛 시도를 근거와 함께 `rework`나 `accepted`로 닫고, 보류 이유가 그대로인 발주는 최종 답변에 열린 보류로 밝힙니다. 새 Maker를 시작하면 발주 식별자 안내가 그 세션에서 마지막 판정이 `held`인 발주를 함께 보여 줍니다. 원장이 두 발주를 자동으로 잇거나 닫지는 않습니다.
`routing_verdict`의 `revision`은 Main이 실제로 검수한 revision입니다. 원장은 Maker 완료 보고에서 관측한
`sourceRevision`을 함께 보존합니다. 원본과 같으면 `same`, 다르지만 Main이 `integratedFrom`에 원본을
명시하면 `integrated`, 연결이 없거나 틀리면 `mismatch`, 원본을 관측하지 못했으면 `unknown`으로 기록합니다.
같은 commit을 가리키는 서술(짧은 해시와 긴 해시, 뒤에 붙은 설명의 차이)은 `same`으로 보고, `integratedFrom`도
같은 표기 차이를 허용합니다. 완료 보고의 revision이 객체이거나 `sourceRevision`이라는 이름으로 와도 읽습니다.
기록마다 그렇게 판정한 이유(`revisionRelationCause`)를 함께 남기고, `mismatch`이면 넘겨야 할 `integratedFrom` 값을 알려 줍니다.
검수 revision을 생략한 `held`도 `unknown`입니다. `integratedFrom`은 연결 주장이며 실제 검수 근거는
기존 `reason`·`evidenceLocators`에 남깁니다. 불일치나 미관측 때문에 수용을 자동 거절하지 않고,
검수 revision이 있으면 진단을 돌려줍니다. 과거 기록의 원본을 추정하거나 품질 집계를 다시 쓰지 않습니다.
자동 전달된 결과도 실제 작업의 종료 상태를 보존합니다. 상태가 없으면 같은 작업의 확인 가능한 종료 기록을 사용하고, 그것도 없으면 정산을 보류합니다. 오류 본문을 키워드로 추측하거나 미확인 결과를 완료로 기록하지 않습니다. 실패한 작업은 완료를 전제로 한 수용 대상이 아닙니다.

Main이 시작한 bash/eval 백그라운드 작업은 관측 없이 계속 기다리지 않도록 보완합니다. 처음 5분이 지난 뒤 `wait`에 들어가려 하면 해당 `proc://` 확인을 요구하고, 이미 `wait` 중이면 기존 알림 경로로 깨웁니다. `wait` 밖에서는 정기 알림을 보내지 않습니다. 관측 기한이 지난 작업을 확인하지 않은 채 다시 `wait`하는 호출은 거절하지만, 다른 작업과 로그 조회는 계속할 수 있습니다. 차단을 풀려면 해당 `read proc://<id>`가 성공해야 합니다.

첫 확인은 출력 비교 기준만 세우므로 다음 기한도 5분입니다. 이후 출력이 바뀐 확인 뒤에는 다음 기한을 10분·15분으로 넓히고, 같으면 5분으로 돌아가 원인 확인을 요구합니다. 이미 끝난 작업의 결과는 먼저 회수할 수 있습니다. 사용자 승인 대기·서비스·서브에이전트에는 이 추가 감시를 적용하지 않으며, 서브에이전트의 기존 활동 감시는 유지합니다. 작업을 자동 취소·재실행하거나 정기적으로 모델에게 상태를 판정시키지 않습니다.

Maker 조각이 예상 시간을 넘기고 같은 막힘이 이어지면, 특히 여러 Maker가 함께 쓰는 개발 서버·브라우저 같은 검증 환경 때문이면, Main은 원인을 확인한 뒤 환경을 되살리며 계속 기다리지 않습니다. 그 Maker에게 지금까지의 수정본과 증거, 확인하지 못한 항목을 보고하게 하고 남은 확인과 통합을 직접 끝냅니다. 경과 시간만으로 회수하지 않고, 진행 중인 명령과 이미 통과한 검사는 다시 하지 않습니다.

Maker를 발주한 뒤 Main은 곧바로 기다리지 않습니다. Maker가 맡은 파일과 겹치지 않는 자기 몫부터 끝냅니다. 사용자에게 보일 문서와 변경 기록, 현재 상태 문서와 작업 기록 초안, 이미 확정된 변경의 읽기 전용 중간 검수, 다음 단계의 검사 준비가 여기에 듭니다. 남은 일이 모두 Maker 결과에 달렸을 때만 기다리며, Maker가 맡은 파일은 그 Maker에게 넘겨받기 전에는 고치지 않습니다.

긴 완료 보고는 표시용 미리보기와 검수용 원문을 구분합니다. 패치된 코어는 실제 완료 결과의 본문을 자식 식별자·실행 시작 시각과 함께 기존 결과 전달 경로에 보존하고, 확장은 자신이 관측한 같은 작업·시도·실행과 일치할 때만 검증 근거를 읽습니다. 자동 전달·`wait`·`proc://` 조회에서 동일하게 적용되며, 예전 대기열의 결과를 같은 이름으로 다시 실행된 작업에 붙이지 않습니다. 원문이나 실행 근거가 없으면 미관측으로 남기고, 미리보기의 경로를 따라 임의 파일을 열거나 누락된 근거를 합격으로 추정하지 않습니다.

Main의 사전 검수 안내에는 발주 당시 실제 사용자 요청의 제한된 발췌와 원문 위치, 발주문·수용 조건, 완료 근거가 함께 연결됩니다. 이후 명시적인 끼어들기 지시는 원 요청과 구분해 표시하고, 별개의 새 요청은 오래된 작업 결과의 원 요청을 대체하지 않습니다. 발췌가 잘렸거나 요청이 앞선 대화를 가리키면 원문 위치와 발주 맥락을 확인해야 합니다. 이 연결은 의미를 자동 판정하지 않으며, Main이 원래 요청과 실제 산출물을 대조하고 최종 수용을 결정합니다. 요청 원문을 별도 원장에 저장하거나 새 모델 검수 호출을 추가하지 않습니다.
서로 다른 호출에서 표시 이름과 작업 계약을 재사용해도 실행 초안과 결과 연결은 호출별로 유지합니다. 준비된 판단을 재사용하는 격리 작업도 각자의 실제 작업 식별자로 기록합니다. 하나가 종료되면 그 작업의 경로만 풀리고, 다른 작업과 재개된 작업의 경로는 계속 보호합니다.
취소 요청만으로 소유권을 풀지는 않습니다. 같은 실행의 실제 종료를 확인하면 다음 발주 전에 취소 결과와 담당 경로를 정산하므로 별도 조회가 필요하지 않습니다. 최근 표시 목록 밖으로 밀린 작업도 코어에 보관된 해당 실행의 종료 기록으로 확인합니다. 종료 중이거나 기록이 사라졌거나 다른 실행의 기록뿐이면 보호를 유지합니다. 이 조회는 대응하는 코어 패치와 확장을 함께 적용해야 하며, 이전 코어에서는 기존 조회 범위의 근거만 사용합니다.

취소되거나 실행 시간 한도를 넘긴 하위 작업은 정리 도중 처음 완료 내용을 보내더라도 성공으로 전환되지 않으며, 기존 수용 결과 파일을 덮어쓰지 않습니다. 늦게 얻은 내용과 기록된 사용량은 중단된 시도의 진단 근거로 남습니다. 정상적인 결과 제출로 실행이 종료된 경우는 계속 성공으로 처리하고, 취소 전에 이미 수용한 결과를 뒤늦은 취소나 추가 제출로 무효화하지 않습니다. 이 보호는 이미 실행된 파일 쓰기·외부 API 요청·과금을 되돌리는 기능이 아니며, 단순히 `wait`의 대기 시간이 끝난 것은 작업 취소와 다릅니다.

사용자 요구로 목적·범위·수용 조건이 바뀌면 변경된 사실로 `maker_route`를 다시 판단합니다.
UI/UX 전문성 경계가 새로 확인되면 비-Opus owner의 미완 변경·증거를 보존해 명시적으로 이관하며, 같은 Opus owner와 완료된 비-UI 작업은 재사용합니다.
Main이 실제 재작업을 지시할 때는 [검수와 수용](../Tools/OMP_Global_Config/agent/rules/subagent.md#검수와-수용)의
`REWORK task_id=... role=maker previous_revision=... next_revision=...`와
`finding_id=... source=...`를 후속 메시지에 넣어야 합니다. 평문 지시만으로 새 attempt가 기록되지는 않습니다.
REWORK 전송 뒤 시작된 재개 실행은 코어가 같은 job id를 다시 써도 그 실행 하나만 다음 attempt(`#a2` 등)로 기록됩니다.
CUELO가 재시작된 뒤에도 같은 Main 세션에서 이전 Maker에게 `write agent://<id>`를 보내면, 코어가 그 Maker의 저장된 대화와 도구·프롬프트 계약으로 되살려 메시지를 받게 합니다. 여러 Main 세션이 함께 열려 있어도 저장된 작업 경로에 따라 원래 부모에게 연결하며, 부모 정체성과 작업 깊이를 유지합니다. 재시작 순간 실행 중이던 도구 호출과 백그라운드 작업은 이어지지 않으며, `isolated` 작업 공간으로 띄운 Maker는 되살리지 않습니다.

하위 작업의 `Main` 별칭은 실제 부모 대화에 묶입니다. 부모를 확인하지 못하면 다른 대화의 Main을 대신 고르지 않고 오류로 알립니다. 재시작 뒤 여러 대화가 동시에 시작해도 ID를 함께 쓰지 않으며 복원된 하위 작업은 자기 대화의 부모에 연결됩니다.

갑작스러운 서버 종료 뒤에는 자동 복구 표시가 있는 **직전 서버 세대 하나**의 진행 기록만 확인합니다. 이전 프로세스의 종료와 대화의 중단 상태가 확인된 부모 세션에 상태 확인 후 이어 가라는 메시지를 보내며, 원래 명령을 그대로 재실행하지 않습니다. 완료·사용자 취소·실패로 끝난 실행, 사용자 답변·승인 대기, 이전 버전의 미표시 기록, 프로세스나 대화 상태를 확인할 수 없는 경우는 자동 대상이 아닙니다. Maker의 후속 행동은 복구된 Main이 남은 결과를 확인한 뒤 정합니다.

정상 업데이트가 남긴 재개 대기열은 보존합니다. 다만 재개 메시지를 보낸 직후 서버가 다시 종료되면 같은 안내가 한 번 더 갈 수 있으므로 정확히 한 번 실행되는 보장은 아닙니다. 복구 기록을 쓰거나 읽지 못해 자동으로 이어지지 않았다면 중단 알림에서 대화를 확인하고 직접 이어 가야 합니다.

WSL 갱신은 진행 기록의 서버 세대를 Linux 부팅 ID와 프로세스 시작 tick으로 확인합니다. 같은 프로세스라면 시스템 시각 보정으로 시작 시각이 달라 보여도 진행 세션을 제외하지 않고, 다른 세대나 종료된 프로세스의 기록은 사용하지 않습니다. 이 식별 정보가 없는 이전 버전의 기록은 기존 시작 시각 비교를 유지합니다.

`maker_route`에 표시되는 history는 Jev 분류 **후** Main에게 붙는 건수 advisory이며 분류 입력이나
모델·강도 자동 조정 근거가 아닙니다.

준비 단계는 `assessment.acceptance`나 `assessment.checks`가 비었거나 공백뿐이면 그 route에 `briefGaps` 경고를 붙입니다. 무엇을 만족해야 끝나는지, 어떻게 확인할지가 빠진 발주라는 뜻이며, Main은 수용 조건과 확인 방법을 채운 뒤 다시 준비합니다. `OWNED_PATHS`에 설명 괄호나 glob처럼 경로가 아닌 항목이 섞여도 같은 경고에 적습니다. 소유 판정은 경로 문자열 그대로 비교하므로 `app/globals.css (일부 블록)` 같은 항목은 실제 파일과 맞지 않아 겹침 검사를 빠져나가기 때문입니다. 같은 파일을 블록으로 나눠 맡기는 범위는 브리프 본문에 적습니다. 같은 준비 배치 안에서 공유 작업공간 소유 경로가 겹치면 `ownershipOverlaps`로 미리 알립니다. 그 배치를 그대로 내면 발주 단계가 배치 전체를 막으므로, Main은 경로를 나누거나 한 owner에게 맡기거나 격리 실행을 정한 뒤 다시 준비합니다. 두 경고 모두 발주를 막지 않고 모델 판정을 추가로 부르지도 않습니다.

이전 측정은 과제·하네스·모델 조건과 수용 품질, 표본 한계를 함께 봅니다. 합성 과제와 실제 제품 작업을 구분하고, 기존 계약·문맥 재사용 및 발주 준비·재작업·통합 검수 비용을 실제 독립 병렬 구간과 대조합니다. 모델 응답 생성과 도구 실행 시간을 섞지 않으며, 단독 대조군 없는 기록으로 속도 우열을 단정하거나 한 사례를 줄 수·인원수 임계값으로 만들지 않습니다.

등급(`NORMAL`·`HARD`)과 후보 슬롯은 구분합니다. 후보는 `NORMAL_SONNET`, `NORMAL_OPUS`, `NORMAL_SOL`, `NORMAL_DEEPSEEK`, `NORMAL_DAYBREAK`, `NORMAL_GEMINI`, `NORMAL_GLM`, `HARD_UI_OPUS`, `HARD_CODE_OPUS`, `HARD_CODE_SONNET`, `HARD_CODE_ASTRA`, `HARD_CODE_DAYBREAK`, `HARD_CODE_GEMINI`, `HARD_CODE_GLM`입니다. 기존 설정·라우팅 식별자 `implSol`·`NORMAL_SOL`·`SOL`은 유지하지만 해당 코드 후보의 실제 모델은 GPT-6 Astra입니다. NORMAL도 레이아웃·반응형·접근성·포커스·터치 표적 등 UI/UX 판단이 남으면 Opus를 선택하며, 이를 위해 HARD로 승격하지 않습니다. 비-UI NORMAL은 과제별 모델 적합성 판단 없이 기본으로 Sonnet을 추천하고, 아래 세 가지 경우에만 `NORMAL_DEEPSEEK`를 먼저 추천합니다. Main이 Sonnet 또는 `NORMAL_DEEPSEEK`가 사용 가능한데 `NORMAL_SOL`을 고르면 추천을 바꾸는 것이므로 `ROUTING_REASON`을 남깁니다. 기존 NORMAL Opus 명시 선택, UI/UX Opus unavailable의 명시 보고, HARD 코드 기본 Opus 및 이유가 필요한 `HARD_CODE_SONNET`·`HARD_CODE_ASTRA` 대안은 유지합니다.

`NORMAL_DAYBREAK`·`HARD_CODE_DAYBREAK`는 비-UI 코드 작업에 한해 Main이 이유(`ROUTING_REASON`)를 적고 고르는 대안입니다. 두 후보는 사용자가 지정한 `modelRoles.implDaybreak`를 `:auto`로 실행하며 기본 추천이나 자동 대체 순서에는 들어가지 않습니다. Daybreak 접근 프로그램은 코어가 해당 계정과 모델의 지원 정보를 보고 자동 적용합니다. 후보 이름이 권한을 부여하거나 프로그램 적용을 강제하지는 않습니다.

`NORMAL_GEMINI`·`HARD_CODE_GEMINI`(`modelRoles.implGemini`)와 `NORMAL_GLM`·`HARD_CODE_GLM`(`modelRoles.implGlm`)도 같은 방식의 명시 선택 전용 후보입니다. 사용자가 그 모델을 작업자나 검증자로 지목했을 때 Main이 `ROUTING_REASON`을 적고 `:auto`로 발주합니다. 역할 배정, 기본 추천, 자동 대체 순서, UI/UX Opus 경계는 바뀌지 않습니다.

비-UI NORMAL의 기본 추천은 Sonnet이고, Sonnet이 후보로 쓸 수 없거나 그 provider의 한도 소진이 관측되면 Hive의 DeepSeek 1017(`NORMAL_DEEPSEEK`)을 먼저 대체로 추천하고, 둘 다 쓸 수 없을 때만 코드 후보 Astra(`NORMAL_SOL`)를 추천합니다(2026-10-11의 "항상 Sonnet" 결정은 2026-10-18에 철회했습니다). 다음 두 가지 중 하나가 걸리면 Sonnet을 쓸 수 있어도 `NORMAL_DEEPSEEK`를 먼저 추천하며, 추천 사유에 걸린 조건을 적습니다. 첫째, 발주 전 판단이 "Main이 이 조각의 결과를 기다리지 않는다"고 본 경우입니다. 이번 요청이 그 결과 없이 끝나는 백그라운드·장시간 배치 작업(결과는 나중에 보고)만 해당하며, 그 사실을 assessment `facts`에 적습니다. 같은 요청 안에서 Main이 그 결과를 통합·검수·커밋·게시·보고해야 하면, 병렬로 돌거나 다른 조각이 더 오래 걸려도 기다리는 조각으로 봅니다. 판단이 불가하거나 그런 사실이 없으면 기다리는 것으로 봅니다. 둘째, 관측된 Anthropic 계정이 모두 7일 공유 구간에서 계정 선택기와 같은 정의의 오늘 몫(`(경과 일수+1)/7`, 최대 1)을 넘긴 경우입니다. 계정 하나라도 관측하지 못했거나 몫 이내면 Sonnet을 유지합니다. `FINDING_ID` 재작업은 이전 시도를 Sonnet이 맡았더라도 트리거가 아닙니다. 재작업은 Main이 결과를 기다리는 조각이기 때문입니다(2026-10-23에 이 트리거를 뺐습니다). DeepSeek는 내부 SJF 비교(12과제, 소표본)에서 Sonnet과 통과 수가 같았고 비용은 낮았지만 소요 시간은 중앙값 약 4.5배였으므로 결과를 기다리는 조각에는 쓰지 않습니다. DeepSeek를 쓸 수 없으면 트리거가 걸려도 Sonnet, 그다음 Astra 순이며, 셋 다 쓸 수 없으면 추천 후보가 없습니다. 트리거가 걸린 `NORMAL_DEEPSEEK` 선택에는 `ROUTING_REASON`이 필요 없고 다른 후보를 고르면 필요합니다. 한도를 관측하지 못한 것은 소진이 아닙니다. 계정 쿨다운·리셋·warm/exact pin과 기존 담당자 재사용은 그대로입니다. [Maker 코드 품질 평가](./maker-quality.md)는 그 과제와 측정 조건 안의 결과이며, Sol의 측정값을 Astra의 성능으로 대신하거나 새 모델의 일반적 우열을 증명하지 않습니다.

Maker의 추론 강도는 Main이 정하지 않습니다. 모든 Maker 후보는 `:auto`로 발주되고, child의 auto 분류기가 발주 항목의 `solutionSpace`를 입력으로 그 모델이 지원하는 가장 낮은 단계부터 가장 높은 단계(Opus는 `max`)까지에서 고릅니다. 정책에 강도 하한·상한을 두지 않습니다. child는 첫 턴을 `solutionSpace`로 분류하고 이후 Main이 보낸 지시마다 다시 분류합니다. 다시 분류할 때도 발주 때의 `solutionSpace`에 그 뒤의 Main 지시를 덧붙여 판단하므로, "승인, 계속" 같은 짧은 지시나 앞뒤만 남기고 잘린 브리프만 보고 강도를 크게 바꾸지 않습니다. 분류가 실패하면 직전 단계(첫 분류 전에는 잠정 단계)를 유지합니다. task hook은 `:high` 같은 구체 강도 suffix나 coarse `effort`를 넣은 발주를 막습니다. Main의 Auto 범위(`medium`~`xhigh`)는 바뀌지 않고, 실행 중인 세션의 모델도 소급 변경하지 않습니다. 재작업도 auto입니다. 수정 뒤 같은 검사가 같은 원인으로 다시 실패했거나, 검수에서 원인 오진·수용 조건 누락이 확인됐거나, 실행 중 범위가 늘었거나, Maker가 막혔다고 보고한 신호는 새 발주의 `solutionSpace`와 재작업 판정 사유에 적습니다. 예전의 후보별 강도 구간과 재작업 강도 한 단계 상향은 2026-10-08에 폐지했습니다.

`solutionSpace`에는 작업량이 아니라 남은 판단이 얼마나 열려 있는지를 적습니다. 해결 방법이나 설계가 이미 정해졌는지, 어떤 원인·설계 후보가 아직 열려 있는지를 쓰고, 모델·등급·강도나 다른 작업과의 조정은 적지 않습니다. 같은 전역 프로필을 쓰는 모든 프로젝트의 새 발주에 이 기준을 적용합니다.

Maker의 읽기 배치는 편집뿐 아니라 조사에도 적용합니다. 이미 필요한 구간을 알고 있으면 한 파일의 여러 범위를 한 번에 읽거나 독립된 읽기를 같은 턴에 묶습니다. 앞 결과를 봐야 정할 수 있는 읽기는 순서대로 진행하고, 편집 전에는 정확한 줄을 앵커와 함께 확인합니다. 처음부터 파일 전체가 필요한 경우에만 원문 읽기를 선택하며, 이 지침이 실제 호출 수나 시간을 얼마나 줄이는지는 실행 기록으로 따로 확인합니다.

CUELO의 패치된 내장 코어에서 Main은 Auto를 유지하며 새 사용자 턴의 자동 선택에 `providers.autoThinkingMinEffort: medium`과 `providers.autoThinkingMaxEffort: xhigh`를 적용합니다. 분류 실패 시 이전 값으로 대체하는 경우에도 같은 하한을 사용합니다. 모델이 지원하는 단계와 명시된 세션 상한 안에서만 고르며, 추론 조절이 없는 모델에 값을 만들어 넣지는 않습니다. 실행 중에 사용자가 직접 보낸 Steer·Follow-up은 이번 턴 요청에 이어 붙여 다시 판정하고, 결과가 현재 강도보다 높을 때만 다음 모델 요청부터 올립니다. 같은 턴 안에서는 내리지 않으며, 다음 새 사용자 턴은 평소처럼 처음부터 다시 고릅니다. 판정을 기다리지 않으므로 메시지 전달은 늦어지지 않고, 입력마다 판정 요청이 한 번 늘어납니다. 강도가 바뀌면 일부 제공자에서 프롬프트 캐시가 한 번 다시 쓰일 수 있습니다. 에이전트가 넣은 메시지·숨김 메시지·도구 후속 실행·수동 선택과 고정 강도 세션의 강도는 바꾸지 않습니다. Maker는 auto이며 Main 지시 때의 재분류는 위 Maker 규칙을 따릅니다. 공식 standalone `omp` 실행 파일에는 이 로컬 코어 패치가 포함되지 않으므로 CLI 업데이트만으로 해당 동작이 적용되지는 않습니다.

웹 입력창의 Auto 선택·상한과 「현재 추론 강도」는 서로 다른 값입니다. 선택기는 자동 선택에 허용한 상한을 보여 주고, 별도 표시는 코어가 보고한 실효값을 보여 줍니다. 새 대화에서는 상한 적용을 마치기 전까지 첫 메시지와 내장 명령 실행을 기다리며, 연결 실패 뒤 다시 보내면 같은 세션에서 미완 적용을 재시도합니다.

사용자가 직접 Steer를 보내면 패치된 내장 코어는 도구 호출이 아직 나오지 않은 모델 요청을 교체하고, 같은 실행 안에서 새 지시로 다시 요청합니다. 제공자가 실시간 주입을 수락했더라도 응답 종료 신호를 기다리지 않습니다. 본문이 이미 표시됐다면 그 본문과 완료된 서명 추론은 보존하고, 작성 중인 추론은 세션 기록과 다음 요청에서 제외합니다. 아직 보인 본문이 없다면 기존 부분 응답을 버립니다. 도구 호출이 나온 요청, 내부 메시지와 Follow-up은 기존 전환 경계를 따릅니다. 세션 중단·목표 일시정지·추론 상한 변경은 하지 않습니다. 재계산에 따른 사용량이 발생할 수 있으며, 요청을 바로 전환해도 새 답변 생성 시간까지 보장하지는 않습니다. 공식 standalone `omp` 실행 파일에는 이 로컬 패치가 포함되지 않습니다.

실행 레지스트리가 확인한 실제 부모 Main의 작업 지시도 이 요청 전환 경로를 사용합니다. 모델 응답을 기다리는 Maker에게 보낸 지시가 대기열에만 남지 않고 같은 실행 안에서 반영됩니다. 출처는 에이전트 지시로 유지하며 일반 peer 메시지·wake relay·합성 알림은 전환을 유발하지 않습니다. 이미 스트리밍되거나 실행 중인 도구 호출은 기존 경계를 지킵니다. 제공자 응답이 늦어진 원인을 자동으로 진단하거나 모든 네트워크 정체를 해결한다는 의미는 아닙니다.

하위 작업에는 모델 응답 대기·스트리밍·도구 실행·사용자 입력 대기를 구분하는 로컬 활동 감시가 붙습니다. 의미 있는 모델 출력이 120초 동안 없거나 도구 진행이 300초 동안 없거나 실제 부모 지시가 대기열에 60초 동안 남으면 기존 IRC 경로로 부모 Main에게 점검 알림을 보냅니다. 이는 제공자 제한 시간이나 실패 판정이 아니라 관찰 기준입니다. 사용자 선택을 실제로 기다리는 동안은 정체 알림을 보내지 않고, 같은 정체의 알림은 5분보다 자주 반복하지 않습니다. 진행이 돌아오면 다음 정체는 별도로 관찰합니다.

Maker가 자신이 시작한 백그라운드 작업을 기다리며 턴을 마치면 `awaiting_own_job`으로 관측을 유지합니다. 실행 중인 소유 작업의 id·종류·짧은 제목·경과 시간을 스냅샷과 점검 알림에 싣고, 기존 도구 대기의 300초 기준과 5분 재알림 간격을 씁니다. 이 시간은 모델 생성이 아니라 도구 대기로 집계합니다. 작업 결과로 Maker가 깨어나면 조용했던 시간을 새로 세고, 최종 종료하면 감시와 작업 목록을 지웁니다. Main은 이 목록만으로 자식의 `proc://` 소유권을 넘어서 읽거나 취소하지 않고, 해당 Maker에게 조회·보고를 지시합니다.

모델이 멈추지 않고 긴 응답만 계속 내보내는 하위 작업도 같은 감시가 알립니다. 15분 안에 출력 8천 토큰 이상 응답이 3번 이상이고, 10분 넘게 경과한 시간의 80% 이상이 모델 시간이면 `generation_heavy` 알림을 한 번 보냅니다. 조건이 풀렸다가 다시 맞으면 새 알림이 갑니다. 발주 브리프에 `EXPECTED_MINUTES: <분>` 한 줄이 있으면 경과가 그 값을 넘는 순간 `over_expected` 알림을 한 번 보냅니다. 모든 알림과 `agent://<id>`·`proc://<id>` 조회에는 경과 시간, 모델·도구 시간, 모델 시간 비중, 응답 수와 출력 토큰(합계·최근 응답·가장 큰 응답)이 숫자로 실립니다. 예상 시간과 완료 조건(`DONE_WHEN`)은 권장 브리프 항목일 뿐이라 없어도 발주가 거부되지 않고 시간 제한도 아닙니다. 두 알림은 Main이 숫자를 읽고 응답을 짧게 쓰도록 조향하는 계기이며 자동 취소·재발주는 하지 않습니다. Maker 지침에는 작은 edit만 하고 파일 전체를 다시 붙여넣지 않으며 긴 스크립트는 파일로 두라는 항목이 더해졌습니다.

`agent://<id>`와 `proc://<id>` 조회에는 현재 단계, 마지막 모델·도구 진행 시각, 부모 지시 대기 시각, 감시 예약·최근 검사·다음 검사·전달 상태가 나타납니다. 과제 본문·도구 인자·출력은 감시 알림에 넣지 않으며, 제공자의 네트워크 바이트·ping 상태는 관측하지 못하므로 `unknown`으로 남깁니다. 에이전트 ID와 실제 세션 ID를 쓰고, 이 경로에서 얻을 수 없는 발주 식별자는 명시적으로 미확인으로 표시합니다.
정체 구간별로 알림 전달과 부모의 확인·조치 관측도 구분합니다. 성공한 `agent://`·`proc://` 조회에서 해당 자식·세션·정체 구간의 활동 스냅샷이 실제로 반환됐을 때 확인으로 기록하고, 부모의 후속 지시가 성공적으로 전달됐을 때는 별도 조치 관측으로 남깁니다. 실패한 도구 결과, 다른 대상, 이전 정체 구간의 늦은 결과는 현재 확인으로 세지 않습니다. 확인하거나 지시를 보냈다는 사실은 해결을 뜻하지 않으며, 실제 자식의 진행과 종료는 기존 활동 관측으로 판단합니다.

알림은 쉬고 있는 Main을 깨우거나 실행 중인 Main의 다음 처리 경계로 전달됩니다. 완료 보고를 대신한 것으로 집계하지 않으며, 종료·교체·폐기 뒤에는 해당 감시를 정리합니다. Main은 알림을 받으면 최신 결과·로그와 감시 상태를 확인하고 안전한 재지시·복구 여부를 판단합니다. 새 역할·외부 감시 서비스·LLM 주기 호출은 추가하지 않고 자동 kill·재시도·재발주는 하지 않습니다. 서버 자체가 멈추거나 Main의 모델 요청이 응답하지 않으면 즉시 확인을 보장할 수 없으며, 감시 예약 시각 역시 제공자 정상 동작의 증거가 아닙니다.

CUELO의 목표 모드에서 실행을 취소하면, 취소 정리가 끝나기 전에 실행 종료 알림이 와도 자동 이어 가기를 다시 시작하지 않습니다. 취소에 따른 중단은 사용자의 직접 입력이나 명시적인 목표 시작·변경·재개로만 해제됩니다. 이미 일시정지된 목표는 새 메시지만으로 재개되지 않으며 `/goal resume`이 필요합니다.

패치된 내장 코어의 Anthropic 계정 재선택은 오늘 쓸 몫 안에 있는 계정 가운데 주간 한도가 곧 리셋되는데 많이 남은 계정을 먼저 씁니다. 순서는 남은 주간 비율을 리셋까지 남은 시간으로 나눈 값(upstream의 required drain)이 큰 쪽이고, 같으면 저장 순서(RIN 먼저)입니다. 오늘 몫은 사용량 패널과 같은 기준으로, 주간 창에서 지난 날 수에 오늘 하루를 더한 몫입니다. 예를 들어 사흘째라면 3/7까지입니다. 몫을 넘은 계정은 몫 안의 계정 뒤로 가고, 두 계정이 모두 넘었으면 덜 넘은 쪽을 씁니다. 사용량·주간 리셋 정보가 완전한 건강한 후보만 재배열하며, 조회 실패·부분 정보는 추정하지 않고 기존 한도·예비량·5시간 보호를 유지합니다. 사용 중인 warm pin과 명시적으로 지정한 캐릭터 계정은 이 선호로 전환하지 않습니다. 캐릭터 `교체`와 summon은 모두 그 계정을 세션 exact pin으로 고정하므로, 그 계정이 막히거나 한도에 닿으면 다른 계정으로 조용히 넘어가지 않고 실패로 알립니다.

캐릭터 summon 표시 없이 띄운 일반 Maker는 부모 세션의 Anthropic 계정 고정(warm pin과 exact pin)을 물려받지 않고 위 순서로 새로 고릅니다. summon으로 부른 Maker는 지정한 자리를 다시 exact pin으로 고정합니다. Maker가 아닌 자식과 다른 provider의 계정은 전처럼 부모에게서 물려받습니다.

Anthropic 구독 계정이 모두 주간 한도로 막히면, 패치된 내장 코어는 예비 API 키로 요청을 넘길 수 있습니다. 키는 `~/.omp/agent/anthropic-fallback-api-key`(한 줄, 권한 600)에 둡니다. 코어는 이 파일을 폴백 판단이 참인 순간에만 읽고, 환경 변수에 올리거나 기억해 두지 않습니다. 그래서 에이전트가 실행하는 셸과 스크립트는 이 키를 물려받지 않습니다. 폴백 조건은 셋이 모두 맞을 때입니다. 그 세션이 쓸 수 있는 Anthropic 계정이 모두 막혀 있어야 하고, 각 계정의 사용량 보고에 아직 리셋되지 않은 주간(7d) 한도 소진이 있어야 하며, 키 파일이 있어야 합니다. 5시간 창만 찬 경우는 전처럼 막힌 계정으로 요청해 리셋을 기다립니다. 인증 실패, 일시적 갱신 실패, 플랜 조건 불일치도 전과 같습니다. 캐릭터 `교체`·summon으로 계정을 지정한 세션은 폴백하지 않고 실패로 알립니다. 폴백 중인 요청은 OAuth 계정 사용량으로 귀속하지 않습니다. 주간 한도가 리셋되면 다음 요청부터 구독 계정으로 돌아갑니다. 한도 정보가 늦게 반영되면 첫 요청이 구독 계정으로 나가 사용 한도 오류를 받은 뒤, 같은 요청의 재시도에서 키로 넘어갑니다. 파일이 없거나 비어 있으면 기존 동작과 같습니다. 이 동작도 standalone `omp` 실행 파일에는 포함되지 않습니다. 자동 충전을 막으려면 키를 발급한 Console 조직에 결제 수단을 등록하지 않습니다. 그러면 크레딧이 떨어졌을 때 요청이 멈출 뿐 청구되지 않습니다.

보관 리셋권의 만료 전 자동 사용은 기본으로 꺼져 있습니다. 해당 서버의 agent 디렉터리(`~/.omp/agent`, 별도로 지정했다면 그 경로)에 `cuelo-reset-expiry.json`을 두고 `{"enabled":true}`로 설정하면 켜집니다. 구매나 추가 사용량 결제를 켜는 설정이 아니라, 이미 보유한 Codex·Anthropic 리셋권을 사용하는 정책입니다. 서버가 실행 중일 때 계정별 실제 만료 시각의 1시간 전부터 확인하며, 사용량이나 현재 대화의 선택 계정과 관계없이 사용 가능한 계정을 대상으로 합니다. 정기 한도 리셋 시각은 이 만료 시각을 대신하지 않습니다.

사용 직전에 같은 계정·리셋권의 상태를 다시 확인합니다. 수동 OFF·인증 오류·불명확한 만료 시각·제공자의 사용 불가 판정은 우회하지 않습니다. 사용 요청의 결과가 불확실하면 서버를 재시작해도 같은 권리를 자동으로 다시 쓰지 않습니다. 서버 중단·네트워크나 제공자 장애 중에는 만료 전 사용을 보장할 수 없으며, 성공을 확인하지 못한 시도를 사용 완료로 표시하지 않습니다. 이 파일은 로컬 운영 설정이므로 다른 PC로 자동 복사하지 않습니다.

패치된 내장 코어는 thinking 요약을 생략하는 설정(`omitThinking`)에서도 Claude Opus 5.5 같은 최신 모델이 도구 호출 사이에 쓴 사용자용 진행 문장(progress update)을 본문으로 보여 줍니다. Anthropic은 이 문장을 별도 thinking 블록으로 보내므로, 생략 설정(`display: "omitted"`)을 그대로 쓰면 화면과 세션 기록에서 사라집니다. 코어는 공식 Anthropic API로 가는 이 요청을 `display: "updates"`(beta 헤더 `thinking-display-updates-2026-08-18`)로 보냅니다. 그러면 reasoning은 비어서 오고, 텍스트가 온 진행 문장만 본문 text로 내보냅니다. thinking 서명은 공식 문서대로 불투명 값으로 다루고 해석하지 않으며, 다음 요청에는 서명된 원래 thinking 블록을 그대로 돌려보냅니다. 공식 API가 아닌 주소는 upstream 동작을 따릅니다. 이 동작도 standalone `omp` 실행 파일에는 포함되지 않습니다.

edit 도구가 이전 read·검색에서 온전히 보이지 않은 줄을 기준으로 한 편집을 거부할 때, 패치된 내장 코어는 그 안내를 한국어로 바꿔 모델에 전달합니다. 안내 원문은 native 모듈이 영어로 만들며, 영어 안내 바로 뒤에 Main이 진행 문장을 영어로 이어 쓰는 일이 있었습니다. 알려진 문장 틀만 바꾸고 파일·줄·태그와 파일 내용 줄은 그대로 두며, 틀이 다른 오류는 원문을 유지합니다.

upstream 18.3.3부터 코어는 `task`·`bash`를 가진 SubAgent에 `wait`를 자동으로 붙입니다. CUELO에서 `wait`는 Main 전용이므로 패치된 내장 코어는 이 자동 부여만 막고, agent 정의가 `wait`를 직접 적은 경우에는 그대로 줍니다. SubAgent는 자기 background job 결과를 기다리지 않고 자동 재개로 받습니다.

에이전트의 `ask` 질문은 추천안(`recommended`)과 자동 선택 허용(`autoSelectRecommended: true`)을 모두 단 질문만 설정한 대기 시간(이 프로필은 `ask.timeout: 120`, 2분) 뒤 추천안으로 진행합니다. 그 밖의 질문과 plan mode 질문은 답할 때까지 기다립니다. 웹 질문 창은 이 안내를 보여 주고, 옵션을 고르거나 답을 입력하면 대기 시간을 다시 시작합니다. 타임아웃으로 고른 답은 결과에 "사용자 응답·승인이 아님"으로 표시되고, 규칙상 배포·삭제·비용·계정·권한·provider 안전 확인 질문에는 자동 선택을 켜지 않습니다.

SubAgent의 service tier는 `tier.subagent: inherit`으로 Main을 따르되, 패치된 내장 코어는 Main의 OpenAI Fast(`priority`)만 새 SubAgent에 넘깁니다. Main의 Anthropic·Google Fast와 Ultrafast·flex는 SubAgent로 자동 상속하지 않습니다. `tier.subagent`에 값을 직접 적거나 agent별 override를 두면 그 값이 그대로 적용됩니다. Fast를 지원하지 않는 모델에는 요청에 싣지 않습니다.

Maker는 자신이 바꾼 범위의 focused check와 실제 변경 표면 검증을 수행하고 원문 증거 locator를 보고합니다. Main은 확정된 변경분을 중간 검수하고, 마지막에는 각 수용 조건과 그 증거를 대조해 직접 판정합니다. Main은 Maker의 focused check를 같은 조건에서 반복하지 않으며, 필요할 때 공통 환경의 통합·전체 수용 검사를 수행합니다. 검사되지 않은 revision을 통과로 처리하지 않습니다. 자세한 책임 경계는 [검수와 수용](../Tools/OMP_Global_Config/agent/rules/subagent.md) 절과 policy의 `mainLane.workerReview`, `routing.reviewPacket`에 규정돼 있습니다.

### 검증 결과 읽기

검사 결과를 보고할 때는 확인한 범위와 남은 경계를 함께 적습니다.

| 확인한 범위 | 근거 | 이 결과만으로 알 수 없는 것 |
| --- | --- | --- |
| 연결 검사 | 고정 응답 대역으로 호출 ID·도구 결과·다음 요청을 대조 | 실제 모델의 도구 선택 능력 |
| 실환경 확인 | 대상 프로그램에서 요청한 상태 변화를 관찰 | 다른 기기·권한·상황에서도 같은 결과인지 |
| 모델 평가 | 실제 모델이 수행한 과제와 평가 기준 | 모의 환경 밖의 동작이나 실제 청구액 |

기존 테스트에 경계를 적을 때는 다음처럼 짧게 남깁니다.

```text
검증하는 계약: 실행 파일이 없을 때만 대체 셸을 쓰고, 실행 후 실패는 재전송하지 않는다.
mock 처리한 경계: 외부 프로세스 실행과 반환값.
아직 증명하지 못한 결과: 실제 버튼의 효과, 전면 창 유지, 모델의 대상 선택.
```

`windows_control`의 요청 전달과 컨트롤 변화는 사용자 목표 달성 여부와 구분합니다.
텍스트·체크 상태가 변했어도 저장·전송 같은 작업의 성공 여부는 대상 프로그램에서 확인해야 합니다.
결과가 불확실하다는 이유로 같은 입력을 다시 보내지 않습니다.

사용량은 모의 집계, 공급자가 반환한 usage, 실제 청구 내역을 구분합니다.
고정 응답 대역에서 집계 경로를 확인해도 실제 토큰 수나 요금이 맞는지는 입증하지 못합니다.

작업 중 만든 일회성 산출물은 둘로 나눠 정리합니다. 실행 중인 검증 서버·브라우저 탭·프로세스, 저장소 밖 임시 파일, 보거나 판정하려고 만든 파일(스크린샷·화면 캡처, 문서를 이미지로 렌더한 것, 확인용 변환본·내려받은 파일, 읽으려고 파일로 남긴 로그), 화면 확인용 fixture 세션, 더 쓰지 않는 검증용 빌드 폴더는 만든 쪽이 확인이 끝나면 바로 지웁니다. 그중 작업 기록이나 보고가 직접 링크해 근거로 쓰는 것만 작업 기록 폴더로 옮겨 남깁니다. 결과를 다시 재현하는 데 필요한 파일(검증 스크립트·결함을 재현하는 fixture·측정 원자료·임시 복사본)은 Maker가 지우지 않고 완료 보고에 남김/삭제 제안으로 올리며, Main이 수용할 때 작업 기록에 연결할 근거와 쓸모없는 임시물로 나눠 임시물을 정리합니다. 정리 대상은 그 작업이 직접 만든 것뿐입니다. 소유권을 확인하지 못한 것, 기존 캐시·stage·rollback, 사용자 파일, 다른 세션의 산출물은 남기고 삭제 승인 규칙을 따르며, 정리하지 못한 것은 위치와 이유를 보고합니다.

위험하거나 표본으로 뽑힌 코드 변경은 커밋 전에 **다른 모델 계열의 검토**를 거칩니다. Anthropic 계열 모델이 쓴 코드(Main 포함)는 OpenAI 모델이, OpenAI 등 그 밖 제공자의 모델이 쓴 코드는 Anthropic 모델이 검토합니다. 작성자가 섞이면 양쪽이 모두 봅니다. 필수 검토는 `crossReviewOpenAI`(Astra)·`crossReviewAnthropic`(Opus) 슬롯으로 정합니다. 보조 자문은 `crossReviewAdvisory`(Argon) 슬롯을 쓰며 저자가 그 모델 자체일 때만 빠집니다. 다른 Anthropic 모델이 썼다는 이유로 자문을 빼지는 않습니다. 자문 실패는 기록만 남기지만 받은 지적(`R*-ADV-*`)은 다른 지적처럼 근거로 닫아야 합니다. 자문은 필수 검토의 실패를 대신 통과시키지 못합니다. 이전 Google 자문 기록과 `R*-GGL-*` 지적은 그대로 읽고 닫을 수 있습니다. `draft`·`ocr` 역할은 바꾸지 않습니다.

대상은 high-risk로 선언한 변경, 변경된 코드 줄·경로에 위험 trigger 표식이 있는 변경, 커밋 단위 결정적 10% 표본입니다. 일반 변경은 `maker_route`의 교차검토 권고·이유·다음 행동을 보고 Main이 선택합니다. 문서·테스트·생성물과 작업 기록(`doc/history/`)의 측정·판정 데이터는 제외하지만 작업 기록 안의 스크립트는 대상입니다. TS/JS 수정은 바뀐 줄이 단독 `//` 주석이나 한 줄 `/*…*/`이고 변경 전후의 Bun 변환 결과도 같을 때만 주석 변경으로 제외합니다. 변경 전후 어느 쪽에든 백틱·역슬래시 줄 연결·단독 CR·U+2028·U+2029가 있으면 이 제외를 적용하지 않습니다. 지시문·여러 줄 주석의 중간 줄·타입 변경이나 판별이 불명확한 변경은 코드로 남습니다. Git이 바이너리로 판정한 이미지·미디어·문서·글꼴 자산도 코드 게이트에서 제외하며 실행 파일·라이브러리는 제외하지 않습니다. `cross_review`는 frozen diff·수용 조건과 명시한 참고 자료를 보내며 프로필·persona 문구는 보내지 않습니다. 관련 호출자·계약·명세는 검토 대상 전체로 늘리지 않고 `inputs`나 `references`로 명시합니다. Main이 각 finding을 코드와 근거로 확인해 `fixed`·`refuted`·`limit` 중 하나로 닫습니다. 검토 결과는 Main이 확인할 증거이며 자동 합격 판정은 아닙니다.

`cross_review`는 파일 이름이 민감해 보인다는 이유만으로 검토에서 빼지 않습니다. `.env*`, 키·인증서 형식(`.pem`, `.key`, `.p12` 등), `id_*`, `agent.db`, `.npmrc`·`.netrc`·`.pypirc`·`.git-credentials`, `~/.omp/agent` 아래 파일처럼 형식이나 위치 자체가 비밀을 담는 파일은 검토자에게 보내지 않습니다. 이런 파일은 검토 결과와 `git_finalize` 거절 메시지가 같은 말로 안내합니다. 정책상 검토할 수 없어 라운드를 더 돌려도 통과가 나오지 않으니, 이름이나 위치를 바꾸거나 커밋에서 빼거나, 사용자가 명시적으로 지시했을 때만 `crossReviewWaiver`를 쓰라는 내용입니다. `credential`·`secret`·`password`·`api-key`가 들어간 이름이나 단독 `auth`·`token` 이름처럼 이름만 걸린 파일은 비밀로 보이는 값을 `[REDACTED]`로 가린 채 검토하고, 가린 횟수는 결과의 `redacted`에 나옵니다. 개인키 블록이 든 파일은 그대로 거절하며, `files`·`references`·`inputs`에 같은 규칙을 적용합니다. 이미 시작된 검토에서 바뀐 줄이 테스트 파일 삭제(같은 이름의 원본도 지운 경우는 제외), `test`·`expect` 호출 순감소, skip·todo 추가, 린트·타입 억제 주석 추가, 빈 catch 추가에 해당하면 판정이 아닌 단서로 검토자 프롬프트와 결과의 `hidingLeads`에 덧붙입니다. 이 단서는 검토 필요 여부, 10% 표본, 게이트 판정을 바꾸지 않습니다.

한 체인은 최대 5회입니다. probe 라운드는 하나, 일반 라운드는 넷입니다. 후속 라운드는 직전 검토 이후의 변경분을 봅니다. 마지막 검토 뒤 코드가 바뀌면 `resolve`의 `unreviewedChanges`로 알리고 통과를 막으므로 수정분도 다시 검토받아야 합니다. 문서·테스트·생성물만 바뀐 경우는 안내입니다. 이미 커밋한 변경은 첫 라운드의 `base`에 HEAD 또는 조상 커밋을 지정해 그때부터 HEAD까지 검토합니다. 이때 대상 작업 트리는 HEAD와 같아야 합니다. 후속 라운드는 `base` 없이 `previousReviewId`로 잇습니다. `git_finalize`가 검토 기록을 확인하고 사용자가 명시적으로 지시한 경우에만 면제할 수 있습니다. 정책 정본은 `mainLane.workerReview.crossFamilyReview`입니다.

자문 검토는 필수 검토와 함께 시작하며 최대 120초까지 기다립니다. 필수 검토가 모두 끝나면 아직 대기 중인 자문 호출은 abort하고 중단 사유를 남깁니다. 제공자가 취소를 확인해 줄 때까지 추가로 기다리거나 중단을 성공 응답으로 기록하지 않습니다. 필수 검토의 600초 제한은 유지하며 중단 전에 받은 자문 지적은 모두 처리해야 합니다. 자문 중단·시간 초과는 필수 검토의 실패를 대신 통과시키지 못합니다. 공개 산출물의 `slop_check`도 같은 대기 방식을 사용합니다. 실행 중에는 검토자별 시작·완료·오류와 대기 상태를 도구 진행 정보로 전달합니다.

미검토 변경 안내는 체인에서 각 파일을 마지막으로 검토한 상태와 현재 상태를 비교합니다. 앞선 라운드에서 검토한 삭제는 이후에도 파일이 없는 상태라면 다시 경고하지 않습니다. 검토한 파일을 그 뒤 새로 삭제하거나 내용을 바꾸거나, 검토한 삭제 뒤 파일을 다시 만들면 안내 대상입니다. 처음부터 없거나 필터로 제외된 경로를 검토 완료로 간주하지 않습니다.

이 가운데 **코드 파일**이 있으면 지적이 모두 닫혀도 resolve는 통과를 기록하지 않습니다(결과의 `unreviewedBlocking`). 실측(2026-10-11~24)에서 통과한 resolve 155건 중 30건이 reviewer가 보지 못한 코드 내용을 통과로 기록했기 때문입니다. 수정을 같은 체인의 다음 라운드(`previousReviewId`)로 reviewer에게 보인 뒤 다시 resolve하면 통과합니다. 실험이 아닌 라운드 넷을 모두 써서 더 돌릴 수 없는 체인이나, 바이너리·개인키·비밀 경로라서 reviewer에게 보일 수 없는 파일만 `unreviewedAcknowledgements`에 파일마다 그 내용에 한 검사를 근거로 적어 통과할 수 있습니다. 라운드가 남았거나 근거가 비면 거절되고, 받아들인 확인은 경로·내용·근거와 함께 기록됩니다. 문서·테스트·생성물만 바뀐 경우는 종전처럼 안내만 하고 통과합니다.

`cross_review`의 선택 입력 `references`에는 심사 대상 변경과 별도로 참고할 파일을 최대 10개 지정할 수 있습니다. 기존 계약이나 새 작업 기록의 내용을 줄 번호와 함께 전달하되, 참고 자료는 통과 지문·코드 검토 범위에 들어가지 않으며 참고 자료만으로 심사하지 않습니다. 저장소·비밀·gitignore·바이너리 필터와 파일당 64 KiB·합계 100 KiB 제한을 적용하고, 제외 이유는 `skippedReferences`에 표시합니다. 읽은 파일 핸들의 실제 경로를 확인할 수 있는 Linux/WSL에서 지원하며, 네이티브 Windows/macOS에서는 이 선택 자료를 제외하고 지원하지 않는 이유를 알립니다. `references`를 쓰지 않는 기존 코드 검토는 그대로입니다. 참고 내용은 비신뢰 데이터이고, Main이 수용 조건을 명시하고 최종 판단하는 책임은 바뀌지 않습니다.

`cross_review`의 선택 입력 `inputs`에는 변경이 서로 어긋나면 안 되는 명세·계약·스키마·호출자 파일을 최대 10개 지정할 수 있습니다. 읽는 방식과 제한(저장소·비밀·gitignore·바이너리 필터, 파일당 64 KiB·합계 100 KiB, Linux/WSL에서만 읽기)은 `references`와 같고, reviewer에게는 "이 파일들과 일관되는지 본다"는 안내와 함께 별도 블록으로 전달합니다. 입력 파일 자체는 심사 대상이 아니며, 제외된 입력은 `skippedInputs`와 다음 단계 경고로 표시합니다. `references`와 달리 입력은 통과에 묶입니다. 통과(resolve) 뒤에 입력이 바뀌거나 지워지면 `git_finalize`는 그 통과가 변경 파일을 더 이상 덮지 않는 것으로 보고, 바뀐 입력의 이름을 알리며 검토를 다시 하라고 요청합니다. 같은 내용을 덮는 통과가 여러 개면 묶인 입력이 모두 그대로인 통과가 하나라도 있을 때 덮입니다. 후속 라운드는 앞 라운드의 입력을 이어받아 현재 내용으로 다시 읽고 입력을 더할 수 있으며, 이어받은 입력을 더 읽을 수 없으면 조용히 빼지 않고 거절하므로 빼려면 새 검토를 시작합니다. `files`와 `inputs`에 같은 경로가 있으면 거절합니다. `inputs`를 쓰지 않는 기존 검토와 게이트 판정은 그대로입니다.

reviewer는 변경 앞뒤 12줄 밖의 코드를 보지 못하고 테스트도 실행하지 못합니다. 그래서 변경이 diff 밖의 코드와 맞물리면(큰 파일 안의 기존 함수와 호출부, 다른 파일의 호출자, 지켜야 할 계약) Main은 첫 검토에 그 맥락을 `references`로 함께 넘깁니다. 64 KiB를 넘는 파일은 빠지므로 큰 파일 자체가 아니라 호출부가 든 다른 파일이나 작업 기록·계약 문서를 고릅니다. 이렇게 해도 diff 밖 동작의 근거는 검토가 아니라 실제 실행 검증입니다.

reviewer는 코드를 읽는 것만으로 가릴 수 없는 의심(이벤트 순서·타이밍·실제로 돌려 봐야 아는 동작)에 finding의 `probe`로 재현 절차와 "사실이라면 관찰될 결과"를 붙일 수 있고, 추측성 major·blocker 대신 이쪽을 쓰도록 안내받습니다. reviewer는 도구가 없어 직접 돌릴 수 없으므로 Main이 직접 또는 기존 Maker로 그 실험을 돌려 `command`·`exitCode`·`output` 발췌를 `probeResults`로 `previousReviewId`와 함께 되돌립니다. 이 probe 라운드는 코드가 그대로여도 받아들여지고, reviewer가 결과를 받은 finding마다 `confirmed`·`withdrawn`·`unresolved` 판단을 돌려줍니다(판단이 빠지면 `unresolved`). 출력 발췌는 결과당 8 KiB(넘으면 앞뒤만 남김)·합계 40 KiB까지이고, 비밀 값은 가려서 비신뢰 데이터로 전달하며 개인키 블록이 든 결과는 거절합니다. 체인에 없는 finding을 가리키거나 한 체인에서 두 번째 probe 라운드를 요청하는 호출도 거절합니다. 권장 흐름은 reviewer 의심 → 실험 → probe 라운드 → 확인된 것만 수정 → 변경분 라운드입니다. 이 판단도 자문일 뿐이라 `withdrawn` finding을 포함해 모든 finding은 여전히 Main이 근거와 함께 닫아야 통과합니다.

교차검토가 필요한 변경을 맡은 Maker는 완료 보고 **전에** 자기 변경분으로 `cross_review` `review`를 실행합니다. 브리프의 고위험 지정, 실제 변경의 위험 표식, Main이 전달한 최종 커밋 표본 요구는 필수이며 일반 변경은 발주·검수 과정에서 Main이 검토를 선택한 경우에 실행합니다. 모든 Maker 코드 변경을 전수 검토하지는 않습니다. `authors`에는 자기 모델 selector를 줍니다. subagent 세션에서 `"main"`은 Main이 아니라 자식 모델로 풀리므로 도구가 거절합니다. 첫 라운드의 `authors`에 세션 자신의 모델과 같은 계열이 하나도 없으면 역시 거절합니다. Maker는 finding마다 고치거나 근거로 반박합니다. 필요하면 probe 라운드를 쓰고 고친 뒤에는 같은 체인의 변경분 라운드를 돌립니다. 통과 지문을 남기는 `resolve`는 Main 전용이며 Maker는 reviewId 체인과 finding별 제안 status(`fixed`·`refuted`·`limit`)·근거를 보고합니다. Main은 같은 코드에 검토를 중복 실행하지 않고 Maker의 체인을 확인해 `resolve`합니다. 마지막 라운드 뒤 내용이 바뀌었으면 그 Maker에게 새 라운드를 맡기며 Maker를 다시 깨울 수 없을 때만 Main이 돌립니다. 통과 지문은 `resolve` 시점 파일 blob이므로 검토 뒤 수정한 코드는 다시 검토받아야 합니다. 정책 정본은 `mainLane.workerReview.crossFamilyReview.makerReview`입니다.

같은 문제가 이미 한 번 실패했고, 원인이나 설계가 둘 이상 남았는데 관찰만으로는 가릴 수 없고, 올바른 동작을 실행 가능한 테스트로 쓸 수 있을 때(비동기·취소·상태 전이·파서 등)는 Main이 경쟁 후보 실행을 쓸 수 있습니다. 세 조건이 모두 맞아야 하고 Main이 각 조건의 관측 증거를 발주 브리프에 적어 판단하며, 난이도 점수만으로는 발동하지 않고 자동 감지기나 영구 gate도 없습니다. 같은 브리프로 후보 Maker 2명을 한 task 배치에 `isolated: "capture"`로 냅니다. `"capture"`는 격리 worktree에서 실행해 변경을 patch(branch 모드면 branch)로 보존하되 부모 checkout에는 적용하지 않는 값이라, 부모 결과에 patch 경로가 나오고 전역 `task.isolation.apply` 기본값은 그대로입니다(내장 코어 패치 제공). 후보끼리는 서로 보지 못하고, 가능하면 서로 다른 모델 계열 둘을 쓰며, 각자 패치와 직접 쓴 경계 테스트를 보고합니다. Main은 저장소 밖 scratch worktree에 두 패치를 각각 적용해 모든 후보의 테스트와 기존 focused check를 교차로 돌립니다. 결과가 갈리면 그 테스트가 사용자 요구에 맞는지 먼저 판단해 한 구현의 선택을 못 박은 테스트는 버리고, 요구에서 도출한 판별 테스트를 더하며, 요구 자체가 모호하면 사용자에게 묻습니다. 요구에 맞는 테스트를 모두 통과하는 패치 하나를 고르고 동률이면 diff가 작은 쪽입니다. 테스트 개수의 다수결로 고르지 않습니다. 고른 패치는 `git apply`로 적용한 뒤 평소의 수용 검사와 계열 교차검토를 거치고, 행렬·버린 테스트와 이유·선택은 작업 기록에 남기며, 둘 다 실패하면 셋째 후보 없이 진단으로 돌아갑니다. 사용할 때마다 발동 증거·소요 시간·결과·이후 회귀를 기록해 이 방식이 값을 하는지 판단합니다. 후보 둘은 primary Maker 둘로 세며 정책 정본은 `routing.competingCandidates`입니다.

upstream 18.4.12는 SubAgent가 빌드·테스트·스모크를 아예 돌리지 않고 검증을 Main에 넘기도록 바꿨습니다. 패치된 내장 코어는 이 계약을 위 분담으로 되돌립니다. Maker는 자기 변경의 집중 검사(테스트 파일 하나·타깃 재현·스모크)를 실행해 명령과 종료 코드를 보고하고, 실행할 수 없거나 무거운 통합 검사는 Main이 돌릴 정확한 명령으로 넘깁니다. 같은 작업 공간을 쓰는 Maker는 배정에 명시되지 않은 프로젝트 전체 빌드·포매터·린터·전체 테스트를 돌리지 않습니다. 형제 Maker의 미완 편집과 CPU 경합 때문입니다. 별도 worktree로 띄운 `isolated` Maker에는 이 금지가 없습니다. Main 세션의 프롬프트는 upstream 그대로입니다. upstream 18.4.11부터 실행 중인 SubAgent에 주기적으로 완료율을 묻는 기능(`task.completionProbeMs`, 기본 2분)은 묻는 횟수만큼 모델 요청이 늘어납니다. 공개 설치는 이 기본값을 바꾸지 않으므로, 끄려면 자기 `config.yml`의 `task.completionProbeMs`를 `0`으로 둡니다.

Maker 정의에 `lsp`가 있어도 코어의 `task.enableLsp`가 꺼져 있으면 자식 세션에 도구가 생성되지 않습니다. 새 프로필의 CUELO 기본값은 `task.enableLsp: true`이며, 기존 프로필은 설치기가 바꾸지 않으므로 필요한 경우 해당 설정을 켠 뒤 서버를 재시작합니다. 전역 `lsp.enabled`와 부모 세션의 LSP 허용 조건도 그대로 적용됩니다.

교훈은 Mnemopi 기억으로 남습니다. `learn`은 Main 세션에만 있으며 저장한 기억 id를 결과에 돌려줍니다. Maker는 교훈을 직접 저장하지 않고 종료 보고에 교훈 후보(적용 조건·원인·바뀐 행동·성공 근거)를 싣습니다. 저장·기존 교훈 연결·기각은 Main이 정합니다. 패치된 내장 코어에서 Maker 세션은 첫 턴에 자기 작업 brief로 기억을 한 번 회상하고, 주입되는 `<memories>` 줄마다 `(id: …)`가 붙습니다. 이전에는 부모 Main의 첫 턴 회상만 물려받았습니다. Main은 위임 attempt가 실제로 적용한 교훈을 `routing_verdict`의 선택 필드 `appliedLessons`에 기억 id로 남기고, 적용 근거는 `evidenceLocators`로 남깁니다. 이 필드는 기록일 뿐 수용 조건을 바꾸지 않으며, 교훈의 효과를 자동으로 판정하지도 않습니다. Main이 혼자 끝낸 작업은 원장에 attempt가 없으므로, 패치된 코어가 Main·Maker 모든 세션에서 첫 턴에 실제로 전달한 기억 id를 LLM 문맥에 들어가지 않는 세션 기록(`mnemopi-recall`)으로 남깁니다. 이 기록과 세션 중 `recall` 결과의 id로 교훈이 전달된 세션과 그 뒤 같은 실패가 다시 났는지를 셀 수 있습니다.
저장 범위도 Main이 판단합니다. 여러 프로젝트에 적용되는 사용자 선호와 작업 운영 원칙은 전역 기억(`global`)으로, 특정 저장소의 구현·경로·환경에 종속된 사실은 프로젝트 기억(`project`)으로 남깁니다. 기존 교훈이 있으면 중복 저장보다 연결·수정을 우선합니다.

`learn(topic)`으로 같은 주제의 교훈을 정정하면 기억 메타데이터의 `session_id`·`cwd`는 최초 출처로 유지하고, `updated_session_id`·`updated_cwd`·`updated_at`에는 최신 정정 출처와 시점을 남깁니다. `context`는 최신 정정의 설명이며 생략하면 `null`입니다. 최초 정정 때 확인할 수 있는 기존 시점·설명은 `first_timestamp`·`first_context`로 보존합니다. 이미 정정된 구형 기록이나 revision이 없는 기록의 최초 시점·설명은 추정해서 채우지 않습니다. `memory://<id>` 조회로 메타데이터를 확인할 수 있고, 이전 교훈 본문은 별도 이력으로 저장하지 않습니다. topic 없는 저장은 기존 주제의 정정으로 취급하지 않으며, 이 기능이 관찰 간 모순을 자동으로 판정하는 것은 아닙니다.

자동 주입과 `recall` 목록에는 확인 가능한 기억 범위(`global`·`project`)를 표시합니다. 같은 주제가 정정된 기억은 정정 횟수가 아닌 revision과 확인 가능한 최초·최신 정정 시점을 구분해 보여 줍니다. 구형 기록에 없는 시점은 추정하지 않습니다. 정정 이유를 일부만 잘라 주입하지 않으며, 필요한 경우 `memory://<id>`로 전체 메타데이터를 확인합니다. 이 표시는 검색 순위·저장 범위·기억 id를 바꾸지 않습니다.

프로젝트 사실·설계 결정·실패 원인을 남기는 `learn`은 `kind: evidence`와 실제로 존재하는 기록 파일(`citations`)을 함께 달아야 저장되고, 회상될 때 그 파일이 "근거 후보"로 붙습니다. 후보는 확인할 위치이지 기억이 맞다는 증거가 아니며, 파일이 교훈을 뒷받침하는지는 저장 때 검사하지 않습니다. 선호·절차·가설은 근거 없이 저장하고, 이미 저장된 기억은 바꾸지 않습니다.

회상할 때마다 근거 파일과 앵커가 지금도 프로젝트에 있는지 다시 봅니다. 파일이 지워졌거나 이름이 바뀌었거나 가리키던 절 제목·줄 범위가 사라졌으면 "근거 후보" 대신 "근거 사라짐"으로 표시합니다. 그 기억이 오래됐을 수 있다는 신호일 뿐 기억을 숨기거나 지우지 않고, 저장소에도 아무것도 쓰지 않습니다. 확인할 수 없는 경우(저장 위치를 모름, 파일이 너무 큼, 권한 오류 등)는 "근거 후보"로 둡니다.

`learn`으로 저장한 직후 같은 저장소에서 아주 비슷한 기존 기억이 있으면 최대 세 개를 "비슷한 기존 기억"으로 알려 줍니다. 같은 교훈이면 새로 쌓지 말고 그 기억을 고치라는 안내이며, 저장 자체는 막거나 바꾸지 않습니다. 임베딩이 꺼져 있으면 알리지 않습니다.

근거의 파일 경로와 앵커(제목·줄 범위 등)에 비밀정보 제거 대상 문자열이 있으면 일반 저장과 주제별 정정 모두 쓰기 전에 거절합니다. 경로나 제목을 조용히 바꾸면 실제 근거 위치와 달라지므로 변형해서 저장하지 않습니다. 거절된 요청은 기존 기억의 본문·출처·revision·임베딩을 바꾸지 않으며, 과거에 저장된 기억을 소급 정리하지 않습니다.

주제별 기억의 본문과 근거는 함께 저장합니다. 갱신 중 DB 오류가 나면 본문·출처·revision·임베딩 변경을 함께 되돌리고, 새 기억 저장이 실패하면 불완전한 행을 남기지 않습니다.

기억 전달과 실제 판단 적용은 다른 단계입니다. 관련 교훈은 현재 요청·적용 조건·예외 및 저장소 정본과 대조해야 하며, 기억에 적힌 과거 승인만으로 새 실행을 허가하지 않습니다. 전달되지 않은 기억, 오래된 내용, 전달됐지만 적용하지 않은 결정을 구별합니다. 범위·정정 표시가 있다는 사실만으로 모델의 판단 준수나 재발 감소가 입증되는 것은 아닙니다.

재발 분석기의 기존 수치는 `isError` 도구 결과에서 지정 패턴이 나타난 횟수입니다. 0건을 사용자 정정이나 잘못된 설명이 없었다는 증거로 쓰지 않습니다. 결과의 `coverage`는 이 관측 범위와 Main 단독 적용의 미관측을 밝힙니다. 교훈 입력에 `correctionPattern`을 명시하면 사용자 메시지에서 맞는 항목의 위치·시각을 별도 `correctionCandidates`로 돌려주지만, 요구 변경과 오류 정정을 자동 판정하지 않으며 재발 수치에 더하지 않습니다. 이 입력이 없으면 후보는 0이 아니라 미검토(`null`)입니다.

JEV 기억 적용 점검은 코어가 회상 블록을 준비한 뒤, 해당 요청의 첫 모델 호출 전에 동작합니다. 기억별로 조건 일치·예외·현재 요청과 충돌·무관·불명을 구분하며 관련 신호가 있을 때만 에이전트에게 안내 한 통을 넣습니다. 보지 않은 저장소 정본과의 충돌은 추정하지 않고, 에이전트가 직접 대조합니다. 판정에는 비밀 패턴을 제외한 기억 최대 8개·각 500자와 요청 1,200자의 발췌만 사용하며 코드·경로·URL·인라인 literal을 제거합니다. 잘리거나 제거된 조건은 확정하지 않고 원문 확인으로 낮춥니다.

같은 판정 입력은 세션에서 한 번만 처리하고, 같은 기억 id라도 정정 내용·범위·요청이 바뀌면 다시 판단합니다. 매 도구 호출에 붙지 않으며 실패·자격 없음·최대 8초 대기 초과 시 안내 없이 진행합니다. 새 입력·세션 변경·종료 뒤 늦은 판정은 버립니다. 이 점검에는 설정한 JEV 제공자의 요청 비용과 지연이 생길 수 있고, 판단 준수나 재발 감소를 자동으로 보증하지 않습니다.

교훈 자동 기록(`autolearn`)을 켜면 도구를 많이 쓴 턴이 끝날 때마다 대화와 분리된 짧은 정리 단계가 교훈을 따로 저장합니다. 정리 단계는 교훈 맨 앞에 한 문장 요약을 붙입니다. 저장한 것이 있으면 대화에 "[교훈 자동 저장] N건" 메시지로 교훈마다 그 요약 한 줄을 최대 3건까지 보여 주고, 다음 턴의 모델도 그 메시지를 봅니다. 이 알림은 작업 과정을 접어도 대화 흐름에 남습니다. 저장한 것이 없으면 아무것도 띄우지 않습니다. 공개 설치의 기본값은 꺼짐입니다.

자동 기록이 실제로 실행되면 `~/.omp/logs/`의 기존 로그에 `Auto-learn capture usage` 항목을 남깁니다. 해당 정리 단계에서 새로 생성한 응답만 집계하며 `requests`(생성된 assistant 응답 수), `incompleteRequests`(오류·취소 응답 수), `input`·`output`·`cacheRead`·`cacheWrite`, `costUsd`(제공자가 보고한 비용 합계), `elapsedMs`, `provider`·`model`, `outcome`을 확인할 수 있습니다. 한 응답이라도 값을 보고하지 않으면 해당 합계는 `null`이며 0으로 간주하지 않습니다. 입력 대화의 과거 사용량은 포함하지 않고, 본문·도구 인자·교훈 내용·오류 원문은 계측 로그에 남기지 않습니다. 기능이 꺼져 실행하지 않은 경우 추가 모델 호출이나 사용량 항목은 없습니다. 이 기능은 계측만 추가하며 모델 선택·입력 범위·학습 예산을 자동으로 바꾸거나 비용 절감을 보장하지 않습니다.

에이전트가 직접 `learn`이나 `manage_skill`로 저장한 교훈·스킬은 자동 기록 설정과 별개로 해당 턴 끝의 "[교훈 저장]" 카드에서 확인합니다. 마지막 답변 뒤에 저장한 내용도 포함하며, 실패한 호출이나 스킬 삭제는 저장 알림에 넣지 않습니다.

Main 승인이 작업을 막고 있다면 관계없는 문서 정리나 새 발주보다 필요한 확인과 회신을 먼저 처리합니다. 승인과 완료 보고가 엇갈렸을 때는 이미 끝난 검사를 반복하지 않고 최신 승인과 남은 동작을 대조해 이어갑니다. 실패를 기록하는 데서 끝내지 않고 기존 규칙의 실행 위반과 실제 누락을 구분해 다음 작업에 반영하며, 효과를 관측하기 전에는 개선됐다고 단정하지 않습니다.

승인 회신을 기다리며 독립 작업도 모두 끝났다면 Maker는 산문만 쓰고 멈추지 않고 `yield`로 blocked/partial을 보고합니다. 산문 종료만 하면 코어가 `yield` 안내를 반복하기 때문입니다. 공유 작업은 Main의 첫 회신으로 이어지고, 격리 작업은 terminal 뒤 자동 재개되지 않아 증거를 인계하고 Main이 후속 소유권을 정합니다. 승인 대기를 완료·수용으로 표시하지 않습니다.

웹 화면 검증은 ego lite TaskSpace를 쓸 수 있는 PC에서는 로그인되지 않은 검증 프로필에서, 그 밖에는 headless 브라우저에서 합니다. 빌드가 깨진 중간 화면을 사용자 브라우저에 띄우지 않기 위해서입니다. 관리형 브라우저 helper나 프로젝트의 지원 검증 명령을 사용하며, bash·eval에서 Chrome/Edge 실행 파일을 직접 띄우지 않고, 지원 명령의 브라우저 프로필도 절대경로의 격리 위치를 사용합니다. headless 실행이어도 프로필 경로 오류는 사용자 데스크톱에 네이티브 오류 창을 띄울 수 있습니다.

앱과 Windows 프로그램 테스트도 사용자가 보는 데스크톱에 창을 띄우지 않고 백그라운드에서 돌립니다. 숨은 Windows 데스크톱, 화면 밖 위치나 표시 장치 없는 하네스, 장비 없는 로직 테스트 가운데 대상에 맞는 방법을 고릅니다. 이렇게 확인할 수 없는 항목(실제 GPU나 표시 장치가 필요한 렌더링 등)은 미확인으로 남깁니다. 사용자 화면에 띄우는 것은 사용자가 요청하거나 승인했을 때뿐이고, 띄운 프로세스는 자기 PID로만 종료합니다.

## 다중 파일 조사 `skim`

Main과 Maker는 [`skim.ts`](../Tools/OMP_Global_Config/agent/extensions/skim.ts)의 `skim(paths, question)`으로 cwd 안 파일·디렉터리·glob의 텍스트를 `modelRoles.skim`에 지정한 모델(기본 Hive의 DeepSeek v4.1 Flash 1017)에 묻고 근거 경로가 붙은 답을 받습니다. 첫 시도가 실패하면 같은 안전 필터를 거친 입력으로 `hive/deepseek-ai/deepseek-v4.1-flash-1017`에 한 번 대체하며, 실제 응답 모델과 앞 시도의 실패 이유를 표시합니다. 처음 지정한 모델이 이미 대체 모델이면 같은 모델을 다시 부르지 않습니다. 허용 파일 내용은 **지정한 모델의 제공자**(기본은 Hive), 대체 시에도 Hive로 전송되므로 역할 변경 시 전송 대상도 확인해야 합니다. 각 제공자의 유효한 인증과 텍스트 입력 지원이 필요하며 실제 모델 품질은 별도 확인 대상입니다. `.env*`와 인증·비밀 경로, **명시 경로도 포함한** gitignore 대상, 바이너리와 1 MiB 초과 파일은 제외합니다. 이름 검사에서 `auth`·`token`은 단어로 떨어질 때만 비밀 경로로 보므로(`auth.json`, `oauth-token.txt`) `authentic-…`·`tokenizer…` 같은 일반 파일은 보내고, 파일 내용의 키·토큰 형식은 따로 검사해 제외합니다. 파일 탐색은 cwd 안에서만 하고, cwd가 더 큰 저장소의 하위 폴더이면 찾은 경로를 `git check-ignore`로 다시 걸러 상위 `.gitignore`도 적용합니다. 그래서 원격 드라이브의 큰 저장소 안에서도 저장소 전체를 훑지 않으며, 한 경로의 탐색이 10초를 넘으면 그 경로만 건너뛰었다고 표시합니다. 전송량은 파일당 256 KiB, 요청당 1 MiB로 제한하며 빠지거나 잘린 파일을 결과에 표시합니다. 답은 최대 8,192토큰이고 3분 안에 받습니다. 답이 그 상한에 닿으면 버리지 않고 받은 데까지 돌려주며 끊겼다고 표시합니다. 두 시도 모두 실패한 결과에는 오류 상태가 붙지만, 성공한 대체·유용한 잘린 답·보낼 자료 없음·사용자 취소를 같은 모델 실패로 세지 않습니다. 정확한 편집 줄은 `read`로 확인합니다. 이미지 `vision`·`ocr`과 Jev 기반 `find`는 바꾸지 않습니다.

`modelRoles.tiny`와 `memory`는 Hive의 DeepSeek v4.1 Flash 1017입니다. 번역·문서 다듬기(`draft`)와 글자 전사(`ocr`)는 Google Cloud Vertex의 Gemini 4 Argon을 쓰고, 이미지 질문(`vision`)은 좌표 정확도 때문에 Opus 5.5 low를 씁니다. 글자 전사가 실패하면 `retry.fallbackChains.ocr`의 후보(Opus, GPT)에 차례로 묻습니다. 세션 제목 생성은 코어의 `tiny → commit → smol` 순서를 써서 실패 시 `commit`의 `anthropic/claude-sonnet-5-5`로 넘어가고, Mnemopi의 `memory` 역할은 전용 후보 체인에서 Sonnet을 시도합니다. `tts/speech-enhancer`는 단일 `@tiny` 호출에 실패하면 모델을 바꾸지 않고 기존의 기계적 음성 텍스트 정규화로 돌아갑니다. 같은 모델을 쓰는 다른 slot이 함께 바뀌지 않도록 모델 키에는 retry 체인을 걸지 않습니다.

세션 제목 프롬프트는 `agent/TITLE_SYSTEM.md`가 정본입니다. [`TITLE_SYSTEM.md`](../Tools/OMP_Global_Config/agent/TITLE_SYSTEM.md)는 요청이 쓰인 언어로 제목을 쓰고(한국어 요청은 한국어, 영어 요청은 영어) 식별자는 원문으로 두며, 인사처럼 이름 붙일 수 없는 입력은 거절하도록 지시합니다. 코어 기본 제목 프롬프트에는 이 언어 지시가 없고, CUELO는 세션을 만들 때 `TITLE_SYSTEM.md`를 코어에 전달하지 않아 CLI와 달리 사용자 파일이 적용되지 않았습니다. 그 둘이 겹쳐 한국어 요청에도 영어 제목이 나올 수 있었고, 그래서 기본 프롬프트가 항상 영어를 강제한다고 단정할 수는 없습니다. 이제 `lib/session-system-prompt.ts`가 세션 cwd 기준으로 코어의 `discoverTitleSystemPromptFile`·`resolvePromptInput`을 호출하고, 결과를 `createAgentSession`의 `titleSystemPrompt`로 넘깁니다. 자동 제목과 수동 이름 짓기(`lib/session-title.ts`)가 그 세션의 같은 값을 씁니다. 탐색 순서는 `SYSTEM.md`와 같습니다: 프로젝트(`.omp/`, `.claude/` 등)가 사용자 수준(`~/.omp/agent/`)보다 먼저이고, 파일이 없으면 코어 기본 동작을 유지합니다. `setup.ps1`/`export.ps1`/`verify.ps1`은 이 파일을 다른 필수 프로필 파일과 같게 설치·내보내기·검사하고, 공개 설치(`install.mjs`)는 `package.json`의 `files`에 있는 이 파일을 `~/.omp/agent`에 없을 때만 추가합니다. 기존 세션의 제목은 일괄 변경하지 않습니다.

## 문서 초안 작성 `draft`

Main과 Maker는 글씨가 들어가는 콘텐츠를 새로 쓰거나 한 문단 이상 다시 쓸 때 먼저 [`draft.ts`](../Tools/OMP_Global_Config/agent/extensions/draft.ts)의 `draft(instruction, output, paths?, overwrite?)`로 `modelRoles.draft`의 모델(기본 Vertex Gemini 4 Argon)에 쓰게 합니다. README·CHANGELOG·문서·보고서·소개 글, 인계 문서와 작업 기록의 서술, Markdown·CSV·Excel·Word·PDF 보고서와 표, PPT 슬라이드 문구, HTML·화면 문구가 모두 대상입니다. 사실·수치·경로·커밋은 지시나 참고 파일로 넘겨 모델이 지어내지 않게 하고, 만들어진 파일은 직접 열어 사실을 검토한 뒤 AI 슬롭 점검(한국어 `humanizer`, 영어 `stop-slop`, 화면 문구 `kill-ai-slop` 스킬)을 거쳐 반영합니다. 코드·설정·규칙 파일, 몇 줄 이하의 정확한 수정, 대화 답변은 대상이 아니어서 계속 `edit`/`write`를 씁니다.

형식은 `output` 확장자로 정합니다. `.md`·`.txt`는 받은 글을 그대로, `.csv`는 RFC 4180으로 파싱되는지 확인한 뒤 Excel이 한글을 깨뜨리지 않도록 UTF-8 BOM을 붙여 저장합니다. `.xlsx`는 모델에게 시트·행 JSON을 받아, `.docx`는 Markdown 부분집합(제목, 굵게·기울임·코드, 글머리·번호 목록, 표, 코드 블록, 인용)을 받아 도구가 직접 OOXML 파일을 만듭니다. 새 패키지는 쓰지 않으며 글꼴은 맑은 고딕입니다. `.pdf`는 같은 Markdown을 HTML로 바꾼 뒤, ego lite가 있는 PC에서는 그 호출만을 위한 ego lite TaskSpace에서 A4 PDF로 인쇄하고 끝나면 공간을 닫습니다. ego lite가 설치되지 않은 PC에서만 Windows Edge headless 인쇄(`--print-to-pdf`)를 씁니다. ego lite가 설치돼 있는데 인쇄에 실패하면 Edge로 바꾸지 않고 오류로 끝납니다. WSL이 아니거나 두 경로가 모두 없으면 모델을 부르기 전에 오류로 끝나며, 다른 형식으로 몰래 바꾸지 않습니다.

저장 경로는 cwd 기준 상대 경로만 받습니다. `..`, cwd 밖으로 해석되는 경로, 심볼릭 링크, `.git`·`node_modules`·비밀처럼 보이는 이름은 거부하고, 기존 파일은 `overwrite: true`일 때만 바꿉니다. 경로 확인은 모델 호출 전에 하므로 거부된 요청은 할당량을 쓰지 않습니다. `paths`의 참고 자료는 `skim`과 같은 안전 필터(비밀·gitignore·바이너리·크기 제한)를 거쳐 지정한 모델의 제공자(기본 Google) 또는 대체 시 Hive로 전송됩니다.

모델은 `modelRoles.draft`(기본 `google-vertex/gemini-4-argon`)이고, 첫 시도가 실패하거나 응답이 형식 검사(CSV·JSON 파싱)를 통과하지 못하면 같은 입력으로 `hive/deepseek-ai/deepseek-v4.1-flash-1017`에 한 번 대체합니다. 처음 지정한 모델이 이미 대체 모델이면 다시 부르지 않습니다. 결과 첫 줄은 실제 응답 모델이며 저장 경로·크기·개요를 함께 돌려줍니다. 두 시도 모두 실패하거나 변환·저장에 실패하면 오류 상태와 원인을 돌려주며 성공으로 표시하지 않습니다. 사용자 취소는 모델 실패와 구분합니다. 출력 상한은 따로 두지 않고 해당 모델의 최대치를 쓰며 10분 안에 받습니다. 최대치에서도 잘린 응답은 반쪽 문서라 저장하지 않습니다. Vertex 호출은 Google Cloud 프로젝트에 과금되며 ADC 인증과 `GOOGLE_CLOUD_PROJECT`·`GOOGLE_CLOUD_LOCATION`이 있는 PC에서만 해석됩니다.

## AI 슬롭 게이트 `slop_check`

문서의 슬롭 검사와 교차검수는 공개 배포·공유용 산출물에만 적용합니다. 비공개·내부 문서는 사용자에게 파일로 전달하더라도 제외합니다. 공개 대상은 커밋 전이나 작성한 턴이 끝나기 전에 `slop_check`로 점검합니다. `review`는 Main과 Maker가 모두 부를 수 있고 `resolve`는 Main 전용입니다. 공개 산출물을 쓴 Maker는 자기 모델을 `authors`에 넣어 점검하고 거짓 양성은 근거와 함께 Main에 보고합니다.

파일 확장자만으로 공개 여부를 단정하지 않습니다. `.publicignore`가 있는 프로젝트는 부정 규칙을 포함한 공개 미러 기준을 따릅니다. 제외된 문서는 비공개이며 나머지 대상 파일은 공개로 봅니다. `.publicignore`가 없으면 `.slop-gate.json`의 `visible` 경로만 자동 검사합니다. 공개 여부가 불명확한 경로는 자동으로 검토 모델에 보내거나 게이트로 막지 않습니다. 저장소 밖의 일회성 공개 산출물은 `slop_check`의 `public: true`로 지정할 수 있지만 비공개·내부 제외 규칙을 우회하지는 못합니다.

공개 여부가 확인된 Markdown·HTML·PPTX·DOCX·XLSX·PDF·HWPX·보고서 CSV와 언어 팩의 화면 문구가 대상입니다. 코드·주석·로그·테스트·생성물·vendor·내부 프롬프트·규칙·SOP·스킬과 `HANDOFF.md`·`doc/history/`·`doc/README.md`는 제외합니다. 비공개 문서는 내용 추출과 검토 모델 호출 전에 `not-public`으로 제외하며 통과로 기록하지 않습니다. 공개 대상의 검사 면제는 사용자의 명시 지시가 있는 `slopGateWaiver`만 허용합니다. 코드 변경의 `cross_review`는 그대로 유지합니다.

점검 기준은 공개 저장소에 각 라이선스(MIT, Apache-2.0)와 함께 들어 있는 세 스킬의 원문이며 바꾸지 않고 그대로 읽어 씁니다. 한국어 글은 `humanizer`, 영어 글은 `stop-slop`, HTML·화면 문구·슬라이드는 `kill-ai-slop`을 씁니다. `kill-ai-slop` 스캐너(`scripts/scan.mjs`)의 적중은 판정이 아닌 단서로 함께 보냅니다. 검토자 배정은 교차 검토(`cross_review`)와 같습니다. `authors` 인자로 글쓴이를 알리며 기본값은 Main입니다. 글을 쓴 모델의 반대 계열 검토자가 필수이고 `crossReviewAdvisory` 슬롯의 모델이 보조 자문으로 함께 봅니다. 자문 모델 자신이 쓴 글에서만 자문을 뺍니다. 검토자는 설정의 교차 검토 자리에서만 나오며 게이트 코드에는 모델 이름이 없습니다. 필수 검토자가 실패하거나 답을 해석할 수 없거나 파일을 건너뛰면 통과가 아닙니다. 자문 실패·120초 시간 초과는 기록만 하고 막지 않지만 받은 자문 지적도 다른 지적처럼 닫아야 합니다.

검토 응답이 JSON으로 해석되지 않으면 응답 원문과 실패 이유를 보존합니다. 다른 검토자가 정상적으로 돌려준 지적도 진단 정보로 남기지만 필수 검토가 실패한 파일은 `resolve`로 통과시킬 수 없습니다. 손상된 JSON을 임의로 닫거나 자동 재호출·모델 교체를 하지 않습니다. 토큰 수로 원인을 추측하거나 응답 형식 오류를 피하려고 문서의 따옴표·쉼표를 바꾸지 않습니다. 실제 내용상 지적을 반영한 교정은 별개입니다.

npm 배포본에는 `humanizer`·`stop-slop`·`kill-ai-slop`과 각 참조 파일·스캐너(`scripts/scan.mjs`)·라이선스를 포함하며, 개인 스킬은 동봉하지 않습니다. 기존 프로필은 패키지를 올린 뒤 하네스 설치·갱신 절차로 빠진 파일을 채웁니다. 이때 사용자가 수정한 파일을 보존하는 기존 규칙을 따릅니다.

도구는 파일을 한 번 읽어 해시하고, 같은 바이트의 사본에서 글을 추출합니다. git이 추적하는 파일은 HEAD 이후 더하거나 바꾼 글만 앞뒤 몇 줄과 함께 검토하며, Office·PDF는 추출한 글끼리 비교합니다. 추적하지 않는 파일, HEAD 버전이 없는 파일, 저장소 밖 결과물은 전체를 보고, 글을 지우거나 옮기기만 한 변경은 모델을 부르지 않습니다. 변경분만 검토해도 통과는 현재 파일 전체 바이트의 sha256에 묶이므로 한 바이트만 바뀌어도 사라집니다. 지적이 없으면 그 호출에서 바로 통과가 기록됩니다. 지적이 있으면 고친 뒤 새 내용을 다시 점검하거나, 내용이 그대로인 파일의 지적을 Main이 근거와 함께 반박(`refuted`)해 닫습니다. `fixed`·`limit` 선언으로는 닫히지 않습니다.

게이트는 공개 대상으로 확인한 산출물에만 적용합니다. 커밋할 때는 `git_finalize`의 `slop-gate` 단계가 교차 검토 뒤에 돌며 현재 내용의 통과 기록이 없으면 파일과 다음 단계(`slop_check`)를 알립니다. 바뀌지 않은 파일·삭제된 파일·push 재시도는 검사하지 않습니다. 저장소 밖의 공개 산출물도 현재 내용의 통과 기록이 없으면 턴 종료 시 점검 안내를 받습니다. 비공개·미지정 문서 때문에 턴을 다시 열지는 않습니다. 검토·실패 진단·해소·통과·면제는 프로필 폴더의 slop-gate 원장(권한 0600)에 기록합니다. 정책 정본은 `mainLane.workerReview.slopGate`입니다.

## Windows 빌드 `windows_build`

[`windows_build`](../Tools/OMP_Global_Config/agent/tools/windows-build/)는 WSL에서 `/mnt/<드라이브>/` 또는 `X:\` 위의 `.sln`·`.slnx`·`*proj`를 Windows MSBuild로 빌드합니다. `vswhere.exe`(`-latest -products * -requires Microsoft.Component.MSBuild`)로 MSBuild를 찾고, `wslpath`로 경로를 바꾼 뒤 `-nologo -m -nodeReuse:false -noconlog -flp`(UTF-8 로그)로 실행합니다. 결과는 종료 코드, MSBuild 경로·버전, 오류·경고 수, 앞쪽 오류 줄, 로그 경로(`%TEMP%\omp-windows-build\`), 그리고 빌드한 소스입니다. 소스는 빌드 직전에 프로젝트 폴더가 속한 저장소의 HEAD 커밋과 그 폴더 아래 미커밋 변경(추적 안 된 파일 포함, ignore 제외)으로 남기므로, "빌드 성공"이 어느 커밋·어떤 수정 상태의 결과인지 함께 보입니다. `/mnt/<드라이브>` 저장소는 Git 마감 도구와 같은 판정으로 Windows Git을 씁니다. 저장소가 아니면 빌드는 그대로 하고 revision 없음으로 표시합니다. 빌드 실패는 `ok:false` 결과로 돌려주고, 입력·환경 문제만 오류로 끝냅니다. 빌드만 합니다: 산출물을 실행·복사·배포하지 않으며, `Run`·`Deploy`·`Publish`·`Install` target과 `PreBuildEvent`·`PostBuildEvent`·`StartProgram` 같은 속성은 거부합니다. `msbuildProperties` 값 안의 `;`·`,`는 MSBuild 이스케이프(`%3B`·`%2C`)로 넘겨 값 하나로 남기므로, 허용된 속성의 값에 금지 속성을 끼워 넣을 수 없고 `DefineConstants: "DEBUG;TRACE"`도 그대로 전달됩니다. 프로젝트 파일에 이미 들어 있는 빌드 이벤트는 막지 않으므로, 빌드는 곧 그 프로젝트 코드의 실행이라는 전제는 그대로입니다. MSBuild가 없으면 Visual Studio 또는 Build Tools 설치를 안내하는 오류로 끝납니다. Main과 Maker가 함께 씁니다.

## Windows 컨트롤 조작 `windows_control`

[`windows_control`](../Tools/OMP_Global_Config/agent/tools/windows-control/)은 WinForms·VB6·MFC 같은 클래식 Win32 창의 버튼·체크박스·입력칸을 사용자 전면 창과 포커스를 건드리지 않고 조작합니다. Windows의 `computer` 요소 동작(`press`·`setValue`)은 이런 창을 앞으로 가져오고, 창 클릭은 WinForms 버튼이 조용히 무시하기 때문입니다. 대상 컨트롤의 자식 창에 `WM_SETTEXT`·`BM_CLICK`을 보내고, 창 안 컨트롤을 다시 읽어 바뀐 글자·체크·활성 상태와 전면 창 유지 여부를 돌려줍니다. 대상 창이 다른 창에 가려져 있어도 동작합니다. 창은 `computer.window()`의 id로 고르고, 컨트롤은 정확한 글자나 클래스 이름 일부로 고릅니다. 후보가 여럿이면 `index` 없이는 아무것도 보내지 않습니다. 버튼이 모달 창을 열면 기다린 시간(기본 2초) 뒤에 "전달됐지만 처리 중"으로 돌아오고, 그 대화상자도 같은 도구로 누를 수 있습니다. 한 번 부르는 데 PowerShell 시작과 컴파일로 약 1초가 걸립니다. WPF·WinUI·웹처럼 컨트롤마다 창이 없는 화면은 다루지 않습니다. 입력 권한은 `computer`와 같습니다.

## ego lite 브라우저 `ego_browser`

[`ego_browser`](../Tools/OMP_Global_Config/agent/tools/ego-browser/)는 ego lite가 설치된 PC에서 에이전트가 ego의 TaskSpace(사용자 탭과 떨어진 작업 공간)를 직접 다루는 세션 도구입니다. 스크립트 본문만 넘기면 도구가 공간 생성과 `task`·`page` 연결을 앞에 붙여 `ego-browser nodejs`로 실행하고, 출력과 종료 상태를 돌려줍니다. 공간은 세션과 프로필마다 하나를 이어 쓰며(호출 사이에 변수는 남지 않고 탭은 남습니다), `finish: true`를 주면 오류가 나도 공간을 닫습니다. 세션이 끝날 때 열려 있는 공간도 닫지만, 사람에게 넘긴(`task.handOff()`) 공간은 닫지 않습니다.

`profile: "user"`(기본)는 사용자의 ego 프로필이고, `profile: "verify"`는 CUELO 화면 검증 전용으로 따로 둔 프로필입니다. 검증 프로필은 PC마다 디렉터리 id가 다르므로 ego 프로필 이름 「CUELO 검증」으로 찾고, 그 이름의 프로필이 없으면 다른 프로필로 넘어가지 않고 실패합니다. 화면 검증은 사용자 프로필을 쓰지 않습니다. ego lite가 없는 PC에서는 이 PC에서 쓸 수 없다고 알리고 기존 `browser` 도구를 쓰도록 안내합니다. 쿠키·캐시·저장소 삭제는 프로필 전체에 닿으므로 하지 않습니다.

## Task Guard와 command guard

[Task Guard 규칙](../Tools/OMP_Global_Config/agent/rules/task-guard.md)은 발주 brief에 `WORK_CLASS`, `PRIMARY_DELIVERABLE`, `OWNED_PATHS` 등 작업 계약을 담도록 정합니다. [`command-guard` 확장](../Tools/OMP_Global_Config/agent/extensions/command-guard/)은 task dispatch에서 maker 역할·요청별 budget·작업 잠금·소유 경로를 검사하고, 자식 작업에서 실제로 바뀐 경로를 advisory로 보고합니다. `bash` 명령에서는 삭제·데이터베이스 변경·배포·Git 마감처럼 보호 대상 동작도 검사합니다. 별도 eval 경로를 이용한 child budget 우회도 막습니다. WSL에서는 Windows 콘솔 프로그램(`git.exe` 제외)을 부르는 `bash` 명령을 새 bash로 감싸 실행해, CP949로 나온 한글 출력을 UTF-8로 바꿉니다. UTF-8로 나온 줄과 종료 코드는 그대로입니다. 감싸지 못한 명령의 출력이 깨졌거나 시스템 `python3`에 모듈이 없어 실패했으면, 다시 실행할 방법(`iconv`, 관리 Python 환경 경로)을 결과에 한 줄 덧붙입니다. 이것은 Main의 요구사항 판단이나 최종 검수를 대체하지 않습니다.

요청별 budget(primary 16, rework 8, 합계 24)은 실제로 시작한 Maker만 셉니다. 승인 거부, 승인 창 오류, 하류 guard 거절, 실행 전 중단·건너뛰기로 task가 실행되지 않은 호출과 작업 등록에 실패한 항목은 그 호출의 예약과 임시 소유 추적만 돌려놓습니다. 이미 시작한 Maker는 호출이 오류로 끝나도 계속 셉니다. 실행 도중 예외로 결과가 사라진 호출은 그 뒤 등록된 작업이 없다고 확인될 때만 돌려놓고, 확인할 수 없으면 그대로 남깁니다. `proc://<id>/kill`로 취소가 확인된 Maker는 이름이 같아도 런타임이 붙인 실제 id로 찾아 그 Maker의 primary·rework 몫만 한 번 돌려받습니다. 취소로 돌려받는 몫은 요청당 8개까지입니다.

이 하네스에서 `agent`를 생략하면 `maker`로 채워 실제 실행에 전달합니다. 명시적으로 `task`나 다른 역할을 적으면 허용하지 않습니다. 내장 코어는 도구 입력 검사에서 생략을 임의의 역할 이름으로 바꾸지 않으며, 이 하네스가 없는 환경에서는 기존 실행기의 기본 역할 선택을 유지합니다. 준비 참조 복원 뒤에도 같은 구분을 적용하고, 모델·추론 강도·소유권·승인·예산 검사는 생략하지 않습니다.

발주 준비와 실행은 같은 `TASK_GUARD` 블록 경계를 사용합니다. 캐릭터 호출은 이번 실제 사용자 요청이 있을 때만 예외이며, 모델이 표식만 써서 검사를 생략할 수 없습니다. 다른 세션 ID로 옮기면 이전 요청의 계약·소환 상태를 비우고, 같은 ID의 reload는 진행 중인 상태를 유지합니다.

같은 `task` 배치에서 공유 작업공간 Maker들의 `OWNED_PATHS`가 겹치면 어떤 작업도 예약하지 않고 배치 전체를 거절합니다. 별도 호출도 앞선 호출의 승인 중 예약과 충돌하면 막습니다. 시작한 작업은 실제 owner로 넘기고, 거절·실패·미실행으로 끝난 호출은 자기 예약만 해제합니다. 하류 guard가 거절한 호출도 같은 메시지의 준비 단계에서는 예약을 유지하므로 뒤 호출이 보수적으로 막힐 수 있으며, 호출 종료 뒤 다음 발주에서 풀립니다.

별도 worktree로 실행하는 `isolated` 작업은 공유 작업공간 충돌에서 제외합니다. 실제로 시작된 작업의 소유 경로와 격리 여부는 원장에 저장해 세션을 다시 열어도 복원합니다. 완료된 Maker도 REWORK나 일반 후속 지시로 실제 job이 실행 중이면 같은 경로를 보호합니다. 과거 원장의 running 상태만으로 잠그지 않으며, 끝났거나 사라진 실행은 경로를 계속 점유하지 않습니다. 옛 기록에 소유 경로가 없으면 실행 중인 동안만 공유 작업공간의 새 발주를 막습니다.

실행 중인 Maker끼리는 쓰기 단계에서도 소유 경로를 지킵니다. 공유 작업공간의 Maker가 `edit`·`write`로 같은 Main이 띄운 다른 Maker의 `OWNED_PATHS` 안을 고치려 하면, 그 Maker가 아직 실행 중일 때 command guard가 막고(`[OwnerWriteGuard]`) 필요한 변경과 이유를 Main에 보고하라고 안내합니다. 자기 소유 경로, 실행 중인 다른 Maker가 갖지 않은 인접 파일, 이미 끝난 Maker의 경로, Main 세션과 격리(`isolated`) 작업은 그대로 허용합니다. 소유 상태를 확인할 수 없으면 막지 않습니다. `bash`로 하는 파일 변경은 대상 경로를 확실히 알 수 없어 이 보호에 들지 않습니다.

Maker가 끝날 때 나오는 `[OwnershipGuard]` 보고에 소유 밖 변경이 있거나(outside 목록) 변경을 관측하지 못했으면(unobserved), 그 보고를 `~/.omp/agent/ownership-outside.jsonl`에 한 줄씩 남깁니다. 시각·세션·Maker 이름과 id·소유 경로·범위 밖 경로·동시에 실행된 Maker를 적으며, 빈도를 확인하는 진단 기록이라 작업을 막지 않습니다.

취소 요청의 소유권 정산은 같은 작업 ID·시작 시각의 `cancelled` 상태와 종료 시각을 함께 확인합니다. 종료 기록이 남아 있는 동안 로컬 snapshot을 다시 확인하지만, 관측 전에 기록이 사라지면 종료를 추정해 잠금을 풀지 않습니다.

`bash` 도구의 내장 셸은 PowerShell이 아니므로, 명령 위치의 cmdlet(`Test-Path`, `Set-Content` 등), 따옴표 밖의 `$env:NAME`, `$x = ...` 대입, `if (...) { }` 블록, `$`가 든 `powershell -Command` 인자는 실행 전에 막고 `write`로 만든 `.ps1`을 PowerShell 7(`pwsh -NoProfile -ExecutionPolicy Bypass -File`, WSL에서는 Windows `pwsh.exe`)로 실행하라고 안내합니다. 7이 없을 때만 `powershell.exe`(5.1)를 씁니다. 따옴표 안의 값과 heredoc 본문은 데이터로 보고 검사하지 않습니다.

명령 가드는 해석 가능한 명령의 실수를 막는 장치이며, 임의 스크립트·동적 코드·다른 실행 도구를 격리하는 보안 sandbox가 아닙니다. 검사에서 잡히지 않은 명령도 사용자 승인과 Git 마감 규칙을 따라야 합니다. 모델이 쓰는 텍스트나 경과 시간만으로 승인·실행 종료를 추정하지 않습니다.

## Typed judgment routing (Jev)

정식 신규 발주나 의미 있는 과제 변경 때 `maker_route`는 작업 분류·등급의 중심 난제·기존 owner 중복 등을 한 번에 판단하도록 사용됩니다. 첫 예상 밖 실패나 보고 검수처럼 다른 경계에서는 [`jev-runtime.ts`](../Tools/OMP_Global_Config/agent/extensions/jev-runtime.ts)가 런타임 advisory로 관측 가능한 사실을 제공하고, Main/owner가 그 사실에 담기지 않은 의미와 승인을 판단합니다. 기존 Maker에게 보내는 지시는 전송을 붙잡지 않고, 뒤에서 JEV가 원 계약(`PRIMARY_DELIVERABLE`·`OWNED_PATHS`·수용 조건) 대비 동일 범위·범위 변경·수용 조건 변경·불명 중 하나로 분류해 Main에게 알립니다. 코드·URL·literal은 가리고 경로는 `OWNED_PATHS` 안/밖 표시로만 보내며, 비밀 형식이 보이면 부르지 않습니다. 실패·시간 초과·자격 없음은 불명이고 다른 모델로 대체하지 않으며, 분류는 승인·차단·모델 교체가 아닙니다. 같은 질문을 반복하거나 Jev 결과를 결정론적 권한·검수로 취급하지 않습니다. 정본은 [subagent 규칙](../Tools/OMP_Global_Config/agent/rules/subagent.md)의 “Typed judgment routing”과 policy `routing.typedJudgmentRouting`입니다.

`maker_route`는 같은 Jev 배치에서 교차검토 필요성 권고(`crossReviewAdvice`), 판단 기준과 다음 행동 또는 부족한 근거를 함께 돌려줍니다. 추가 모델 왕복이나 별도 차단 게이트는 없으며 Jev의 권고는 고위험·위험 표식·표본의 필수 검토나 사용자 승인을 면제하지 않습니다. `WORK_CLASS`·`PRIMARY_DELIVERABLE` 불일치처럼 규칙으로 확정되는 형식 오류는 Jev 호출 전에 Task Guard와 같은 정규화 기준으로 확인합니다. 같은 요청의 작업은 이 두 값을 공유하고 조각별 완료물은 `TASK_TITLE`·`TODO_TASKS`·`# Acceptance`로 구분합니다. 뒤 작업에서 두 값을 생략하려면 같은 준비 묶음 안에서 앞 작업이 값을 정했거나 기존 요청의 발주 lock이 있어야 합니다.

Jev 런타임은 `findScopedSettings(ctx.cwd)`로 실제 실행 프로필/프로젝트 설정을 읽고 SDK의 `resolveJudge`를 호출합니다. 이 확장은 API 키 파일이나 비공개 `models.yml`을 복사해서 활성화되지 않습니다. 설정 기본값 `auto`는 자격 있는 `modelRoles.judge` 체인으로 해석되고, 첫 native 판정 후보 뒤로는 chat/local 후보와 세션 모델을 붙이지 않습니다. CUELO는 `judge`에 OpenRouter의 `typesafe/jev-1.14`(판정 전용 `openrouter-decisions` API)을 두며, 판정 한 번은 1초 안에 끝납니다. Maker 후보 여섯 개는 이 Jev 역할과 별도로 `modelRoles.implSonnet` 등에서 읽습니다. 가입·키 입력·역할 지정은 [기존 프로필의 역할과 Jev 보완](installation.md#기존-프로필의-역할과-jev-보완)에서 사용자가 직접 마칩니다. 실제 판정의 외부 요청/과금과 미검증 경계는 `setup`·`health` 성공으로 넘기지 않습니다.

판정 후보의 계정이 인증·결제·한도 문제(401·402·403)로 거절하면, 그 후보는 1분 동안 건너뛰고 다음 후보로 갑니다. 판정마다 같은 키로 다시 요청하지 않게 하려는 것입니다. 1분이 지나면 다시 요청하므로, 한도를 올리거나 키를 바꾼 뒤 판정이 오래 막혀 있지 않습니다(상류 기본값은 5분).

`maker_route`는 Jev 판정과 후보 제공자 사용량 조회를 함께 시작하고, 빠른 판정에도 조회를 조기 취소하지 않습니다. 사용량 조회는 기존 2초 제한 안의 결과를 기다리며 실패·timeout은 미측정으로 표시합니다. 사용량은 배정 참고 정보이지 Jev 판단 입력이 아닙니다.

확장의 판정 호출도 CORE의 사용량 기록과 공유 답변 캐시를 사용합니다. 실제로 청구된 시도만 세션에 기록하고, 캐시로 답한 요청을 새 과금으로 세지 않습니다. 이 캐시는 동일한 판정 입력·질문·조건의 **답변**을 재사용하며 제공자가 프롬프트 토큰을 재사용하는 캐시와는 다릅니다. 캐시가 승인 권한을 부여하거나 판정 전용 호출을 일반 채팅 모델로 우회시키지는 않습니다.

턴 경계에는 JEV를 한 곳 더 씁니다. [`turn-end-guard.ts`](../Tools/OMP_Global_Config/agent/extensions/turn-end-guard.ts)는 작업 중 사용자가 던진 질문에 이후 본문이 실제로 답했는지 입력당 한 번 판정하고, 미답이면 먼저 답하라고 안내합니다. 경로·URL·코드·secret을 지운 짧은 발췌만 보내고, 승인이나 도구 차단이 아닙니다. [`external-advice-check.ts`](../Tools/OMP_Global_Config/agent/extensions/external-advice-check.ts)는 다른 모델의 긴 답을 붙여 검증을 요청하면 주장마다 도구로 확인·반박·미확인으로 답하라는 고정 안내를 그 사용자 메시지와 같은 턴에 숨김 메시지로 붙입니다. JEV를 부르지 않아 첫 응답을 기다리게 하지 않고, 별도 턴을 열지 않으므로 긴 첫 메시지가 밀려나지 않습니다. `jev-runtime.ts`는 Windows 셸 경계 실패(PowerShell 변수 소실, 역슬래시 경로 소실, PATH 첫 `bash`인 WSL이 CRLF `.sh`를 읽어 낸 `$'\r'` 구문 오류, Windows `curl.exe`가 `-o /dev/null`에 쓰지 못해 응답을 받고도 낸 exit 23 등)를 따로 분류해 고치는 방법을 알리고, 이 세션이 띄운 실행 중 작업이 쥔 폴더를 지우려는 호출은 그 작업이 끝날 때까지 막습니다. `verify.ps1`은 PATH 첫 `bash`가 WSL 실행기이면 판정에 넣지 않는 경고 한 줄을 출력합니다.

같은 판정을 두 곳에 더 씁니다. [`steering-reply-gate.ts`](../Tools/OMP_Global_Config/agent/extensions/steering-reply-gate.ts)는 작업 중 끼어든 질문에 첫 도구 앞 본문이 답했는지 판정합니다. 질문이 아닌 지시·수락에는 이를 받아들이는 답도 인정합니다. 판정은 뒤에서 돌아 도구 실행을 붙잡지 않으며, 이후 본문이 바뀌거나 실행이 끝났으면 늦게 도착한 판정으로 다시 답하게 하지 않습니다. `turn-end-guard.ts`는 미완 TODO가 없어도, 본문 마지막 500자에 "다음에 하겠다" 같은 미루기·계속 약속 표현이 있으면 승인 없이 지금 할 수 있는 일을 남기고 끝낸 턴인지 판정해 이어 가라고 안내합니다. 완료 보고 안에서 지금 고칠 수 있는 결함·검증을 "남은 것"으로 적거나 "원하시면 고칠게요"로 넘긴 경우도 같은 판정 대상입니다. 그런 표현이 없는 턴 끝에는 JEV를 부르지 않습니다. 배포·삭제·비용·사용자 선택·외부 대기는 자동으로 이어 가지 않습니다. 그런 동작을 묻거나 기다리거나 미루는 문장이 있으면 판정 전에 멈추고, 이미 끝낸 배포·재시작을 보고한 문장만으로는 멈추지 않습니다. 체크포인트 회신을 기다리는 child 세션은 제외합니다. 사용자 정지나 업데이트·재시작 중단으로 abort된 턴도 다시 깨우지 않습니다. 업데이트가 세션을 멈춘 뒤 옛 서버에서 도구가 다시 도는 일을 막기 위해서입니다. `jev-runtime.ts`의 재시도 경계는 judge 없이 로컬에서 테스트·CI 실패를 시간 초과·모듈/환경·source manifest 불일치·assertion으로 나눠, 다시 돌릴 일인지 고칠 일인지 알려 줍니다. 이런 범주와 Windows 셸 경계 실패, 종료 코드 없이 취소된 실행처럼 구체적인 다음 행동이 있을 때만 알리고, 그 밖의 첫 실패에는 알림을 넣지 않습니다.

화면 확인에도 JEV를 씁니다. [RULES.md](../Tools/OMP_Global_Config/agent/RULES.md)의 화면 확인 규칙은 Main과 Maker 모두에 적용됩니다. 웹은 `browser`, 네이티브 데스크톱 창은 `computer`, 로직은 테스트로 확인합니다. 먼저 조작할 창·요소와 사용자가 원하는 결과를 정하고, 결과를 확인할 수 있는 조작·대기·확인 단계만 한 `eval` 셀에 묶습니다. 화면 전환이나 입력 대상이 불확실한 경계에서는 새 상태를 확인한 뒤 이어갑니다. DOM 텍스트·AX 속성은 정확한 값으로 먼저 비교하고, 문자열로 가를 수 없는 의미 판단만 `judge()`(JEV)에 텍스트로 넘깁니다. 스크린샷은 모양이나 원격 화면처럼 의미 있는 AX 정보가 없는 대상을 확인할 때 쓰며, `judge()` 결과는 참고 신호이지 최종 수용 근거가 아닙니다. `computer`는 실제 데스크톱을 조작하므로 자기가 띄운 창만 다루고, 되돌릴 수 없는 버튼은 누르지 않습니다. 같은 순서를 여러 문서·기록·로그를 분류할 때(정해진 문구로 거른 뒤 남은 것만 `judge_batch`)와 긴 작업을 감시할 때(종료 문구는 문자열, "멈췄나"만 `judge()`)도 씁니다. 기준선과 비교하는 재측정은 기준선과 같은 방법으로 셉니다.

패치된 내장 코어의 `computer` 행동(`press`·`click`·`setValue`·`focus`·창 좌표 입력 등)은 `{ action, status, suggestedNext, evidence?, reacquired? }`를 돌려줍니다. `status`는 `verified`·`unverified`·`suspected_noop`이고, `verified`는 해당 행동의 접근성 readback에서 변화나 요청한 값을 읽었다는 뜻이지 사용자 목표의 완료 판정이 아닙니다. 좌표·키 입력은 애플리케이션 효과를 직접 읽지 못하므로 `unverified`와 `reobserve`를 돌려줍니다. 행동 결과를 버리지 말고 목표 상태와 함께 확인합니다. `ax()`·`observe()`·`find()`가 준 ref가 화면 갱신으로 만료되면 발급 때 저장한 지문(role·이름·RuntimeId·AutomationId·이름 있는 부모 경로·위치)으로 후보를 좁혀, 하나로 특정될 때만 그 요소를 다시 잡습니다. 후보가 없거나 여럿이면 다른 요소를 조작하지 않고 기존 `StaleRef`로 실패하며, 오류의 `computerAction` 필드에 거절 이유와 후보를 싣습니다. 설계는 [Cua의 행동 결과 계약](https://github.com/trycua/cua/blob/main/libs/cua-driver/docs/action-result-contract.md)과 [browser-use의 요소 재식별](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/service.py)을 참고했습니다.

background 입력을 받지 않는 창(Chromium 계열·XAML 메모장 등)은 `BackgroundUnavailable`로 거절합니다. CUELO 프로필은 `computer.backgroundFallback: refuse`를 써서, 이런 창에 포커스를 빼앗아 입력하는 takeover를 자동으로도, `{ takeover: true }`로 명시해도 하지 않고 아무것도 보내지 않습니다. takeover는 호출마다 포커스를 가져왔다가 사용자 창으로 돌려주므로, 여러 번 나눠 보낸 입력이 그 사이 사용자가 쓰던 창으로 샐 수 있기 때문입니다. 웹 페이지는 `browser` relay로, 네이티브 컨트롤은 접근성(AX) 동작으로 다루고, 둘 다 안 되는 단계는 사용자에게 맡깁니다. 패치된 코어 안내도 오류가 알려 주는 설정을 따르게 하고, 조작 결과는 같은 셀에서 확인하되 문구가 매번 달라 문자열로 가를 수 없을 때만 스크린샷 대신 AX 텍스트를 `judge()`에 넘기게 합니다. 포커스·창 정체·권한처럼 OS가 답하는 판단은 `judge()`에 맡기지 않습니다. 작업 전체의 포그라운드 장악(`computer.control.acquire`)은 확인 창이 그대로 있고, 사용자가 지속적인 포그라운드 조작을 요청할 때만 씁니다.

원격 데스크톱 창을 찾았다는 사실은 그 안의 앱·입력칸을 찾았다는 뜻이 아닙니다. 로컬 창의 정체는 OS 정보로 확인하고, 원격 대상은 새 화면에서 별도로 확인합니다. 로컬 클립보드 쓰기 성공도 원격 붙여넣기 성공이 아닙니다. 명령은 대상 확인 → 붙여넣기 → 경로·중요한 인자를 포함한 내용 확인 → 실행 → 실행 결과 확인 순서로 다룹니다. 내용을 읽을 수 없거나 대상이 바뀌면 후속 입력을 멈춥니다. 포커스 오류가 없어질 때까지 키 입력을 반복하거나, 같은 오류에 단축키 이름만 바꿔 재시도하지 않습니다. 이미지를 통한 전사는 기존 `?ocr=` 경로를 따르고, 불명확한 글자를 추측해 실행하지 않습니다.

탐색기에서 폴더가 열렸다는 증거와 요청한 파일이 선택됐다는 증거도 구분합니다. 창 제목만 확인했다면 파일 선택은 미확인으로 보고합니다. 좌표는 같은 대상의 최근 전체 스크린샷 기준을 유지하며, `InvalidCoordinateFrame`이나 `StaleRef`가 나오면 보호를 우회하지 않고 다시 관찰합니다.

행동 뒤 목표 상태는 `computer.run` 안에서 행동을 한 번 부른 다음 `wait(predicate, { timeout })`으로 확인합니다. 예: `await save.press(); const row = await wait(async () => (await win.find({ title: "Saved row 1" }))[0], { timeout: 5000 });`. `wait(predicate)`는 upstream에 이미 있던 기능이고, 새 API나 도구는 추가하지 않았습니다. 기존에는 predicate를 100ms 고정 간격으로 다시 불렀고, 그 안의 클릭·도구 호출도 매번 그대로 실행했습니다. 늦게 끝난 읽기의 나머지 코드도 deadline 뒤에 계속 돌았습니다. 패치된 코어는 다음처럼 바꿉니다.

- predicate를 바로 한 번 읽고, 이후 100·250·500·1000ms 간격으로 다시 읽습니다(마지막 간격 반복). `interval`을 주면 그 고정 간격(최소 10ms)을 씁니다. 대기는 남은 시간을 넘지 않고, deadline이나 취소 뒤에는 새 읽기를 시작하지 않습니다. 참이 되면 그 값만 돌려줍니다.
- predicate 안에서 데스크톱 입력·`clipboard.write`·도구 호출은 실행 전에 거절됩니다. 그래서 목표가 늦거나 끝내 나오지 않아도 다시 클릭하거나 takeover하거나 다른 창을 고르지 않습니다. 스크린샷은 읽기로 허용하되 probe마다 이미지를 대화에 붙이지 않습니다.
- 제한 시간 안에 목표가 없으면 `wait(predicate) timed out after …` 오류로 끝나고, 취소는 취소로 끝납니다. predicate 안의 native·프로그래밍 오류는 재시도하지 않고 그 오류를 그대로 올립니다. 제한 시간·취소·성공 뒤에는 늦게 끝난 읽기의 나머지 코드가 데스크톱을 더 읽거나 조작하지 못합니다.

predicate는 여전히 샌드박스가 아닌 Bun/Node 코드입니다. 위 거절은 데스크톱 facade와 도구 bridge에만 적용되고, 임의 I/O를 모두 막지는 않습니다. 어떤 행·문구·값이 목표인지는 호출하는 쪽이 정해야 하고, 버튼 모양 변화만으로 저장이 성공했다고 보지 않습니다. 이 대기는 행동의 승인 등급을 바꾸지 않으므로, 저장·전송처럼 결과가 남는 클릭은 전처럼 사용자 승인이 필요합니다. 간격과 deadline 처리는 [Playwright `pollAgainstDeadline`](https://github.com/microsoft/playwright/blob/main/packages/isomorphic/timeoutRunner.ts)과 [`expect.poll`](https://playwright.dev/docs/test-assertions#expectpoll)을 참고했고, 코드를 가져오거나 의존성을 추가하지 않았습니다.

이미지를 읽을 때는 vision 모델에게 먼저 묻습니다. [`image-question-router.ts`](../Tools/OMP_Global_Config/agent/extensions/image-question-router.ts)는 Main이나 Maker가 이미지 파일을 `?q=`·`?ocr=` 없이 `read`하려 하면, 이미지가 컨텍스트에 실리기 전에 막고 질문으로 묻게 합니다. `경로?q=<질문>`은 `modelRoles.vision`(Opus 5.5 low)이 레이아웃·간격·색·정렬·잘림·좌표 같은 형태 판단과 특정 값 확인에 답하고, `경로?ocr=<질문>`은 OCR 전용 `modelRoles.ocr`(없으면 vision 순서)이 글자·숫자·표 전사에 답합니다. OCR에는 후보군을 둘 수 있습니다. `retry.fallbackChains.ocr`에 모델을 순서대로 적으면 `modelRoles.ocr`을 쓸 수 없을 때 그 순서대로 고르고, 고른 모델이 오류·중단·시간 초과로 실패하면 다음 후보와 마지막으로 vision 모델에 같은 질문을 묻습니다. 다른 모델이 답했으면 답 앞 한 줄에 실패한 모델과 답한 모델을 밝힙니다. 사용자가 끊은 요청과 `?q=` 질문은 다음 후보로 넘기지 않습니다. 각 역할의 모델은 별도로 지정할 수 있으며, 작은 글자의 전사 불일치는 원본 이미지로 대조합니다. 답만 텍스트로 돌아옵니다. JEV 판정 없이 동작하는 로컬 규칙입니다. 그 경로로 한 번 질문한 뒤에는 같은 경로를 다시 읽어 직접 볼 수 있고, 질문 없이 다시 읽으면 계속 막힙니다. `browser`·`computer` 스크린샷은 `read`가 아니라서 대상이 아닙니다.

[`gitnexus-autosync.ts`](../Tools/OMP_Global_Config/agent/extensions/gitnexus-autosync.ts)는 새 Main 세션이 시작될 때 작업 폴더가 속한 저장소에 GitNexus 색인(`.gitnexus/meta.json`)이 있고 그 색인 커밋이 현재 `HEAD`와 다르면, 백그라운드에서 `gitnexus analyze --index-only`를 한 번 실행합니다. 세션 시작은 기다리지 않고, 저장소마다 잠금 파일로 한 번만 돌며, 색인이 없는 저장소에는 새 색인을 만들지 않습니다. `--index-only`라서 `AGENTS.md`·`CLAUDE.md`·skill 파일은 다시 쓰지 않습니다. 실행 파일은 `PATH`의 `gitnexus`를 먼저 쓰고, 없으면 이미 받아 둔 `bun x --no-install gitnexus`를 씁니다. 새로 설치하거나 내려받지 않습니다. GitNexus MCP가 색인 DB를 열고 있으면(Windows) 건너뛰고 다음 세션에서 다시 확인합니다. 결과와 실패는 저장소의 `.gitnexus/autosync.log`에만 남고 세션에는 알리지 않습니다. 서브에이전트 세션에서는 돌지 않습니다. 색인 갱신은 저장소 크기에 따라 몇 분 동안 CPU를 쓰며, 그동안 GitNexus 질의는 이전 색인으로 답하거나 일시적으로 실패할 수 있습니다.

갱신 뒤에는 Function 행의 식별자 무결성을 확인합니다. 현재 `HEAD`와 같은 색인도 해당 커밋의 검사 이력이 없으면 갱신 없이 먼저 확인하며, 손상이 발견되면 `--force` 전체 재구축을 한 번 시도합니다. DB 사용 때문에 재구축을 미룬 경우 다음 세션에서 다시 확인하고, 실제 재구축 후에도 손상이 남으면 반복하지 않고 로그에 남깁니다. `.gitnexus/autosync-health.json`은 검사 이력이지 전체 그래프의 정확성 보증이 아닙니다. 손상 유발 조건은 아직 확정하지 못했으며, 비색인 의존성과 찾지 못한 심볼의 `UNKNOWN`을 안전한 `LOW`로 해석하면 안 됩니다.

Windows에서는 FTS 확장이 Git의 `mingw64/bin`에 있는 OpenSSL DLL을 필요로 할 수 있습니다. 자동 갱신 워커의 PATH 보정은 별도 터미널의 직접 CLI 호출에 전파되지 않습니다. 직접 호출에서 FTS 로드 경고가 나면 기존 Git 설치의 해당 DLL 디렉터리를 그 명령의 PATH에 포함해 실행합니다. 시스템 PATH나 전역 패키지를 자동으로 변경하지 않습니다.

## 캐릭터 말투와 확장

[`character-voice.ts`](../Tools/OMP_Global_Config/agent/extensions/character-voice.ts)는 사용자 대면 말투 block을 현재 세션에 주입하고, 캐릭터 호출 의도를 지정된 경로로 전달합니다. 사용자 지정 말투와 기술적 사실은 보존하고, 반복되는 고정 대사를 피하는 규칙은 [AGENTS.md](../Tools/OMP_Global_Config/agent/AGENTS.md)에 있습니다. [`todo-nudge.ts`](../Tools/OMP_Global_Config/agent/extensions/todo-nudge.ts)는 사용자 요청 하나에서 Main이 TODO 목록 없이 도구를 세 번 부르면 요청당 한 번 목록을 만들라고 안내합니다. 목록이 진행 중일 때 작업 종료·Maker 보고·DM 알림이 도착하면 해당 항목의 상태를 바로 갱신하라는 안내도 한 번 넣고, TODO를 다시 갱신하면 다음 알림에서 또 안내합니다. 사용자가 화면의 TODO로 진행 상황을 볼 수 있게 하려는 것이며, 도구를 막지 않고 child 세션에는 개입하지 않습니다. 다른 공개 확장과 `command-guard`는 `agent/extensions/`에 있습니다.

서버 설정의 「기본 / 사무실 모드」를 사무실로 두면, 이 PC 프로필(`characters-office/roster.json`)에 유효한 항목이 있는 자리들을 프로필의 별칭·이름·말투로 바꿔 씁니다. 대상은 YUKI·ISANA·MIO·RIN·SHION·HIKARI이며 MITSU는 그대로입니다. 각 자리의 모델·계정 위치·도구 사용 권한과 SHION의 상담 전용 경계는 바뀌지 않습니다. 이름이나 id가 겹치면 위의 고정 순서에서 먼저 받아들인 자리를 유지하고 뒤의 충돌 항목은 기본 캐릭터로 남깁니다. 프로필이 없거나 읽을 수 없을 때도 기본 캐릭터로 동작합니다. 캐릭터 데이터와 이미지·음성 자산은 저장소나 공개본이 아니라 각 PC의 프로필에만 둡니다.

Main은 TODO를 최초 계획에만 쓰지 않고 실시간 현황으로 유지합니다. 착수·검증 완료·외부 대기·재개·재작업을 확인한 자리에서 갱신하고, agent나 검사 결과를 기다리는 항목에는 담당과 남은 조건을 적습니다. 도구의 자동 활성 포인터가 앞선 통합 항목으로 돌아갈 수 있으므로 갱신 결과도 확인합니다. 사용자에게 먼저 답해야 할 때는 즉답 후 같은 턴에서 동기화하며, 채팅 설명만으로 TODO 갱신을 대신하거나 포인터를 맞추려고 미완을 완료 처리하지 않습니다.

[`korean-reply-guard.ts`](../Tools/OMP_Global_Config/agent/extensions/korean-reply-guard.ts)는 Main의 사용자 표시 답변이 영어로 새는 일을 막습니다. 코드·인라인 코드·URL·경로·식별자·원본 오류 줄을 뺀 산문에서 라틴 글자가 20자 이상이고 한글 비율이 15% 미만이면(한 줄짜리 영어 진행 문장 포함) 영어로 봅니다. 영어로 나간 메시지는 처음부터 `modelRoles.tiny` 모델로 한국어로 번역해, 이미 나간 내용도 한국어로 읽을 수 있게 합니다. 번역 통지는 원문 답의 시각과 텍스트 hash를 함께 남기고, CUELO 대화창은 이를 따라 그 답 말풍선의 본문을 한국어 번역으로 바꾸며 영어 원문은 「영어 원문 보기」로 접어 둡니다. 도구 호출·사고 블록은 그대로 보이고, 번역이 도착하기 전에는 영어 본문이 그대로 보입니다. 원문을 하나로 정할 수 없는 번역(같은 시각·같은 내용의 답이 둘인 경우)과 이 연결이 생기기 전의 옛 기록은 전처럼 작업 과정에 별도 상자로 남습니다. 긴 답도 앞부분만 자르지 않고 전체를 번역하며(출력은 모델 최대치, 2분 제한), 모델 한도에서 끊기면 끊긴 번역과 그 사실을 함께 보여 줍니다. 영어로 나간 답마다 숨김 안내도 넣어 다음 답부터 한국어로 쓰게 합니다. 한 번만 안내하면 한 답만 한국어로 돌아왔다가 다시 영어가 길게 이어질 수 있어서입니다. 같은 문구라도 한국어 답이나 새 요청을 사이에 둔 별도 답이면 다시 안내하고, 같은 답이 그대로 다시 전달된 경우만 건너뜁니다. 번역은 최근 50가지 내용 안에서 같은 내용을 한 번만 요청하므로, 같은 문구가 반복된 답은 첫 답에만 번역이 붙습니다. 안내가 쌓이지 않도록 모델 문맥에는 마지막 안내 하나만 남기고, 번역은 모델 문맥에서 빠집니다. 민감 정보처럼 보이는 글은 외부로 보내지 않으며, 그때와 번역이 실패했을 때는 영어 본문 아래에 그 사실을 한 줄로 붙입니다. 사용자가 영어로 쓰거나 영어 답을 요청한 턴과 서브에이전트에는 개입하지 않으며, 번역에는 tiny 모델 요청 비용이 듭니다.

[`report-chart-guard.ts`](../Tools/OMP_Global_Config/agent/extensions/report-chart-guard.ts)는 위 차트 규칙이 빠지는 일을 줄입니다. 답변 전체의 숫자를 한데 모으지 않고 같은 문단·목록·표의 수치를 확인합니다. 날짜·회차·주기·추정 표현은 구분하고 이어진 분·초 표기는 한 시간 값으로 셉니다. 기록된 비교·추이·분해에 차트를 붙이는 기준은 바뀌지 않습니다. 이미 끝난 답변은 비교 구조가 확인된 후보에서만 다시 열고 숫자만 있는 모호한 산문 때문에 불필요한 마무리 응답을 만들지 않습니다. 도구 실행 중에는 숨김 안내를 보내며 같은 응답의 `ask`는 차트 필요 여부를 확인하도록 한 번 보류합니다. 이미 차트가 있거나 서브에이전트의 답변이면 개입하지 않고 별도 모델을 호출하지 않습니다.

Main과 서브에이전트(Maker)가 서로 주고받는 글은 양방향 모두 영어입니다. 발주·후속 지시뿐 아니라 Maker의 진행 발화·완료 보고·체크포인트·Maker끼리 보내는 메시지도 영어로 쓰고, 사용자에게는 Main이 필요한 내용을 한국어로 옮겨 전합니다. 사용자가 캐릭터를 불러 직접 답하게 한 경우는 사용자에게 하는 말이므로 한국어입니다.

캐릭터 교체는 인용 밖의 명확한 명령형으로 요청하세요. 부정문, 방법·설명 요청, 과거에 일어난 전환을 말하는 문장, 따옴표·코드·인용문 속 예시는 자동 전환하지 않습니다. 가능 여부를 묻는 모호한 질문도 교체 명령으로 처리하지 않습니다.

## 의미 검색의 폴더 탐색 보완

패치된 내장 코어의 `find`는 기존 파일 검색 결과를 보존하면서, 폴더 구조와 파일명 표본을 JEV로 판정해 기존 키워드 후보 범위 밖의 파일도 추가로 살펴봅니다. 기존 후보 밖 파일이 없으면 이 단계는 실행하지 않습니다. 추가 후보와 파일 읽기는 제한돼 있으며, 저장소 전체의 누락 없는 검색을 보장하지는 않습니다.

기존 비밀 파일·숨김 파일·무시 파일 제외와 검색 시간 제한은 그대로 적용합니다. 보완 단계가 실패하거나 시간 제한에 걸려도 이미 완료된 기본 검색 결과는 유지하고, 사용자 취소는 취소로 처리합니다. 결과에는 종전처럼 경로·줄 범위·짧은 미리보기를 반환하며 코드 원문을 일괄 덧붙이지 않습니다.

폴더 판정과 추가 탐색만큼 JEV 호출·검색 시간이 늘 수 있습니다. 전체 코딩 비용이나 성공률 개선으로 일반화하지 않으며, 별도 공식 `omp.exe`에는 이 로컬 패치가 포함되지 않습니다.

## 요청별 MCP 선택 연결

패치된 CUELO 내장 코어와 소스 CLI에서 다음 설정을 켜면, 시작할 때 모든 MCP에 연결하는 대신 요청마다 JEV가 필요한 서버를 고릅니다.

```yaml
mcp:
  selection: per-request
```

기본값 `all`은 기존의 시작 시 연결 동작을 유지합니다. 설정을 바꾼 뒤에는 새 세션에서 확인하세요. 별도 공식 `omp.exe`와 ACP 연결에는 이 로컬 기능이 적용되지 않습니다.

- 자동 연결 후보는 기존 설정과 프로젝트 신뢰 조건을 통과한 서버입니다. 꺼진 서버를 임의로 켜거나 인증·권한을 대신 승인하지 않습니다.
- JEV에는 현재 요청에서 추린 짧은 단서와 최소 프로젝트·서버 설명을 보냅니다. 설정의 환경변수·헤더·인증값이나 도구 스키마 전체는 보내지 않습니다. 알려진 비밀 형식은 가리지만 모든 개인정보를 검출한다는 보장은 아닙니다.
- 필요하지 않은 자동 연결 서버는 다시 실행하지 않고 도구 노출만 줄입니다. 사용자가 직접 연결한 서버는 수동 선택을 존중합니다.
- JEV를 사용할 수 없으면 새 연결을 만들지 않고 실패 상태를 알립니다. 개별 서버의 필요성을 판단하지 못한 경우도 연결하지 않으며, 요청에서 이름을 부른 서버에만 보류 안내를 표시합니다. 이름을 부르지 않은 보류 후보는 나열하지 않습니다. 전체 서버 연결이나 다른 채팅 모델로 조용히 대체하지 않습니다.
- 전역·프로젝트 설치 추천은 공식 출처와 필요한 작업·권한을 함께 안내하고 사용자 승인을 요청합니다. 승인 뒤에는 에이전트가 설치·등록·설정·연결·검증을 수행합니다. 사용자 본인 로그인·인증정보 입력·제공자 안전 확인·동의가 필요한 단계만 사용자에게 넘깁니다. 선택 확장은 스스로 설치를 실행하거나 승인을 대신하지 않습니다. `/mcp` 설치·인증 명령이 필요한 경우 터미널의 대화형 `omp`를 사용합니다.
- 같은 서버의 설치 추천은 한 번만 보여 줍니다. 보여 준 서버 이름은 agent 데이터 디렉터리의 `mcp-suggested.json`에 남고, 이후 세션에서는 요청에 그 서버 이름을 직접 적었을 때만 다시 판단합니다. 다시 처음부터 추천받으려면 그 파일에서 이름을 지웁니다.

`tools.xdevDocs: catalog`는 도구 상세 설명을 필요할 때 읽도록 하는 별도 설정입니다. 서버 연결을 고르는 `mcp.selection`과 같은 기능이 아닙니다. 요청별 판정은 JEV 사용량을 추가하며, 전체 작업 비용 절감률은 별도 측정 없이 보장하지 않습니다.

### 바이너리 분석용 REA 연결(선택)

소스가 없는 .NET 어셈블리·JavaScript/Electron 배포물을 **정적으로** 조사할 때 [REA](https://github.com/morluto/rea)를 기존 MCP 경로로 선택 연결할 수 있습니다. 일반 소스 개발은 기존 `read`·`grep`·LSP·테스트가 우선입니다. 전용 역할·코어·중계 서버는 필요 없습니다. 사용할 프로젝트의 `.omp/mcp.json`에 아래 항목을 기존 서버·설정·비밀정보를 보존하며 **병합**합니다(파일을 통째로 덮어쓰지 않습니다). 설치·등록은 사용자 승인 뒤에만 합니다.

```json
{
  "mcpServers": {
    "rea": {
      "enabled": true,
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "rea-agents@6.3.0", "mcp"],
      "timeout": 120000
    }
  }
}
```

- REA는 Node `22.x >=22.19`, `24.x >=24.11` 또는 `26+`에서 돕니다. CUELO 서버가 도는 OS(WSL이면 Linux)의 Node가 기준이며, 서비스 환경에서 `npx`를 못 찾으면 실제 경로를 `command`에 적습니다. 경로 인자도 그 프로세스가 읽는 경로(`/mnt/c/...`)로 줍니다.
- 사용자 전체 프로필을 바꾸는 `rea setup`은 자동 실행하지 않습니다. 첫 연결은 `/mcp reconnect rea`로 명시적으로 확인하고 실제 도구 목록과 호출 결과를 확인합니다. 처음 등록한 서버는 도구 캐시가 없어 `per-request` 자동 선택이 보장되지 않으므로 첫 확인은 명시 재연결로 합니다. 이후에는 기존 선택 연결 정책을 유지합니다.
- 큰 분석 결과는 MCP 전달 한도(약 10MiB)를 넘어 `resource_constraint`로 돌아오거나 표시 단계에서 잘릴 수 있습니다. 같은 연결의 retained Evidence ID로 `inspect_analysis_view` 범위를 좁히거나 `export_evidence_bundle`로 전체 근거를 조회합니다. 잘린 본문을 완전한 결과로 보고하지 않으며 분석 버전·입력 해시·범위·`unsupported`·`unknown`을 남깁니다.
- 여러 Maker가 REA의 열린 대상(`open_binary`·`close_binary`)을 동시에 바꾸지 않게 하고, managed 검사에는 매번 명시 경로를 줍니다. 비공개 바이너리, 대상 실행·디버거 부착, 브라우저·장치 연결, Ghidra·IDA·Hopper 연동은 이 도입 범위가 아니며 별도 승인과 검증이 필요합니다. MCP 등록 자체는 보안 샌드박스가 아닙니다.
- 소스가 있는 프로젝트는 기존 `read`·`grep`·LSP·테스트가 기준입니다. 추천 카탈로그는 HTTP 서버만 다루므로 REA는 자동 추천 목록에 없습니다.
- 제거할 때는 해당 세션의 REA 연결을 끊고 승인된 프로젝트 설정의 `mcpServers.rea` 항목만 제거합니다. 다른 서버·설정·비밀정보와 분석 결과는 보존합니다. 사용자 전체 설정을 바꾸는 uninstall은 사용하지 않습니다.

**검증 범위:** Linux/WSL의 패치된 OMP 18.8.9·REA 6.3.0·Node 24.21.0에서 공개·자체 생성 fixture와 실제 stdio 서버, 로컬 fake 모델을 사용했습니다. 실제 .NET 메타데이터·CIL 및 Electron IPC 결과 전달, Maker 도구 상속, CUELO의 신뢰하지 않은 프로젝트·도구 끔 세션 차단, 선택 연결·명시 재연결, 기존 설정 병합 보존, 정상 종료와 handshake 취소 후 프로세스 정리를 확인했습니다. 실행 파일 부재·연결 실패·시작 timeout은 별도 오류로 확인했고, 미지원 Node는 배포 패키지의 engine 조건으로 구분했습니다. 미지원 Node 실행, 분석 도중 취소, Windows REA 호환성은 미확인입니다. 운영 프로젝트에 자동 등록하거나 추가 자격증명을 설정하지 않습니다.

## Git 마감 도구

[`git_finalize`](../Tools/OMP_Global_Config/agent/tools/git-finalizer/)는 Main 전용 도구입니다. 정확한 파일 목록을 대상으로 경로·저장소 경계와 ancestry를 확인하고, 잠금 아래 commit 및 push를 수행합니다. 저장소에 `Tools/CUELO_Setup/files/source-build-helper.js`가 있으면, 커밋할 source 파일이 `source-integrity.json`과 다른데 manifest를 함께 넣지 않은 경우 commit 전에 멈추고 재생성 명령을 알려 줍니다. Maker에게 Git 마감을 허용하는 도구가 아닙니다. 구현과 PowerShell finalizer는 `agent/tools/git-finalizer/`에 있습니다.

WSL에서 Windows 드라이브(`/mnt/c`·`/mnt/v` 등) 위의 저장소를 마감할 때는 같은 finalizer를 Linux `pwsh` 대신 Windows `powershell.exe`로 돌리고, 경로는 `wslpath -w`로 바꿔 넘깁니다. 그래서 commit·push는 Windows Git과 그 자격 증명으로 실행됩니다. Linux Git은 Windows 드라이브의 파일을 하나씩 확인하느라 파일이 많은 저장소에서 수 분이 걸리고, 마감 제한 시간(3분)에 걸려 중단될 수 있기 때문입니다. 다만 Linux Git으로 만든 linked worktree는 `.git` 파일이 Linux 경로(`gitdir: /mnt/...`)를 가리켜 Windows Git이 열지 못하므로, 대상이 그런 worktree 안에 있으면 Linux `pwsh`와 Linux Git으로 마감합니다. WSL 디스크 안의 저장소는 이전처럼 Linux에서 실행합니다. 이 선택은 세션 작업 폴더가 아니라 마감할 파일의 위치로 정합니다. 그래서 작업 폴더가 Windows 드라이브의 사본(`/mnt/f/repo`)이어도 마감할 파일이 WSL 디스크의 다른 저장소(`~/src/repo`)에 있으면 Linux에서 마감합니다. Windows Git은 WSL 디스크의 저장소를 열지 못합니다.

같은 판정을 command guard의 저장소 확인, 앱의 Git 변경 보기(`/api/git/status`·`/api/git/diff`), worktree 조회도 씁니다. WSL에서 `/mnt/<드라이브>` 위 저장소이고, Linux 경로를 가리키는 linked worktree가 아니며, `git.exe`를 찾을 수 있으면 Windows Git으로 실행하고 출력 경로(`D:/repo`)는 `/mnt/d/repo`로 되돌립니다. 그 밖의 경우(ext4 저장소, Windows, 일반 Linux)는 이전과 같습니다. 판정 규칙은 하네스(`agent/tools/git-finalizer/wsl-git.ts`)와 앱(`lib/wsl-git.ts`)이 번들이 달라 두 벌이며, 바꿀 때는 둘을 함께 바꿉니다. worktree 만들기·지우기는 Linux Git으로 남깁니다(Windows Git이 만든 `gitdir: D:/...`를 Linux Git이 읽지 못합니다). Git 변경 보기는 세션 작업 폴더가 저장소의 하위 폴더이면 그 폴더 아래만 봅니다.

같은 이유로 command guard는 bash에서 Linux `git`으로 이런 Windows 드라이브 저장소를 여는 명령을 막고 `git.exe`로 다시 실행하라고 안내합니다. 두 Git은 index에 적는 파일 정보가 서로 달라서, 번갈아 쓰면 바뀐 쪽이 추적 파일 전체를 다시 확인하고 index를 통째로 다시 씁니다. 파일이 많은 저장소에서는 이 작업이 bash 제한 시간에 끊겨 `index.lock`이 남고, 이후 `git_finalize`가 막힙니다. `--no-optional-locks`를 붙여도 `git diff`의 index 갱신은 막히지 않습니다. 대상 폴더는 `cd <리터럴 경로> &&`와 `-C`로 판정하며, `git.exe`, Windows PowerShell 안의 `git`, Linux 경로를 가리키는 linked worktree, `git version`·`git help`는 그대로 둡니다.

세션 저장소의 raw `git add`·`commit`·`push`는 `git_finalize`로만 하도록 막고, 다른 저장소를 향한 명령은 허용합니다. 대상 저장소는 bash 도구가 실제로 명령을 실행하는 폴더로 판정합니다. 그래서 WSL에서 `cwd`를 `E:/repo`처럼 Windows 드라이브 경로로 주면 bash와 같은 규칙으로 `/mnt/e/repo`에서 확인하고, 없는 경로로 오인해 다른 저장소의 Git까지 막지 않습니다.

부작용이 없는 미리보기(`git add --dry-run`/`-n`, `git push --dry-run`/`-n`, `git commit --dry-run`)는 세션 저장소에서도 허용합니다. `git commit -n`은 미리보기가 아니라 `--no-verify`이므로 계속 막습니다. 명령 안에서 `cd <경로> && git commit …`처럼 리터럴 경로로 옮긴 뒤 `&&`로만 이어진 Git은 옮긴 폴더로 판정하므로, 이미 있는 임시 저장소에서는 그대로 실행됩니다. `cd`가 실패해도 다음 명령이 도는 `;`·`||`·줄바꿈 연결, 변수 경로(`cd "$T"`), 닫힌 괄호 subshell 밖, `GIT_DIR`·`GIT_WORK_TREE`를 쓰는 명령은 위치를 확정할 수 없어 막습니다. 아직 저장소가 아닌 폴더는 같은 저장소의 worktree일 수 있어 막으므로, 새 임시 저장소는 `git init`을 먼저 실행한 뒤 다음 명령에서 커밋합니다.

커밋은 됐는데 push가 실패했다면(원격 오류·네트워크 끊김) 같은 파일 목록으로 다시 호출합니다. 요청한 파일이 이미 깨끗하고 아직 원격에 없는 커밋에 들어 있으면, 새 커밋을 만들지 않고 그 커밋을 그대로 다시 보냅니다. 원격 브랜치가 있으면 upstream..HEAD를, 원격에 처음 올리는 브랜치면 원격 추적 ref(`refs/remotes/<remote>/*`) 어디에도 없는 HEAD 커밋을 원격에 없는 커밋으로 봅니다. 재시도 사이에 새로 바뀐 파일이 있으면 그것만 새 커밋으로 만들어 함께 보냅니다. 이미 원격에 있는 파일이나 바뀌지 않은 파일만 넘기면 기존처럼 거절합니다.

저장소에 기억 동기화 스크립트(`Tools/OMP_Global_Config/memory-sync/sync.ts`)가 있으면 `git_finalize`는 커밋 전에 이 PC의 프로젝트 기억을 `memories.jsonl`로 내보내고, 바뀐 경우 그 파일을 같은 커밋에 넣습니다. 다른 PC는 설치(`setup`)나 WSL 앱 갱신 때 이 파일을 가져옵니다. 가져오기는 기존 기억을 지우지 않고 쓰기 전에 백업을 남깁니다. `memory_edit`로 고친 기억과 무효화한 기억도 다음 내보내기에서 수정 시각이 붙어 다른 PC에 전달됩니다. 아직 내보내지 않은 이 PC의 수정은 다른 PC가 더 나중에 같은 기억을 고쳤더라도 가져오기가 덮지 않고, 다음 내보내기에서 이 PC의 수정이 이깁니다. 무효화는 되돌리지 않는 방향으로만 전달되며, 활성 상태인 기억을 무효화할 때는 본문을 바꾸지 않습니다. 내보내기가 실패해도 요청한 파일의 커밋은 진행하고 결과 문구에 실패 이유를 남깁니다. 기억 파일은 공개 미러에 올라가지 않습니다.

커밋할 소스·설정 파일(문서·그림 제외)의 폴더에서 저장소 루트까지 `HANDOFF.md`가 하나도 없으면, `git_finalize`는 커밋을 그대로 진행하고 결과 문구에 그 폴더와 함께 「작업한 프로젝트 폴더에 `HANDOFF.md`·`doc/README.md`·`doc/history` 기록을 만들어 이어서 커밋하라」는 알림을 한 줄 붙입니다. 프로젝트가 여럿인 저장소에서 문서가 없던 프로젝트의 첫 코드 커밋이 기록 없이 올라간 일을 커밋 순간에 다시 짚으려는 것입니다. 루트나 상위 폴더에 `HANDOFF.md`가 있으면 알림은 나오지 않습니다.

## 스킬 비용 리포트

omp는 세션마다 스킬의 이름과 짧은 설명만 system prompt에 넣고, `SKILL.md` 본문은 `skill://<name>`을 읽을 때마다 컨텍스트에 들어갑니다. [`skill-cost.mjs`](../Tools/OMP_Global_Config/skill-cost/skill-cost.mjs)는 설치된 스킬(`skills`, `managed-skills`)마다 설명·본문·참조 파일의 추정 토큰과, 최근 세션 기록에서 실제로 읽은 횟수·세션 수를 세어 **본문 토큰 × 읽은 횟수** 순으로 보여 줍니다. 한 번도 읽지 않은 스킬은 `[never read]`로 표시하고, 이 PC에 없는 스킬을 읽은 기록도 따로 남깁니다. 읽기 전용이며 네트워크나 모델을 호출하지 않습니다.

```sh
bun Tools/OMP_Global_Config/skill-cost/skill-cost.mjs [--days 30] [--json] [--agent-dir <dir>]
```

토큰은 토크나이저 없이 ASCII 4자당 1, 그 밖의 문자는 1자당 1로 추정하므로 순위 비교용입니다. 마지막 줄은 `skill-descriptions.db`에 저장된 설명 캐시 전체의 합계이며, 이전 설명이나 모델별 캐시가 남아 있으면 현재 세션의 실제 주입량과 다를 수 있습니다. `--days`는 세션 파일 수정일 기준이고, 읽기 횟수는 직접 `read` 호출만 셉니다. 병렬 도구나 eval 안에서 읽은 경우는 누락될 수 있으므로 `[never read]`를 모든 접근의 부재로 해석하지 않습니다.

## 기억 주제 갱신

`learn`에 선택 인자 `topic`을 주면 같은 프로젝트 bank에서 그 주제의 기억 한 행을 새로 쌓지 않고 갱신하며, 결과에 기억 id와 revision을 보여 줍니다. 동시 실행 한도처럼 값이 바뀌는 사실이 여러 버전으로 쌓여 회상 자리(기본 8건)를 서로 차지하지 않게 하려는 것입니다. 본문이 그대로이고 저장 이유만 바뀐 갱신은 기존 검색용 임베딩을 그대로 쓰고, 본문이 바뀌면 임베딩을 다시 만듭니다. `topic` 없는 `learn`은 이전과 같습니다.

## 한국어 기억 회상

패치된 내장 코어는 기억을 회상할 때 다음을 바로잡습니다. 한글 어절은 조사·어미를 뗀 어간으로도 키워드 검색을 해서 `배포를`로 물어도 `배포는`이 적힌 교훈을 찾습니다. 수면 통합이 원본 교훈 여러 개를 이어 붙여 줄인 에피소드는, 그 원본이 모두 남아 있으면 회상 후보에서 빠지고 원본이 대신 실립니다. 원본 중 하나라도 지워졌거나 새 교훈으로 대체되면 에피소드가 유일한 사본이므로 그대로 후보에 남습니다. `learn`·`retain`으로 남긴 교훈은 회상 점수에서 자동 저장 기록보다 낮게 평가되지 않습니다.

시간을 묻지 않는 일반 회상에서는 저장 시점이 최근이라는 이유로 점수를 올리지 않고, 의미 유사도의 비중을 높여 질문과 뜻이 가까운 교훈을 앞에 둡니다. 시간을 묻는 질문의 최근성 가중은 그대로입니다. 로컬 임베딩은 모델 이름에 임베딩 런타임 버전과 입력 방식을 더한 값으로 기록합니다. 이 값이 바뀌면 은행을 처음 열 때 기존 벡터를 지우고 백그라운드에서 다시 만듭니다. 다시 만드는 동안 아직 처리되지 않은 기억은 키워드로만 찾아지며, 대화 턴은 기다리지 않습니다.

질문과 기억이 서로 다른 문자(한글과 영문)로 쓰였으면 키워드가 겹칠 수 없으므로, 키워드 점수에 최소값을 주어 의미가 가까운 기억이 키워드 불일치만으로 밀리지 않게 합니다. 그래서 한국어로 물어도 영어로 남긴 교훈을 찾고, 반대도 마찬가지입니다. 로컬 e5 임베딩을 쓸 때는 키워드가 맞지 않는 기억을 걸러내는 의미 유사도 기준을 e5의 유사도 분포에 맞춰 높였습니다. 다른 임베딩 모델의 기준은 그대로입니다. 기억마다 고정 점수로 자르면 맞는 교훈까지 빠지므로 고정 하한은 두지 않습니다. 대신 로컬 e5 임베딩에서 새 세션의 첫 요청에 대한 후보들의 원시 의미 유사도 최댓값이 0.80 미만이면 그 턴에는 기억을 하나도 붙이지 않습니다. 이 기준을 넘은 턴에서도 가장 가까운 기억보다 원시 의미 유사도가 0.035 넘게 낮은 기억은 붙이지 않으므로, 한 요청에 붙는 기억 수가 줄어듭니다. 가장 가까운 기억은 항상 남습니다. 두 기준은 `mnemopi.recallDenseGate`·`mnemopi.recallDenseBand`로 바꾸거나 0으로 끌 수 있고, 직접 호출한 `recall`에는 적용되지 않습니다.

## 작업 기록 후보 안내

[`docmap-route.ts`](../Tools/OMP_Global_Config/agent/extensions/docmap-route.ts)는 사용자 요청마다 작업 폴더가 속한 프로젝트의 문서 지도(`doc/README.md`와 하위 프로젝트 지도)와 작업 기록(`doc/history/`)의 제목·`RECORD:` 헤더만으로 그 자리에서 키워드 순위를 매깁니다. 긴 요청은 앞 1,000자와 끝 1,000자만 보고, 한 글자 낱말·시간 표현·조사처럼 거의 모든 기록에 나오는 낱말은 뺍니다. 후보는 두 경우에만 고릅니다. 하나는 1위 점수가 기록 수에 맞춰 잰 기준보다 충분히 높고, 기록 대부분에 나오는 흔한 낱말을 뺀 요청 낱말 중 일정 몫 이상을 1위 기록이 담고 있을 때입니다. 다른 하나는 짧은 질문처럼 점수는 낮아도 요청 낱말 대부분을 1위 기록이 담고 그 낱말들이 드문 낱말일 때입니다. 둘 다 기록 수로 정규화하므로 기록이 많은 프로젝트에서 짧은 질문이 밀리지 않고, 여러 주제를 섞은 긴 지시가 낱말 수만으로 통과하지도 않습니다. 이렇게 고른 후보 최대 3개를 붙이기 전에, 판정 모델(Jev)에 후보마다 「이 요청이 가리키는 과거 작업의 기록인가, 낱말만 겹치는가」를 한 번에 물어 그렇다고 본 후보만 그 요청과 같은 턴에 숨김 메시지로 붙입니다. 낱말만 겹치는 새 지시나 반응에는 아무것도 붙지 않고, 남는 후보가 없으면 붙이지 않습니다. 판정이 1.5초 안에 끝나지 않거나 실패하면, 또는 실행 중에 끼어든 요청이면 판정 없이 낱말로 고른 후보를 그대로 붙입니다. 점수가 같으면 `DATE`가 최근인 기록이 앞서고, "최근"이나 날짜를 담은 질문은 그 날짜의 기록을 먼저 보입니다. 후보마다 경로, 지도 줄, `SCOPE`·`STATUS`, 질문과 가장 맞는 절의 줄 범위와 짧은 발췌가 실립니다. 에이전트는 답하기 전에 그 구간을 읽어 맞는지 확인하고, 맞지 않으면 버린 뒤 지도와 헤더를 직접 찾습니다. `STATUS: superseded-by`로 대체된 기록은 새 기록으로 바꿔 보여 줍니다.

색인을 디스크에 남기지 않습니다. 후보 판정은 설정된 판정 모델(`modelRoles.judge`)을 한 요청에 한 번 부르며, 판정 모델이 없으면 낱말로 고른 후보를 그대로 붙입니다. 지도가 없는 프로젝트, 기준에 못 미치는 요청, 서브에이전트 세션, 업데이트 재개 통지처럼 사용자가 보내지 않은 메시지, 검색 중 오류가 난 경우에는 아무것도 붙이지 않습니다. 기록이 10개 미만이거나 본문이 아주 짧은 프로젝트에서는 흔한 낱말을 가려낼 수 없어 흔한 낱말 하나로도 후보가 붙을 수 있습니다. "지난주" 같은 기간 표현은 날짜로 풀지 않고, 2,000자를 넘는 요청의 가운데 부분은 보지 않습니다. `omp -p`처럼 한 번 실행하는 CLI도 최상위 세션이면 같은 후보를 받습니다. 후보는 확인할 곳이지 근거가 아니며, 회상된 기억도 같은 이유로 단서로만 다룹니다. 지도에 줄이 없는 기록은 제목과 헤더로만 찾으므로 새 기록은 지도에 한 줄을 다는 것이 좋습니다. 지도 줄이 작업 기록 밖의 문서(`HANDOFF.md`·규칙·운영 문서 같은 `.md`)를 가리키면 그 문서도 지도 줄의 글과 문서 머리로 후보가 됩니다. 그래서 여러 기록에 흩어진 결정을 정본 문서 한 절에 모으고 지도에서 가리키면, 질문이 기록보다 그 정본을 먼저 찾습니다. `18.12.6`처럼 점으로 이은 버전 번호는 통째로 한 낱말로도 봅니다.

지도와 기록이 어긋난 곳은 요청할 때 한 번 돌리는 진단으로 봅니다. `bun Tools/OMP_Global_Config/agent/extensions/lib/docmap-lint.ts [작업 폴더]`는 지도에 링크가 없는 기록(다른 문서가 링크하는지 여부와 `RECORD:`·`SCOPE:` 헤더 누락 포함), 지도·`HANDOFF.md`·기록의 상대 링크 중 대상이 없는 것, `superseded-by`의 대상 없음·사슬 길이 초과·순환, 그리고 여러 기록의 `SCOPE`에 되풀이되지만 어떤 정본 문서의 제목·절 제목에도 없는 낱말(종합 절 후보)을 구역별 개수와 함께 보여 줍니다. `--json`은 전체 목록을, `--limit N`은 한 구역에 보이는 줄 수(기본 15)를 정합니다. 검색은 지도 링크와 무관하게 모든 기록을 색인하므로 지도 누락은 검색 실패가 아니라 탐색·완결성 문제이고, 헤더가 없는 기록만 제목으로 찾게 됩니다. 읽기만 하며 파일을 고치지 않고, 모델을 부르지 않으며, 항상 종료 코드 0입니다. 빌드·병합·배포를 막는 관문이 아니고 어디에도 자동으로 연결되어 있지 않습니다. 종합 절 후보는 작성자가 `SCOPE`에 적은 낱말만 세고, 본문에서 그 낱말을 말하는 기록 중 `SCOPE`에도 적은 기록이 너무 적은 낱말(과정·상태·호스트 이름 같은 말)은 뺍니다. 같은 주제의 다른 표기는 작업 폴더의 `doc/docmap-aliases.json`(`{"groups": [["steering", "스티어링", "steer"]]}`, 첫 낱말이 표시 이름)에 적으면 한 후보로 묶어 셉니다. 각 표기는 띄어쓰기·하이픈·점이 없는 한 낱말이어야 하고 한 그룹에 둘 이상, 파일 전체에서 한 번씩만 나와야 합니다. 이 파일이 없으면 표기마다 따로 세고, 하나라도 틀리면 파일을 통째로 무시하고 읽지 못한 파일로 보여 줍니다. 그래도 낱말 빈도로 고른 단서라 일반어가 섞일 수 있으며, `SCOPE`에 세 기록 미만으로만 적힌 주제는 보이지 않습니다.

## 편집 경로에 묶인 교훈

[`edit-lessons.ts`](../Tools/OMP_Global_Config/agent/extensions/edit-lessons.ts)는 에이전트가 `edit`·`write`로 파일을 고치려 할 때, 그 파일 경로로 저장된 기억을 찾아 도구 호출 직후의 다음 모델 요청에 단서로 붙입니다. 첫 턴 회상은 특정 파일을 고치는 시점에는 다시 나오지 않으므로, 파일에 묶인 교훈(예: 어떤 스크립트는 배포 전에 검증 모드를 먼저 돌린다)이 실수한 뒤에야 닿는 일을 줄이려는 것입니다. `learn`·`retain`으로 남긴 기억 중 본문에 그 파일 이름이 든 것만 파일마다 관련도 높은 순으로 최대 3건까지 붙입니다. 기억 검색은 본문을 앞 500자까지만 보여 주므로, 미리보기가 잘렸고 그 안에 파일 이름이 없는 후보는 `memory://<id>`로 전문을 읽어 다시 확인하고, 전문에서만 찾은 교훈은 미리보기 뒤에 파일 이름 앞뒤 발췌를 덧붙입니다. 붙는 줄은 미리보기를 공백만 정리해 싣고, 비밀번호·토큰처럼 보이는 낱말이 미리보기나 전문에 있는 기억은 내용 없이 id만 알립니다. 검색을 끝낸 경로는 세션에서 다시 찾지 않고 이미 붙인 기억은 되풀이하지 않습니다. 도구 실행을 막거나 바꾸지 않으며, 기억을 쓸 수 없거나 검색·전문 읽기가 실패하거나 1.5초 안에 끝나지 않으면 이번에는 아무것도 붙이지 않고 같은 파일을 다시 고칠 때 한 번 더 찾아 봅니다(경로마다 세션에서 최대 2번). 붙는 내용은 단서일 뿐이라 현재 지시와 정본이 우선합니다.

`proc://`·`agent://` 같은 제어 대상과 세션 임시 URI에서는 파일 편집 교훈을 찾지 않습니다. 일반 파일 경로와 `file://` URI는 실제 파일 경로로 정규화해 기존처럼 조회합니다.

## 큰 출력 검색

`artifact_search`는 이미 저장된 큰 도구 출력에서 필요한 구간을 찾는 선택적 도구입니다. 기존 OMP 도구가 실행하고 원문을 `artifact://`에 저장한 뒤에만 사용합니다. 새 명령 실행기나 MCP 서버를 설치하지 않으며, `bash`·`read`를 막거나 검색 도구로 자동 전환하지 않습니다.

`path`에는 현재 세션의 `artifact://<번호>`, `query`에는 오류 코드·함수명처럼 원문에 들어 있을 키워드를 넣습니다. 로컬 SQLite FTS5 검색이며 모델 요약이나 의미 검색이 아닙니다. 검색 조각과 함께 반환된 `read` 경로로 원문을 다시 확인하세요. 결과의 줄 번호는 저장된 artifact의 줄 번호이지, 그 안에 인용된 소스 파일의 줄 번호가 아닙니다. 검색 조각은 편집을 위한 원본 파일 읽기 증거로 등록되지 않습니다.

예: `{"path":"artifact://12","query":"ERR_CONN_RESET","limit":5}`. `path`에는 파일 경로나 줄 선택자가 아닌 artifact 번호만 넣습니다. `limit`은 기본 10, 허용 범위는 1–50이고, `offset`으로 다음 결과를 요청합니다. 반환된 다음 offset을 사용하면 됩니다.

검색은 대소문자를 구별하지 않는 단어·단어 시작 부분 기준입니다. 구두점이 있는 오류 코드는 토큰으로 나누어 찾고, 공백으로 나눈 검색어를 모두 포함하는 구간이 없으면 일부 검색어만 포함하는 결과로 바뀌었다고 표시합니다. 자연어 질문을 이해하거나 한국어 형태소를 분석하지는 않습니다. 한 artifact의 색인 허용 크기는 32 MiB이며, 넘으면 일부만 몰래 색인하는 대신 기존 `read` 사용을 안내합니다.

Main과 자식 에이전트가 원래 공유하던 artifact 저장소는 함께 사용할 수 있습니다. 서로 다른 최상위 세션에서는 같은 번호라도 다른 출력으로 취급하며, 현재 저장소에 없는 번호를 다른 세션에서 대신 찾지 않습니다. 도구 인스턴스마다 색인 하나를 필요할 때 메모리에 만들고 원문이 바뀌면 다시 만듭니다. 세션 전환·종료나 유휴 상태에서는 버리며 원문을 변경하거나 별도의 장기기억으로 보관하지 않습니다.

매우 긴 한 줄은 검색에서 찾았더라도 기존 `read`가 앞부분만 반환할 수 있습니다. 이때 검색 조각은 여전히 단서이며 원문 확인을 대신하지 않습니다. `read`의 부분 반환 안내에 표시된 원본 파일을 기존 `grep`·`bash` 등으로 확인해야 합니다. 줄을 나눈 경계의 중첩 때문에 같은 긴 줄의 결과가 다른 구간으로 다시 나올 수도 있습니다.

검색 결과가 없거나 일부만 보인다고 오류가 없다는 뜻은 아닙니다. 표현이 다른 오류나 키워드 밖의 문맥을 놓칠 수 있으므로 기존 `read`·범위 읽기·`grep`으로 돌아갈 수 있습니다. 정확한 문자열을 이미 알고 있으면 `grep`이 적합하며, 검색 결과가 짧아진 것은 더 적은 구간을 보여준 결과일 수도 있습니다. 최초 색인과 원문 재조회에도 시간이 들며, 토큰·비용·완료 시간의 고정 절감률을 보장하지 않습니다.

## omp core 패치

[`Tools/OMP_Global_Config/patches/`](../Tools/OMP_Global_Config/patches/)에는 이 하네스의 동작을 omp core에 맞춰 적용하는 패치와 적용·검증 도구가 있습니다. 소스 `setup`은 빌드 뒤 앱 자체 SDK에 패치를 적용·검사하고, npm의 `postinstall`은 설치된 `cuelo` 패키지 SDK를 준비합니다. **사용자가 별도 설치한 standalone `omp.exe`는 이 패치의 대상이 아닙니다.** `apply-core-patch.mjs`, `validate-harness-policy.mjs`, `core-*-test.ts`가 관련 도구·회귀 검사를 담습니다. 이 공개 저장소의 CI는 앱 빌드·테스트를 `Verify build (Linux)`(Ubuntu)에서 돌립니다. 하네스 검사는 `Verify harness (Linux, extensions)`와 `Verify harness (Linux, core)` 두 러너가 동시에 맡습니다. 두 러너 모두 앱이 고정한 core 버전을 새로 설치·패치한 뒤, 앞의 것은 확장·가드·finalizer 테스트를, 뒤의 것은 core 회귀 검사를 돌립니다. core 회귀 검사는 파일마다 별도 프로세스와 임시 HOME을 쓰므로 CPU 수만큼 동시에 실행하고, 로그는 끝난 뒤 파일 순서대로 출력합니다. Windows에서는 `Verify build (Windows smoke)`가 설치·SDK 준비·typecheck·build·웹 런타임 패치만 확인합니다. 확장 테스트는 하네스가 등록하는 모든 도구의 입력 스키마를 코어의 전송 변환에 넣어, JSON Schema 키워드 자리(`properties`·`required`·`enum`·`type`)에 잘못된 값이 생기지 않는지 확인합니다. 패치된 변환기는 실제 하위 스키마만 정규화하여, `properties`처럼 키워드와 같은 파라미터 이름의 빈 속성 맵과 `default`·`const`·`enum`·`examples`의 데이터를 보존합니다. 기존 boolean 스키마 의미와 공개 도구 인자 이름은 바꾸지 않습니다. core 러너는 사용자 셸 PTY 경로 검사가 실제로 돌아 통과해야 성공합니다. 정책·생성 에이전트 일치, source manifest, eval 분석, setup·WSL 배포 도구 테스트는 공개 미러에 없는 파일을 읽으므로 원본 저장소에서만 Linux로 실행하고, PowerShell 도우미를 재생하는 내용 검사만 Windows에서 수동으로 실행합니다.

Codex WebSocket에서 실행 중 끼어든 메시지(live steering)를 서버가 `unsupported_native_inflight_message`로 거절하면, 코어 18.5.1부터는 upstream 복구를 따릅니다. 그 세션에서는 이후 끼어들기를 보내지 않고, 거절된 연결을 닫은 뒤 새 연결에서 현재 요청을 다시 시도합니다. 거절된 끼어들기 입력은 유실되지 않고 되돌려집니다. 패치된 내장 코어는 사용자가 직접 보낸 Steer가 도구 호출 인자를 쓰는 도중에 거절된 경우도 오류로 끝내지 않습니다. 이미 보인 본문은 남기고, 인자가 끝나지 않아 실행되지 않은 도구 호출은 버린 뒤, 같은 실행에서 Steer를 한 번 실어 다시 요청합니다. 도구 호출이 완성된 뒤에 거절되면 그 도구를 먼저 실행하고 Steer는 결과 뒤에 싣습니다. 실제 서비스에서의 거절 순서는 로컬 WebSocket fixture(`core-native-inflight-test.ts`·`core-steer-stream-test.ts`)로만 확인했습니다.

Codex의 `Codex steering rejected` 진단 로그에는 입력 준비 시간(`prepareMs`)과 전송 후 거절 응답까지의 시간(`ackMs`)을 밀리초로 남깁니다. 수락 로그와 같은 시각값을 사용하며, 사용자 메시지 본문을 추가로 기록하지 않습니다. 이 값은 거절까지의 처리 시간을 구분하는 진단 정보이지, 브라우저에 답변이 표시될 때까지의 전체 지연이나 속도 개선을 뜻하지 않습니다. 끼어들기 지원 여부·재시도·취소·입력 전달 동작은 바꾸지 않습니다.

`read` 결과는 두 단계에서 줄어들 수 있습니다. 먼저 `read`가 자기 예산 안에 온전히 들어오는 줄까지만 모으고, 그다음 도구 결과가 출력 상한을 넘으면 앞뒤만 남기고 가운데를 생략한 뒤 전체 출력을 `artifact://`에 저장합니다. 이때 `Use :N to continue`의 N은 원본 파일 줄 번호로, 실제로 전달한 마지막 줄 바로 다음입니다. 반면 `Showing lines A-B and C-D of T`의 범위는 원본 파일이 아니라 저장된 출력(artifact)의 줄 번호입니다. 생략된 가운데는 그 artifact를 범위로 읽거나 본문 줄 앞의 원본 줄 번호를 보고 원본 파일을 범위로 다시 읽어 가져옵니다. 첫 줄 하나가 `read` 예산보다 크면 다음 줄로 넘어가라는 안내는 하지 않습니다. 패치된 내장 코어는 줄 단위 편집 표시(hashline) 모드에서 이 줄을 한 바이트도 보여 주지 않은 경우, 안내에도 전달량을 0B로 적습니다. 그 줄의 앞부분은 `:raw` 선택자로 볼 수 있습니다. 긴 줄을 표시 폭에서 자른 경우는 `Some lines truncated to …`로 따로 알립니다.

WSL에서 에이전트 셸이 Windows 실행 파일을 띄울 때 패치된 내장 코어는 `WSL_UTF8`을 `WSLENV`에 넣어 Windows 프로세스까지 넘깁니다. interop은 `WSLENV`에 이름이 든 변수만 넘기므로 `WSL_UTF8=1`만으로는 효과가 없습니다. 그래서 `wsl.exe` 자체 메시지(`--version`·`--list`·오류)가 UTF-16 대신 UTF-8로 와서 깨지지 않습니다. 이미 설정된 값과 기존 `WSLENV` 항목은 보존하고, WSL이 아닌 환경은 이전과 같습니다. PowerShell·cmd처럼 콘솔 코드페이지(CP949)로 출력하는 프로그램은 이 설정과 관계없으므로 출력 쪽에서 변환해야 합니다.

## 미결 작업 처리

[문서 지도 규칙](../Tools/OMP_Global_Config/agent/rules/docs-handoff.md)은 세션이 관련 작업을 시작할 때 `HANDOFF.md`의 연관 항목을 현재 소스·기록과 대조해 끝남·실행 가능·대기·타 owner 진행 중으로 가르고, 이번 요청이 승인한 범위의 실행 가능 항목만 검증까지 수행한 뒤 현재 문서와 `HANDOFF.md`를 맞추도록 정합니다. 기준이 되는 `HANDOFF.md`는 바꾼 파일에서 저장소 루트까지 올라가며 처음 만나는 것이고, 하나도 없으면 첫 소스 변경 커밋에서 작업한 프로젝트 폴더에 `HANDOFF.md`·`doc/README.md`·`doc/history` 기록을 새로 만듭니다. `HANDOFF.md`를 맞춘다는 것은 행을 덧붙이는 것이 아닙니다. 남은 행동·관찰 조건·새 경계만 남기고, 이번 작업으로 끝난 행은 같은 커밋에서 지웁니다. 그 자리에서 끝난 작업은 `HANDOFF.md` 대신 작업 기록에 남깁니다. 날짜·관측·사용자 기기·다른 PC·승인 대기 항목은 조건이 충족되기 전에는 실행하지 않으며, 적힌 TODO는 승인이 아닙니다. 미해결 실패는 기존 실패 환류 규칙대로 증거로 원인을 좁히고 다른 조치를 한 뒤 원래 실패 경로를 다시 실행하며, 같은 시도를 그대로 되풀이하거나 검증을 약화하지 않습니다. 막히면 증거·시도·차단 사유·재검증 기준을 `HANDOFF.md`에 남겨 다음 관련 세션이 이어받게 합니다. 상시 감사·백그라운드 자동 수정·새 장부나 hook은 없습니다.

AI가 추가로 제안하는 개선은 착수 전에 **어떤 실제 실패를 고치는가**, **왜 가장 작은 수정인가**, **어떤 관측 결과면 완료인가**를 근거와 함께 제시합니다. 하나라도 빠지면 구현을 보류하고 읽기 전용 원인 조사는 할 수 있습니다. 사용자가 명시적으로 요청한 새 기능에는 기존 실패가 있어야 한다는 요건을 적용하지 않습니다. 별도 검사기나 자동 차단 장치를 추가하는 것이 아니라 기존 최소 변경 규칙의 착수 기준입니다.

사용자 고유의 결정(원하는 결과, UI 동작, 데이터 처리·판정 기준, 기존 기능 보존 여부)이 요청·코드·기억·문서로 정해지지 않았으면 그 부분을 구현하기 전에 추천안과 이유를 붙여 묻습니다. 이런 질문은 2분 뒤 추천안 자동 선택을 켜지 않으며, 무응답·취소면 그 부분만 보류하고 나머지 작업을 계속합니다. 결과를 바꾸지 않는 내부 구현 선택은 묻지 않습니다. 턴을 끝내기 전에는 남은 항목을 사용자 결정·승인 필요, 외부 대기, 합의된 한계, 승인 범위 밖으로 나눕니다. 어디에도 들지 않고 지금 처리할 수 있는 항목(이번 변경의 결함·어색한 표시, 빠진 검증)은 위의 "추가 개선"이 아니라 요청의 일부로 보고 그 턴에 처리하며, 남기는 항목에는 분류와 재개 조건을 적습니다.

설계 선택과 최종 수용의 근거를 남기되, AI의 재평가만을 독립 검증으로 보거나 테스트 통과를 사용자 PC 실동작·제품 전체 품질의 증거로 확대하지 않습니다. 확인·미확인 범위를 구분하고, 실패는 모델 판단·구현 오류, 도구·환경 한계, 요구사항 누락·충돌을 근거로 나눠 보고합니다. 원인이 확인되지 않았으면 미상으로 남기며 사용자 책임으로 단정하지 않습니다.

회귀 테스트는 수정 전에 재현한 그 결함 때문에 실패하고 수정 후 통과했는지 확인해 보고합니다. 테스트를 쓰거나 남길 때는 동작을 깨면 실패하고 내부 구조만 바꾸면 통과하는지 두 가지 가상 수정으로 판단합니다. 성능·지연·크기 수치로 결론을 낼 때는 측정 횟수, 편차, 수치를 묶는 요인을 함께 적습니다. 전후 비교는 같은 조건에서 번갈아 여러 번 재고, 차이가 편차 안이면 판정 불가로 둡니다. 디버깅 스킬(`systematic-debugging`)은 수정 전에 세 가지를 확인하게 합니다. 문제를 일으킨 상태가 애초에 정당한지, 재시작 뒤에만 나는 실패라면 저장된 상태를 먼저 의심했는지, 같은 패턴이 다른 곳에도 있는지입니다. 예상과 다른 결과가 나오면 코드를 더 고치기 전에 관측 대상부터 확인하게 합니다. 같은 전제 위에서 수정이 두 번 실패하면 그 전제를 적고 직접 검증하게 하며, 반박된 가설 때문에 넣은 변경은 되돌린 뒤 내보내게 합니다. 위험한 변경은 그 변경이 안전한 근거가 되는 사실 하나를 기존 확인 실행으로 직접 시험합니다. 심볼 검색이나 앱 타입 검사가 닿지 않는 JSON·wire 형식 소비자, 로컬 의존성 패치, 종료 시점이 그 대상입니다. 모델이나 운영 방식을 비교하는 평가에서는 정답·채점 기준·비교 대상 이름을 후보가 읽을 수 있는 파일과 프롬프트 밖에 두고, 판정 모델에는 익명 라벨만 보입니다. 이 항목들은 앞의 원칙처럼 따로 검사기를 두지 않는 작업 기준입니다.

구조만 바꾸는 리팩터링은 영향받는 반환값·저장 결과·부수효과를 지키는 기존 검사를 같은 입력과 기대값으로 변경 전에 한 번, 변경 후에 한 번 돌려 둘 다 통과한 명령과 종료 코드를 남깁니다. 기존 검사가 그 동작을 지키지 못할 때만 현재 동작을 고정하는 최소 검사를 먼저 만듭니다. 버그 수정의 실패→통과와 달리 원본을 일부러 실패시키지 않고, 도중에 찾은 결함은 동작 보존 범위와 나눠 보고합니다. 외형을 그대로 두라는 요구가 있는 화면 교체 작업만, 같은 창 크기·데이터·화면 상태로 전후 화면을 비교해 잘림·간격·배치 변화를 확인합니다. 모든 UI 작업에 픽셀 차이 0을 요구하지는 않습니다. 새 모듈 경계·상태 소유자·공개 API를 정하는 큰 설계 결정에서는 Main이 구조가 다른 두 안을 호출 방법·소유권·유지 비용으로 비교하고, 고른 이유를 작업 기록에 남깁니다. 이 비교를 위해 다른 모델을 따로 부르지 않습니다.
