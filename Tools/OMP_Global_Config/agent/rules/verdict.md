# 착수 계약과 최종 판정

## 착수 전에 확정할 것

- 최종 목표와 산출물, 완료 조건과 필요한 증거.
- 확정된 설계·인터페이스·제약과 보존해야 할 기존 동작.
- 검증되지 않았지만 진행에 사용하는 가정, 데이터·보안·호환성·배포·회귀 위험, 사용자 승인이 필요한 항목.
- 완료 조건은 **관측 경로가 실재하는 것만** 쓴다. 통과 경로가 없는 조건은 조건이 아니라 미확인
  항목이고, 그런 조건을 기대치·채점표에 넣으면 영구 실패만 만든다. 새 계약을 정본에 단정으로
  쓰기 전에 그것을 소비하는 경로(도구 스키마·설정 키·코드)를 증거로 확인한다.
- 모호성은 먼저 증거로 좁힌다. 명시 요구·승인된 계약, 실제 호출부와 데이터 흐름, 테스트·재현
  결과, 현재 동작과 문서로 방향이 정해지면 근거를 남기고 진행한다. 테스트·문서·현재 동작 중
  어느 하나도 자동으로 정답이 아니며 요구와 충돌하면 실제 동작을 확인한다. 결과의 제품 의미를
  바꾸는데 증거로 정할 수 없거나 권한·외부 승인이 없는 항목만 사용자 판단으로 올리고, 그 부분이
  막혀도 독립적으로 허용된 작업은 계속 수행한다.

## 증거

- 최소 증거는 변경 파일, 핵심 변경, 실행한 검증 명령과 결과, 계획과의 차이, 남은 위험과 미검증 조건이다.
- 수용 조건이 둘 이상이면 증거를 **조건별로 연결**한다. 조건마다 충족(확인한 동작 + 원문 증거
  위치)이나 미확인(막힌 이유 + 필요한 확인)을 revision과 함께 남긴다. "테스트 통과"는 조건 하나의
  증거일 수 있어도 조건 전체의 증거가 아니다. 최종 수용에서 Main이 빠진 조건을 확인한다.
- 하위 에이전트 보고가 부족하면 전체를 다시 시키지 말고 빠진 증거만 요청한다.
- 위임한 조각의 Maker는 source·contract·caller 증거와 자기 검증의 exact command·cwd·exit
  status·관측·raw artifact locator·재사용 근거·미검증 조건을 함께 제공한다. 위임한 조각에서
  Main은 조립·한정된 확인·finding 판단·최종 수용을 맡고, 그 조각의 집중 검사를 같은 환경·같은
  조건으로 반복해 확인하지 않는다(공통 격리 환경과 필요한 전체 빌드·통합·수용 검사는 Main이
  실행한다). `routine`은 Main이 직접 구현하고 검증해 같은 증거를 스스로 남긴다.
- 검수는 Main이 소유한다. Main은 owner의 불변 raw artifact와 locator를 검수 대상으로 쓰고,
  owner의 집중 검사를 같은 환경·조건에서 반복하지 않는다. 공통 격리 환경과 필요한 전체
  빌드·통합·수용 검사는 Main이 frozen revision에서 실행하며, 검사가 도는 동안 그 revision을
  수정하지 않는다. 아직 실행 중인 필수 검사는 gap이 아니라 pending으로 남기고 그 revision을
  PASS로 닫지 않는다. 검수 주체를 다른 역할이나 다른 세션으로 넘기지 않는다. 절차는
  `rule://subagent`의 「검수와 수용」이 정본이다.

`large` 분해 트리거와 검수 트리거는 다르다. public/shared interface, cross-module contract,
shared state, data flow, complex state transition, 여러 조각이 한 실행 경로로 합류, meaningful
existing-caller regression risk, auth/authz/secret review, Main이 제공 증거로 닫을 수 없는 경우 중
하나가 있으면 `integration-risk`이고 Main이 그 delta를 검수한다. 나머지 `independent-only`
large에는 별도 검수를 요구하지 않는다. material/high-risk는 모든 관련 owner 수렴 → Main 검수의
직렬 계약을 유지한다.

## 검수와 최종 판정

검수는 Main이 중간과 최종 두 단계로 소유한다. 아래는 Main이 검수할 때 적용하는 기준이다.

Maker 보고를 받은 뒤 Main 검수에 들어가기 직전의 `pre-review`는 런타임(`jev-runtime`)이 로컬 구조 관측으로
처리한다(`harness-policy.json` `routing.typedJudgmentRouting.batching`·`observation.localStructuralPlacements`).
metadata 유효성·검증 증거 존재·권한 충돌 같은 셀 수 있는 신호만 `[JevRuntime:pre-review]` advisory로 싣고
`judge()`를 호출하지 않는다. Main도 같은 보고에 수동 `judge()`를 따로 부르지 않는다. 요구-증거 정합,
미확인 수용 조건, 증거를 넘는 보고 주장은 advisory가 판정하지 않는 의미 판단이므로 아래 결정론적
검수에서 Main이 원본 증거로 직접 확인한다. 관측할 수 없는 의미는 unknown으로 두고 개수나 키워드로
추정하지 않는다. exit status·파일·경로 소유권·권한·test result·배포 승인은 결정론 증거가 정본이고,
high-risk 분류·승인과 최종 판정은 Main만 소유한다.

- **증거 요구사항.** 판정 전에 검수 대상과 계약, 변경 경로, 최종 Diff, 영향 경계, raw 출력이
  있는 검증 증거, 알려진 미검증 항목을 갖춘다. `TARGET`·`CHANGED PATHS`·`FINAL DIFF`·
  `IMPACT BOUNDARY`·`VALIDATION EVIDENCE`·`KNOWN UNVERIFIED` 여섯 이름과 그 순서는 권장 형식이지
  합격 조건이 아니다. 경로·`artifact://`·`agent://`·이미 받은 원문 tool 출력처럼 **닿을 수 있는
  원본 artifact가 그 사실을 공급**하며 packet에 다시 붙여넣으라고 요구하지 않는다. 실질적인
  결손만 판정을 막는다.
- `FINAL DIFF`는 삭제를 포함한 frozen raw before/after 또는 그것을 가리키는 불변 참조여야 한다.
  현재 파일, 요약, 가변 `HEAD` 이름은 Diff를 대체하지 못한다. `VALIDATION EVIDENCE`에는 검사마다
  exact command·exit status·닿을 수 있는 raw 출력 artifact나 locator가 들어간다. `CHANGED PATHS`의
  분류와 impact-bearing caller index는 점검을 안내할 뿐 정확성을 세우지 못한다.
- **비교 기준선은 Main의 지시가 아니라 사용자 요구와 브리프에 실린 수용 조건이다.** 지시를 완벽히
  구현했는데 수용 조건이 미충족이면 PASS가 아니라 요구 누락 finding이다. packet에 요구나 수용
  조건 자체가 없으면 지시에서 추론하지 말고 그 부재를 gap으로 보고한다. 수용 조건별 증거 연결도
  실제 Diff와 대조해 조건마다 충족-증거 또는 미확인-사유가 있는지 보고, 없으면 실질 gap으로 본다.
- 영향받는 caller만 추적한다. public/shared contract, shared state, data flow, 호환성,
  material-risk 동작을 건드리면 그 caller를 본다. 요구 누락, 논리 결함, 회귀, 경계값, 데이터 손실
  위험, 불필요한 변경, 테스트 공백을 확인하고, 구체적인 모순이나 의심스러운 주장이 있을 때만 표적
  점검으로 범위를 넓힌다.
- **material-risk는 기술명이 아니라 consequence다.** `harness-policy.json`
  `routing.high-risk.materialRiskDefinition`으로 판정한다: 되돌릴 수 없는 데이터·설정·스키마 변경,
  시스템 밖으로 나가는 결과(배포·결제·실제 장치·출력·외부 전송), 제품 의미를 결정하는 계산·판정,
  기존 소비자·데이터·API 계약 파괴, 물리 안전이 걸린 출력. VB6/COM/OCX, 32-bit·XP 대상, 모니터링,
  protocol 처리, timeout·retry·reconnect, 단순 전달은 그 자체로 올리지 않는다. 실행 환경이 아니라
  **수정한 코드의 성질**이 분류하며, 그 분류는 도메인 중립이다 — `irreversible-state-change`·
  `external-side-effect`·`correctness-defines-product-meaning`·`state-machine-transition`·
  `trust-boundary`·`compatibility-break`·`artifact-representation`에 걸리면 fixture·mock·평가용이어도
  high-risk다. 단 `trust-boundary`는 감시만 붙이고 auth·authz·secret 자체는 integration-risk
  검수로 남는다. 프로젝트별 구체 목록은 그 프로젝트 저장소의 `AGENTS.md`가 이 분류에 사상한다
  (`materialRiskDefinition.projectOverlay`).
- **finding 우선순위는 실제 결함과 안전 영향으로 정한다.** 범위 밖 정리, 동작 영향 없는 잔여물,
  이름·문구, 스타일·API 형태 선호는 차단 사유가 아니다. 비차단으로 한 번만 적고 그것 때문에 PASS를
  보류하거나 새 검수 회차를 열지 않는다.
- **재검수 규칙.** 반증이나 그 finding을 건드린 변경 없이 이미 닫힌 finding을 다시 열지 않고, 새로
  발견한 실제 결함은 닫힌 finding에 접지 않고 새 finding으로 보고한다. 같은 finding이 미해결로
  돌아오면 기존 증거가 무엇을 지지하는지 밝힌다 — 요구가 모순인지, 검수 판정이 틀렸는지, 구현이
  틀렸는지, 증거가 없는지 — 그리고 그 근거로 판단한다. 무효화되지 않은 delta·증거는 새 의심 근거
  없이 재검수하지 않는다.
- 동일 revision에서 확인 가능한 지적은 변경·영향 계약·증거를 한정된 범위에서 본 뒤 한 묶음으로
  전달한다. 같은 변경에 뒤늦게 지적을 더한 왕복은 Main의 검수 분할 문제이지 Maker 실패 횟수로
  세지 않는다. 새 증거와 실제 반복 오류는 구분하며 R번호만으로 owner를 바꾸지 않는다. 인수가
  필요하면 기존 writer를 정지하고 변경·job·검증 증거를 회수해 소유권 이전을 명시한 뒤 진행한다.

Main은 근거가 있는 finding을 각각 다음 중 하나로 닫는다.

- `ACCEPTED`: 담당 `maker`가 수정하고 영향받은 검증 증거를 갱신했으며 필요한 delta 검토까지
  끝났다. 변경 없는 범위의 증거는 재사용한다.
- `REJECTED_WITH_EVIDENCE`: 코드·테스트·요구사항 근거로 오탐임을 설명했다.
- `ESCALATED`: unresolved major finding이거나 Main도 확신할 수 없어 사용자 판단으로 올렸다.

모든 finding을 종결한 뒤 Main이 범위 준수, 완료 조건, 검증 근거와 남은 위험을 자연스러운
한국어로 전한다. 판정 의미는 PASS·REWORK·INCONCLUSIVE로 구분하되 `FINAL`·`OWNER` 같은
고정 표시는 사용자나 실제 parser가 요구할 때만 쓴다. SubAgent의 자체 판정은 최종 승인이 아니다.

해결 가능한 `REWORK`와 보충 가능한 증거 누락은 사용자 재지시를 기다리지 않고 내부 작업으로
이어간다. 중간 실패를 보고했다는 사실만으로 원래 과제를 완료 처리하지 않는다. 재작업 뒤에는
영향을 받은 검증을 갱신하고, 검수 전제였던 공개 계약·위험·중요 실행 경로가 달라졌으면 그 delta를
다시 검수한다. 무효화되지 않은 증거는 다시 만들지 않는다.

## 종료 조건

- 모든 검수 finding이 `ACCEPTED`, `REJECTED_WITH_EVIDENCE`, `ESCALATED` 중 하나로 닫혔다.
- `integration-risk` large와 material-risk 산출물에는 Main의 중간 검수와 최종 수용 증거가 있다:
  확정 delta에 대한 검수와, 그 revision의 수용 조건별 증거 연결을 실제로 확인한 기록.
  `independent-only` large에는 별도 검수를 요구하지 않는다.
- 인터페이스, 공유 타입, 설정, 데이터 흐름에 필요한 최소 통합 검사를 마쳤다.
- material-risk 변경에는 실제 출력 안전, 측정·판정 정확성, 데이터·설정 보존, 권한,
  롤백 가능성 중 해당 증거가 있다.
- 열린 위험과 미검증 조건을 숨기지 않고 영향과 후속 조치를 적는다.
- 수용 조건을 막는 미해결 escalation이나 미검증 항목이 있으면 전체 과제를 PASS로 닫지 않는다.
  부분 성과를 보고하더라도 남은 조건을 그대로 남긴다.
- 사람만 할 수 있는 확인은 agent가 흉내내지 않는다. 사용자가 같은 화면을 직접 볼 수 있으면 사용자
  관찰이 우선이고(미관·레이아웃 감각, 실장비 동작, 로그인·권한이 걸린 외부 연결), 실장비·실 IO·
  실운영 데이터가 필요한 항목은 코드·build·텍스트 관측 검증을 끝낸 뒤 3줄 이내 인계(무엇을 열지 /
  어떤 순서로 클릭할지 / 합격 기준)와 함께 `pending-user-device-check`로 보고한다 — **PASS가 아니다**.
  인계 뒤 idle로 기다리지 않고, 사용자 관찰은 ground truth로 항목을 닫으며 다시 검증하지 않는다.
  정본은 `implementationOwnership.writerValidation.userObservation`과 `deviceVerificationHandoff`다.

여러 웨이브로 가는 작업에서는 목표와 완료 조건, 확정 사항, 작업 패키지의 담당·검수자·의존성·파일
소유권·상태, 증거, 위험, 다음 웨이브만 최신으로 유지한다.

## 작업·모델·에이전트 효율을 판정할 때

- 원인 가설 제출은 효율 검증이 아니다. 실제 완료한 수용 조건·회귀·미완료 항목을 먼저
  확인하고, 그 성과에 사용한 경과 시간·모델 호출·생성 토큰·추정 비용·재작업·사용자 개입을
  함께 판단한다. 단계나 역할이 다른 호출 수·응답 중앙값만으로 모델 우열을 정하지 않는다.
- 기존 기록으로 확인 가능한 낭비와 비교 불가능한 부분을 분리한다. 오류가 없는 기록도
  효율적이라는 증거는 아니며, 병목 구간 전체를 절약 가능한 시간·비용으로 계산하지 않는다.
  인수받은 코드·캐시·빌드·검증 준비물을 밝히고 인수 후 짧은 마감 시간을 독립 구현과 비교하지 않는다.
- 합산 전 세션·요청·종료 cutoff와 분석 자체 제외 범위를 고정한다. 모델 생성 시간·도구 실행·
  대기·사용자 요청 전환을 구분하고, 병행 구간을 경과 시간처럼 더하지 않는다. `unmeasured`를
  대기 원인으로 단정하지 않는다. 캐시 포함 총토큰과 생성 토큰, 기록상 추정 비용과 청구액도 구분한다.
- 모델·운영 방식의 상대 효율을 주장하려면 같은 시작 산출물·환경·수용 조건의 비교가 필요하다.
  비교가 없으면 운영상 결함은 판정하되 모델 순위·개선율은 미검증으로 남긴다. 유료 재실행이나
  새 벤치마크는 별도 승인 없이 시작하지 않는다.
- 마지막에는 관측된 실패마다 기존 규칙의 누락인지 실행 위반인지 판별하고, 바꿀 행동과
  예상 효과를 구분해 제안한다. 가설 나열로 끝내거나 반대로 규칙·스킬을 무조건 늘리지 않는다.
  보완했다면 같은 수용 조건을 유지하는지 확인하고, 새 지침의 실제 효율 개선은 후속 동등 작업의
  관측 전까지 검증됐다고 말하지 않는다.

### 실패를 다음 작업의 실행 방식으로 환류

- **실패를 해결한 뒤, 종료 보고 전**에 owner는 실패→변경한 조치→성공 검증의 근거를 연결한다.
  입력·경로·인자 실수, 환경·의존성, 권한·provider, 제품 결함, 의도한 실패 확인(negative probe)을
  구분한다. 도구가 실패로 표시됐다는 사실만으로 agent 실수나 같은 원인이라고 단정하지 않는다.
- 수치가 필요하면 기존 trace 분석의 `evidence.observability.toolOutcomes`와 `repeatedReads`,
  `reworkEvents`를 재사용한다. 호출 수와 **결과가 관측된 호출만을 분모로 한 실패율**을 함께 보고,
  결과 미회수·호출 없는 결과·child 귀속 누락을 따로 남긴다. 비정상 exit와 도구 오류의 합집합을 세며
  한 호출을 두 번 실패로 세지 않는다. 비동기 작업의 접수 응답은 실제 작업 완료가 아니다.
  분석 결과가 없으면 해당 요청에서 이미 확보한 호출/결과만 한정해 사용하고 없는 수치는 미관측으로 둔다.
  숫자를 채우려고 새 상시 수집기·전체 이력 재분석·유료 재실행을 붙이지 않는다.
- 같은 파일을 다시 읽은 이유가 변경·새 질문·새 증거인지 확인한다. 필요한 조사와 중복 호출을 구분하며
  총 호출 수·실패율·낮은 오류율만으로 낭비나 모델 우열을 정하지 않는다.
- **원인과 해결책이 검증되고 재사용할 가치가 있을 때** 기존 `learn`/memory 경로에 적용 조건,
  원인, 달라진 행동, 성공 근거 locator를 남긴다. 원문 로그·비밀은 넣지 않는다. 이미 충분한 규칙을
  어긴 실행 실수면 기존 규칙 적용을 교정하고, 규칙·Skill 누락일 때만 해당 정본을 보완한다.
  미확정 가설이나 실패율 임계값으로 규칙을 자동 생성·변경하지 않는다.
- **다음 유사 작업의 같은 도구·경계에 진입하기 전** 적용되는 교훈을 현재 문맥이나 `recall`로 확인해
  실행 방식에 반영한다. 이미 문맥에 있는 내용을 또 조회하지 않는다. 같은 실패가 재발하면 교훈이
  없었는지, 조건이 달랐는지, 실행에서 누락했는지를 가르고 같은 규칙을 하나 더 쓰지 않는다.
- 분류 보정은 완료된 **위임 조각**의 수용 결과·재작업 비용과 발주 당시 남은 판단을 함께 본다.
  NORMAL 안에서 기존 계약과 명세로 정해지는 과제는 Main 직접 처리 routine과 구분하며, 이를 이유로
  HARD로 승격하지 않는다. 등급별 위임 비율을 맞추려는 배정, 호출·실패 수 기반 자동 승격, 실행 중
  재발주는 금지한다.
  효과는 후속 동등 작업의 재발·불필요한 호출·재작업이 줄었는지 관측한 뒤에만 검증됐다고 말한다.
